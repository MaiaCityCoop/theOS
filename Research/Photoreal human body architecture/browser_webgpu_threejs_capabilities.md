## 1. three.js r187 under WebGPURenderer: what exists for skin and characters

### Takeaway
r187 has no true subsurface diffusion and no skin or "digital human" example: `MeshSSSNodeMaterial` is the 2011 Barré-Brisebois back-light translucency term bolted onto the physical material's direct-light loop, and the addon named `SSSNode` is screen-space *shadows*, not subsurface scattering. What r187 does give is every building block a custom skin pipeline needs: MRT passes, full-screen quad and UV-space rendering, compute with storage buffers and storage textures, compute skinning, GTAO/SSAO, contact shadows, bilateral and depth-aware blurs, and TRAA/TAAU.

### Cited Findings

**MeshSSSNodeMaterial (the only "SSS" material)**
- **[S]** File `src/materials/nodes/MeshSSSNodeMaterial.js`. It extends `MeshPhysicalNodeMaterial`, is described in its own doc comment as "an experimental extension", and its lighting model `SSSLightingModel extends PhysicalLightingModel` cites one reference: "Approximating Translucency for a Fast, Cheap and Convincing Subsurface Scattering Look" (Barré-Brisebois, GDC 2011). — [MeshSSSNodeMaterial.js L39-L75](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/MeshSSSNodeMaterial.js#L39-L75)
- **[S]** The whole model is four lines inside `direct()` (run once per direct light): `scatteringHalf = normalize( lightDirection + normalView * thicknessDistortionNode )`; `scatteringDot = pow( saturate( dot( positionViewDirection, -scatteringHalf ) ), thicknessPowerNode ) * thicknessScaleNode`; `scatteringIllu = ( scatteringDot + thicknessAmbientNode ) * thicknessColorNode`; `reflectedLight.directDiffuse += scatteringIllu * thicknessAttenuationNode * lightColor`. It then calls the normal physical `direct()`. There is no blur, no diffusion profile, no shadow-map thickness. — [MeshSSSNodeMaterial.js L47-L65](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/MeshSSSNodeMaterial.js#L47-L65)
- **[S]** Inputs and defaults: `thicknessColorNode = null` (the term is enabled only when this is non-null, via the `useSSS` getter), `thicknessDistortionNode = float(0.1)`, `thicknessAmbientNode = float(0.0)`, `thicknessAttenuationNode = float(0.1)`, `thicknessPowerNode = float(2.0)`, `thicknessScaleNode = float(10.0)`. — [MeshSSSNodeMaterial.js L92-L147](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/MeshSSSNodeMaterial.js#L92-L147)
- **[S]** The example `webgpu_materials_sss` applies it to the Stanford bunny (`models/fbx/stanford-bunny.fbx`) with a baked thickness texture `models/fbx/bunny_thickness.jpg`: `material.thicknessColorNode = texture( thicknessTexture ).mul( vec3( 0.5, 0.3, 0.0 ) )`, distortion 0.1, ambient 0.4, attenuation 0.8, power 2.0, scale 16.0. It is not a head or a skin demo. — [webgpu_materials_sss.html at r187](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_materials_sss.html)
- **[S]** The WebGL counterpart `examples/jsm/shaders/SubsurfaceScatteringShader.js` cites the same GDC 2011 talk and has the same uniforms (`thicknessMap`, `thicknessColor`, `thicknessDistortion` 0.1, `thicknessAmbient` 0.0, `thicknessAttenuation` 0.1, `thicknessPower` 2.0, `thicknessScale` 10.0); `webgl_materials_subsurface_scattering` also uses the Stanford bunny and `bunny_thickness.jpg`, not the Lee Perry-Smith head. — [SubsurfaceScatteringShader.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/shaders/SubsurfaceScatteringShader.js), [webgl_materials_subsurface_scattering.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgl_materials_subsurface_scattering.html)

**MeshPhysicalNodeMaterial: no diffusion either**
- **[S]** Node inputs present: `clearcoatNode`, `clearcoatRoughnessNode`, `clearcoatNormalNode`, `sheenNode`, `sheenRoughnessNode`, `iridescenceNode`, `iridescenceIORNode`, `iridescenceThicknessNode`, `transmissionNode`, `thicknessNode`, `attenuationDistanceNode`, `attenuationColorNode`, `dispersionNode`, `anisotropyNode`. — [MeshPhysicalNodeMaterial.js L57-L291](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/MeshPhysicalNodeMaterial.js#L57-L291)
- **[S]** "Transmission + thickness" is refraction of the already-rendered framebuffer: `getIBLVolumeRefraction()` bends a ray by `thickness` and `ior`, samples `viewportMipTexture`, and multiplies by a Beer-Lambert `volumeAttenuation( distance, attenuationColor, attenuationDistance )`. It moves what is seen *behind* the surface; it does not spread diffuse light *across* the surface. — [PhysicalLightingModel.js L29-L146](https://github.com/mrdoob/three.js/blob/r187/src/nodes/functions/PhysicalLightingModel.js#L29-L146)
- **[S]** A case-insensitive search of `src/` and `examples/jsm/` in 0.187.0 for `subsurface`, `burley`, `diffusion profile`, `separable` finds only `MeshSSSNodeMaterial.js`, `SubsurfaceScatteringShader.js` and unrelated hits (a "Burley clearcoat" comment, separable blurs in OutlinePass and UnrealBloomPass). **SSSNode is screen-space shadows**
- **[S]** `examples/jsm/tsl/display/SSSNode.js`: "Post processing node for applying Screen-Space Shadows (SSS) to a scene. Screen-Space Shadows (also known as Contact Shadows) should ideally be used to complement traditional shadow maps." Signature `sss( depthNode, camera, mainLight )`; it ray-marches the depth buffer toward one directional light. Parameters: `maxDistance` 0.1 (world units; "ideally the maximum shadow length should not exceed 1 meter"), `thickness` 0.01, `shadowIntensity` 1.0, `quality` 0.5, `resolutionScale` 1, `useTemporalFiltering` false (needs `TRAANode`). Output is a one-channel 8-bit target (`RedFormat`, `UnsignedByteType`). Stated limits: one directional light only; only on-screen occluders; hard edges unless blurred (`boxBlur( sssPass.r, { size: 2, separation: 1 } )`). References: Panos Karabelas and Bend Studio's screen-space shadows. — [SSSNode.js L11-L45, L61-L131, L230](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/tsl/display/SSSNode.js#L11-L45)
- **[S]** `mainLight` must be a three.js `DirectionalLight`: the ray direction is `lightPosition( mainLight ) - lightTargetPosition( mainLight )` transformed to view space. — [SSSNode.js L370](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/tsl/display/SSSNode.js#L370)

**How a compute-written position buffer is fed to a mesh (three patterns in the r187 examples)**
- **[S]** Pattern A, geometry attribute: create `new THREE.StorageBufferAttribute( count, 3 )`, `geometry.setAttribute( 'storagePosition', it )`, write it from a compute node through `storage( it, 'vec3', count ).element( instanceIndex )`, then `material.geometryNode = computeUpdate` (runs the compute each frame) and `material.positionNode = attribute( 'storagePosition' )`. Used on the Lee Perry-Smith head (`models/gltf/LeePerrySmith/LeePerrySmith.glb`) in `webgpu_compute_geometry`. — [webgpu_compute_geometry.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_compute_geometry.html)
- **[S]** Pattern B, storage read in the vertex shader: `const vertices = attributeArray( instanceCount * vertexCount * 2, 'vec4' )` written by a compute pass (position and normal interleaved), then `material.positionNode = vertices.element( instanceIndex * vertexCount + vertexIndex ... ).xyz` and `material.normalNode = transformNormalToView( ... ).toVarying()` on a plain `Mesh` with `mesh.count = instanceCount` and `frustumCulled = false`. Used in `webgpu_skinning_instancing_individual`. — [webgpu_skinning_instancing_individual.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_skinning_instancing_individual.html)
- **[S]** Pattern C, built-in helper: `computeSkinning( skinnedMesh, toPosition = null )` returns the skinned position node for use inside a compute `Fn`; `webgpu_skinning_points` does `materialPoints.positionNode = Fn( () => { updateSkinningPoints(); return pointPositionArray.toAttribute(); } )().compute( countOfPoints ).onInit( ... )`. Support for `compute()` integrated into a material node was merged for r175 (#30768). — [Skinning.js L308-L378](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Skinning.js#L308-L378), [webgpu_skinning_points.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_skinning_points.html), [PR #30768](https://github.com/mrdoob/three.js/pull/30768)

### Inferences
- Because the project lights through its own function and writes `fragmentNode` by hand, `MeshSSSNodeMaterial` gives it nothing: the translucency term lives in `SSSLightingModel.direct()`, which only runs inside three.js's own light loop. The four-line formula can simply be copied into the project's sun term as the cheap back-light ("thin ear") component, with a baked thickness map as `thicknessColorNode`'s role.
- "Real" subsurface scattering for this project has to be written: either a screen-space diffusion pass over a separate diffuse-light target (section 5), or a pre-integrated curvature LUT in the forward shader (no extra pass; needs the baked curvature map the team already plans).
- `SSSNode` (contact shadows) is usable in principle for skin pores-to-nostril scale self-shadowing, but it reads a `DirectionalLight`; a project with its own sun can pass a dummy `DirectionalLight` kept in sync with its sun direction, or copy the ~150-line ray-march into its own pass.
- The compute patterns B and C are the r187-native route to "skin once, draw many times" (beauty, shadow atlas, depth pre-pass, velocity) for a 180 000-triangle body; pattern A/B need WebGPU proper (see section 2 on the WebGL fallback).

## 2. Skinning in three.js WebGPU: how it works, limits, morphs, crowds

### Takeaway
Built-in skinning is linear blend skinning with exactly four influences per vertex, bone matrices in a uniform buffer up to the device's uniform-binding limit (1 024 bones at the WebGPU default) and in an RGBA32F texture above it, with previous-frame bones kept only when a `velocity` MRT output is active. Dual quaternions and correctives are not in core (the DQS pull request was closed in May 2026), but `positionNode` on a plain `Mesh`, or a compute pass, lets the project keep its own skinning; morph targets live in a float texture array, cost one texel fetch per active target per vertex, and do not produce motion vectors.

### Cited Findings

**The `skinning()` node**
- **[S]** `src/nodes/accessors/Skinning.js`, TSL function `skinning( skinnedMesh )` ("the standard skeletal animation vertex shader setup. Transforms positionLocal, normalLocal, and tangentLocal in-place"). Attributes `skinIndex` as `uvec4` and `skinWeight` as `vec4`: four influences, fixed. Position: `bindMatrixInverse * Σ( boneMat_i * w_i * ( bindMatrix * position ) )`. Normal and tangent: `mat3( bindMatrixInverse * Σ( w_i * boneMat_i ) * bindMatrix ) * n` (the blended matrix itself, not its inverse transpose). — [Skinning.js L102-L161, L234-L297](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Skinning.js#L102-L161)
- **[S]** Bone storage is chosen per skeleton: if `bones.length * 16 * 4` bytes `<= builder.getUniformBufferLimit()` the matrices are a uniform buffer (`referenceBuffer( 'skeleton.boneMatrices', 'mat4', bones.length )`); otherwise `skeleton.computeBoneTexture()` creates a square `DataTexture` (`RGBAFormat`, `FloatType`, four texels per matrix, side rounded up to a multiple of 4) and each matrix is read with four `boneTexture.load( ivec2 )` calls. — [Skinning.js L27-L89](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Skinning.js#L27-L89), [Skeleton.js computeBoneTexture](https://github.com/mrdoob/three.js/blob/r187/src/objects/Skeleton.js)
- **[S]** On WebGPU `getUniformBufferLimit()` returns `device.limits.maxUniformBufferBindingSize`; on the WebGL 2 fallback it returns the context's max uniform block size. — [WebGPUCapabilities.js L40-L42](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/utils/WebGPUCapabilities.js#L40-L42), [WebGLCapabilities.js L75](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgl-fallback/utils/WebGLCapabilities.js#L75)
- **[S]** The WebGPU default for `maxUniformBufferBindingSize` is 65 536 bytes (16 384 in compatibility mode), and a device only gets better-than-default limits if they are requested; three.js forwards `requiredLimits` from the `WebGPURenderer` constructor and defaults it to `{}`. — [WebGPU spec, limits table](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs), [WebGPUBackend.js L97, L245-L250](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/WebGPUBackend.js#L97)
- **[S]** Order of vertex transformations in `NodeMaterial.setupPosition()`: morph targets (`morphReference`) → `skinning` (if `object.isSkinnedMesh`) → `displacementMap` → `batch` (BatchedMesh) → `instancedMesh` → finally `positionLocal.assign( this.positionNode )` if a `positionNode` is set. — [NodeMaterial.js L766-L810](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/NodeMaterial.js#L766-L810)

**Previous-frame positions and motion vectors**
- **[S]** Previous data is generated only when the active MRT has an output named `velocity`: `needsPreviousData() { const mrt = this.renderer.getMRT(); return ( mrt !== null && mrt.has( 'velocity' ) ); }`. — [NodeBuilder.js L3908](https://github.com/mrdoob/three.js/blob/r187/src/nodes/core/NodeBuilder.js#L3908)
- **[S]** When needed, `skeleton.previousBoneMatrices` (a `Float32Array` copy) and, on the texture path, `skeleton.previousBoneTexture` are created; once per skeleton per frame (`_skeletonsUpdated` WeakMap keyed by `frameId`) the current matrices are copied to the previous ones before `skeleton.update()`; the vertex shader skins `positionPrevious` with the previous bones. — [Skinning.js L168-L224, L243-L278](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Skinning.js#L168-L278)
- **[S]** `VelocityNode` (`velocity` in TSL) computes `ndc( currentProjection * modelView * positionLocal ) - ndc( previousProjection * previousView * previousModelWorld * positionPrevious )`, tracking previous camera and object matrices itself. — [VelocityNode.js L171-L185](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/VelocityNode.js#L171-L185)
- **[S]** `positionPrevious` is by default just the geometry position as a varying (`positionGeometry.toVarying( 'positionPrevious' )`); only `Skinning.js`, `Batch.js`, `Instance.js` and `Line2NodeMaterial.js` assign it. `Morph.js` does not import or assign it. — [Position.js L54](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Position.js#L54), [Morph.js imports L2-L16](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Morph.js#L2-L16)
- **[S]** A bug where skinned meshes sharing a material computed `positionPrevious` from another skeleton's pose ("static skinned meshes reported false motion, which hurt TAA, motion blur, and temporal upscaling", issue #34974) was addressed in r187 by "Skeleton: take ownership of previous data" (#34976), after PR #34975 was closed for leaking cached textures. — [PR #34975](https://github.com/mrdoob/three.js/pull/34975), [r187 release notes](https://github.com/mrdoob/three.js/releases/tag/r187)

**Dual quaternion and custom skinning**
- **[S]** Core has no dual quaternion skinning. ### Inferences
- Bone count: with default limits the uniform-buffer path holds `65536 / 64 = 1024` bones; larger skeletons silently switch to the float bone texture (16 `textureLoad` per vertex for four influences, 32 with velocity). A human body rig with correctives and helper joints stays far below 1 024, so built-in skinning would use the uniform buffer; the project's own float-texture skinning is the costlier of the two access paths per vertex.
- Influences: more than four per vertex, dual quaternions, or pose-space correctives all require custom code. Three places to put it, in rising order of effort and payoff: (1) `positionNode` on a plain `Mesh` (what the project does today); (2) a compute pass writing position and normal to a storage buffer read by `positionNode` (pattern B), which skins once per frame for every pass; (3) the same compute pass on a low-resolution cage followed by a subdivision-stencil pass (section 4).
- Motion vectors: a custom `positionNode` gets no previous position for free. When the game's own temporal upscaler needs per-vertex velocity for the body it must evaluate the skinning twice (previous bone frames) and either assign `positionPrevious` inside its vertex function, as `Skinning.js` does, or output its own velocity. With compute skinning the cheap way is to keep last frame's skinned buffer (ping-pong two storage buffers) and read both in the vertex shader.
- Morph targets as correctives are memory-heavy in the built-in form: bytes per target = vertices × (1, 2 or 3 texels) × 16. For a 90 000-vertex body with position and normal deltas that is about 2.9 MB per target, about 290 MB for 100 correctives, all in unfilterable RGBA32F. Sparse correctives (indices + deltas in a storage buffer, applied in the compute pass) avoid this. At most 256 targets fit in the array texture at default limits.
- Morph-driven motion (facial animation, correctives) produces zero velocity with the built-in `velocity` node, which will ghost under TRAA/TAAU unless handled by the custom pipeline.

### Gaps
- No published numbers for instanced skinned crowds in three.js WebGPU (instances × triangles × fps on a named device) were found; the two official examples use 30 instances and state no performance.
- Whether r187's `skinning()` plus a non-null `positionNode` on a real `SkinnedMesh` composes as expected was not tested here; the r185 migration note about `positionLocal` inside `positionNode` is ambiguous in wording and should be tested before relying on it.

## 3. Generating textures at run time in the browser from code

### Takeaway
r187 can bake a procedural TSL material to textures entirely on the GPU: `rtt()` / `convertToTexture()` for screen-aligned bakes, a UV-space rasterization (the exact trick `LightMapper` uses: `vertexNode = uv → clip space`) for per-mesh maps, or a compute shader writing a `StorageTexture`; r187 even ships a CPU UV unwrapper (`unwrapUVs`). What it does not ship is a run-time texture compressor, so run-time-generated maps stay uncompressed (rgba8, rg8, r8 or half float) unless the project adds an encoder, and that sets the phone memory budget.

### Cited Findings

**Render-to-texture with TSL**
- **[S]** `rtt( node, width = null, height = null, options )` / `convertToTexture( node, ... )` (`src/nodes/utils/RTTNode.js`): "takes another node and uses it with a `QuadMesh` to render into a texture"; options `type` (default `HalfFloatType`), `autoUpdate` (default true), `resolutionScale`. `webgpu_procedural_texture` shows `convertToTexture( procedural, 512, 512 )` and the bake-once switches `proceduralToTexture.autoUpdate = false; // update just once` and `proceduralToTexture.textureNeedsUpdate = true; // manually update`. — [RTTNode.js L18-L49, L336-L365](https://github.com/mrdoob/three.js/blob/r187/src/nodes/utils/RTTNode.js#L336-L365), [webgpu_procedural_texture.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_procedural_texture.html)
- **[S]** Manual full-screen pass: `const quad = new QuadMesh( material ); material.fragmentNode = Fn(...)(); renderer.setRenderTarget( rt ); quad.render( renderer );` with `RendererUtils.resetRendererState / restoreRendererState` around it; this is how every addon effect node and `LightMapper`'s resolve step work. — [LightMapper.js L100-L140 and update()](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/lighting/LightMapper.js)

**Baking into UV space (the r187 reference implementation)**
- **[S]** `LightMapper` (r187, WebGPURenderer only) rasterizes the meshes in UV space: `material.vertexNode = vec4( uv( 1 ).flipY().mul( 2 ).sub( 1 ).add( this._jitter ), 0, 1 )`, `side = DoubleSide`, depth test and write off, additive blending (`CustomBlending`, `OneFactor`/`OneFactor`) with the sample count accumulating in alpha, a Halton sub-texel jitter per sample, accumulation in a `HalfFloatType` nearest-filtered target ("bake at most 256 samples, since samples accumulate in half float precision"), then a resolve pass that divides by the count and dilates: empty texels take the average of covered neighbours in a 5×5 window ("the resolve fills two texels around covered surfaces"; "atlas charts need at least three texels of padding"). — [LightMapper.js L1-L140, _createBakeMaterial](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/lighting/LightMapper.js)
- **[S]** `unwrapUVs( root, options )` (`examples/jsm/utils/unwrapUVs.js`, r187, PR #34944): "Generates a unique UV atlas for the meshes in a hierarchy, measured in world space." Options: `attribute` (default `uv1`), `mode` `'lightmap'` or `'normal'` ("Normal tries LSCM"), `resolution` (default 1024), `padding` (default 4), `texelsPerUnit`, `respectUVSeams`, `useInputUVs`. ### Inferences
- A one-time UV-space bake of the existing procedural skin shader is directly buildable in r187: give the new subdivided mesh UVs (authored by the anatomy code, or `unwrapUVs( mesh, { mode: 'normal', attribute: 'uv' } )`), render it with `vertexNode = vec4( uv().flipY().mul( 2 ).sub( 1 ), 0, 1 )` and a `fragmentNode` that evaluates the 3D-noise functions at `positionLocal` (rest pose), into an MRT target (albedo, object- or tangent-space normal, roughness/thickness/curvature packed), then dilate like `LightMapper`'s resolve and let three.js generate mipmaps. Jitter-and-accumulate gives antialiasing of the bake for free.
- Uncompressed memory with a full mip chain (×4/3): rgba8 2K = 22.4 MB, rgba8 4K = 89.5 MB; rg8 4K = 44.7 MB; r8 4K = 22.4 MB; rgba16float 4K = 179 MB. At 8 bits per pixel (BC7, ASTC 4×4) a 4K map is 22.4 MB and a 2K map 5.6 MB; ASTC 6×6 (3.56 bpp) makes 4K about 9.9 MB. Five uncompressed 4K rgba8 maps are about 447 MB, far outside the phone budgets above; five 2K maps packed into three textures (albedo rgba8, normal rg8 via `NormalRGPacking`, roughness/thickness/curvature in one rgba8) are about 56 MB uncompressed and about 14 MB if compressed at 8 bpp.
- Since three.js has no run-time encoder, the realistic choices for generated maps are: keep them uncompressed at 2K on desktop and 1K on phones; or run a compute-shader or WASM block encoder once and cache the compressed bytes in IndexedDB next to the mesh (the project already caches there). ASTC covers Apple GPUs and most Android; BC covers desktop including (per WebKit's check) Macs whose device reports BC support; a desktop-BC7 / mobile-ASTC split, or ETC2/EAC as the single mobile target, covers the field.
- Bake targets should be 8-bit or half float, not 32-bit float: on devices without `float32-filterable` (about 44% of sampled iOS browsers per the extract above) a filtered `FloatType` lookup becomes a multi-load shader emulation.
- `StorageTexture` baking by compute is WebGPU-only; if the WebGL 2 fallback must also generate the maps, use the render-target route (`QuadMesh` or UV-space rasterization), which works on both backends.

### Gaps
- No published byte limit for WebGPU texture memory per page on iOS or Android; only crash reports. The numbers above for "what fits" are arithmetic plus third-party avatar budgets, not a platform guarantee.
- Not verified here: whether `StorageTexture` mip generation after a compute write behaves well in r187 (the official example leaves the mipmap filter commented out), and which storage texture formats beyond the default rgba8 are usable on each browser.
- No run-time GPU texture compressor for three.js WebGPU was identified in this session (search budget ran out before a dedicated search).

## 4. Subdivision in the browser

### Takeaway
three.js core has no subdivision-surface modifier; its one official example pulls in the external `three-subdivide` (Loop, triangles only, unmaintained since August 2023, loses indexing and mishandles 4-component skin attributes), and the only Catmull-Clark option found is a small 2026 WebAssembly port of Pixar OpenSubdiv with self-reported timings of about 25 ms for 126 000 output triangles. WebGPU has no tessellation stage, so the practical designs are "subdivide once in a worker and cache" or "skin a coarse cage, then apply precomputed subdivision stencils in a compute pass".

- **[S]** r186 re-implemented `SimplifyModifier` on `meshoptimizer` (and made `modify()` async), which is the in-box tool for generating lower levels of detail from a dense mesh. — [Migration Guide 185 → 186](https://github.com/mrdoob/three.js/wiki/Migration-Guide)
- **[S]** The WebGPU pipeline has vertex, fragment and compute stages only; the limits table and pipeline descriptors define no tessellation or geometry stage. — [WebGPU spec](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)
- **[X]** A search for a WebGPU compute-shader Catmull-Clark demo found none (only general compute demos and an icosphere subdivider). — [search result list, e.g. s-macke/WebGPU-Lab](https://github.com/s-macke/webgpu-lab)

### Inferences
- `three-subdivide` should be avoided for the Body: it is Loop-only (the team wants a clean quad-style cage), allocates heavily (string hashes, non-indexed expansion), has not been released since 2023, and its `Vector3` path would drop the fourth component of `skinIndex` / `skinWeight` and "smooth" bone indices as if they were positions.
- Because the project already builds its anatomy mesh in web workers and caches it in IndexedDB, the lowest-risk design is its own Catmull-Clark (or an OpenSubdiv WASM build) in the worker, run once, emitting: the dense mesh, limit normals, UVs, and a stencil table (for each dense vertex, a short list of cage-vertex indices and weights). The self-reported OpenSubdiv numbers suggest the refinement itself is tens of milliseconds for the 100 000 to 500 000 triangle range.
- With the stencil table in a storage buffer, run-time evaluation is a compute pass: skin the cage (roughly 11 000 vertices for a 180 000-triangle level-2 result) with any number of influences, dual quaternions and correctives, then `dense[i] = Σ w_ij · cage[j]`. Skin weights then never need to be subdivided, and one level less can be evaluated for phone levels of detail from the same cage. This is how OpenSubdiv's own GPU evaluators work **[R]**.
- Limit-surface normals for a deforming mesh: either evaluate two more stencil sets (tangent stencils; OpenSubdiv provides derivative stencils **[R]**) or recompute normals in the compute pass from the dense positions via a precomputed one-ring adjacency buffer; a baked tangent-space normal map then sits on top.

### Gaps
- No independent benchmark of either library on an M1 or a phone was found; the OpenSubdiv WASM figures are the author's own and name no device.
- No maintained, widely used Catmull-Clark library for three.js was found; the WASM port is young and little used.
- Compute-shader adaptive tessellation in WebGPU (as opposed to uniform pre-subdivision) has no reference implementation that this session could locate.

## 5. Screen-space effects available to a custom pipeline in r187, and how a custom extra pass is done with MRT

### Takeaway
r187 ships GTAO, a cheaper self-denoised SSAO, screen-space (contact) shadows, SSGI, SSR, bilateral and depth-aware blurs, TRAA, TAAU and FSR1 as addon nodes, but no screen-space subsurface scattering; a separable or Burley SSS pass has to be written, and the framework for it (an extra MRT attachment holding diffuse light, a full-screen blur reading depth, a composite) is fully there. The one trap for this project: a hand-written `fragmentNode` is not merged with the pass's MRT layout, so the body's fragment node must itself return an `mrt({...})` struct.

### Cited Findings

**Passes and MRT**
- **[S]** `pass( scene, camera, options )` creates a `PassNode` whose render target defaults to `HalfFloatType` (`new RenderTarget( w, h, { type: HalfFloatType, ...options } )`). API: `setMRT( mrtNode )`, `getTextureNode( name = 'output' )`, `getPreviousTextureNode( name )`, `getViewZNode()`, `getLinearDepthNode()`, `setResolutionScale( s )`, `setLayers()`, `overrideMaterial`, `transparent` / `opaque` switches, `options.samples`, and `contextNode` (for example `scenePass.contextNode = builtinAOContext( ao )`). `depthPass()` is the depth-only variant. — [PassNode.js L175-L360, L526-L800, L1135-L1167](https://github.com/mrdoob/three.js/blob/r187/src/nodes/display/PassNode.js#L175-L360)
- **[S]** `mrt( { output, normal: normalView, ... } )` is an `MRTNode extends OutputStructNode`: a dictionary from output name to node; at build time each name is matched to the render target's texture of the same name and outputs "that exist in the MRT but have never been used" are skipped; per-output blend via `setBlendMode( name, blend )` (default: `output` uses the material's blending, all others `NoBlending`) and per-output clear colors. — [MRTNode.js L34-L140 and setup()](https://github.com/mrdoob/three.js/blob/r187/src/nodes/core/MRTNode.js)
- **[S]** In the normal (lit) material path the renderer's MRT is applied automatically and merged with the per-material override: `resultNode = mrt; if ( materialMRT !== null ) resultNode = mrt.merge( materialMRT );` (`material.mrtNode`). — [NodeMaterial.js L556-L583](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/NodeMaterial.js#L556-L583)
- **[S]** In the `fragmentNode` path that merge does not happen: `let fragmentNode = this.fragmentNode; if ( fragmentNode.isOutputStructNode !== true ) fragmentNode = fragmentNode.convert( builder.getOutputType() ); resultNode = this.setupOutput( builder, fragmentNode );`. - **[S]** WebGPU validation for a render pipeline: for each color target, "If colorState.writeMask is not 0: entryPoint must have a shader stage output with location equal to index". three.js sets the write mask to all or none per material (`material.colorWrite`). — [WebGPU spec, validating GPUFragmentState](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs), [WebGPUPipelineUtils.js L124-L187, L938-L940](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/utils/WebGPUPipelineUtils.js#L938-L940)

- **[S]** `DirectRenderPipeline` (in core, `src/renderers/common/DirectRenderPipeline.js`): "applies output processing directly in material shaders. This avoids the intermediate framebuffer and output pass used by Renderer, but changes blending and is not compatible with materials that sample the framebuffer"; with the WebGL backend `antialias` has no effect. `StandardDrawingPipeline` is the new (experimental) hook for custom culling and submission. — [DirectRenderPipeline.js](https://github.com/mrdoob/three.js/blob/r187/src/renderers/common/DirectRenderPipeline.js), [StandardDrawingPipeline.js](https://github.com/mrdoob/three.js/blob/r187/src/renderers/common/StandardDrawingPipeline.js)

**Ambient occlusion**
- **[S]** `GTAONode` (`ao( depthNode, normalNode, camera )`): horizon-based GTAO after Activision's "Practical Real-Time Strategies for Accurate Indirect Occlusion"; defaults `samples` 16, `radius` 0.25, `thickness` 1, `scale` 1, `resolutionScale` 1, `useTemporalFiltering` false; output in a one-channel `RedFormat` target; the recommended wiring is a normal+depth pre-pass and `scenePass.contextNode = builtinAOContext( aoPass.getTextureNode().sample( screenUV ).r )` so that AO attenuates only ambient light. — [GTAONode.js doc and L91-L173](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/tsl/display/GTAONode.js)

**Screen-space subsurface scattering**
- **[S]** None in three.js r187 core or addons (see the source search in section 1). — [examples/jsm/tsl/display at r187](https://github.com/mrdoob/three.js/tree/r187/examples/jsm/tsl/display)

- **[S]** The one TSL "subsurface" community project found is `prizemlenie/subsurface-refraction-shader`: a parallax-plus-blur trick for crystals and water after a Path of Exile talk, not skin diffusion. — [subsurface-refraction-shader README](https://github.com/prizemlenie/subsurface-refraction-shader)
- **[S]** A complete, open reference for the pass exists in another web engine: Babylon.js's `subSurfaceScattering.fragment.fx` (GLSL and WGSL), see section 6. — [Babylon.js subSurfaceScattering.fragment.fx](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/core/src/Shaders/subSurfaceScattering.fragment.fx)

### Inferences
- Recipe for a diffuse-light buffer in r187 with hand-written materials: (1) `scenePass.setMRT( mrt( { output, diffuseLight, velocity, ... } ) )` to declare the attachments; (2) the Body material's `fragmentNode` returns `mrt( { output: specularAndAmbient, diffuseLight: vec4( diffuseIrradianceTimesAlbedoOrNot, sssMask ), velocity: ... } )`; (3) every *other* hand-written material drawn in that pass must also return a struct covering all attachments (writing zero to `diffuseLight`), because a plain vec4 `fragmentNode` produces only location 0 and WebGPU rejects a pipeline whose color target has a non-zero write mask and no shader output; (4) a full-screen node reads `scenePass.getTextureNode( 'diffuseLight' )` and depth, blurs separably or with Burley disk samples, and (5) the composite adds it back to `output` before the game's temporal upscaler.
- Budget the attachments against 32 bytes per sample: rgba16float color (8) + rgba16float diffuse light (8) + rg16float velocity (4) + rgba8 normal/mask (4) = 24 bytes fits the default; four rgba16float targets are exactly 32. Set types explicitly (`scenePass.getTexture( name ).type = ...`) because every MRT attachment defaults to half float RGBA.
- Tile-based GPUs pay for every extra full-screen attachment in tile memory and for every extra pass in a load/store; the cheapest SSS variant on an M1 at 1440p is likely a single-pass Burley disk blur at half resolution on a body-only mask, resolved by the temporal upscaler, rather than two full-resolution separable passes. This is a design judgment, not a measurement.
- Since the project draws at about 1440p and upscales with its own pass, `TAAUNode` is the built-in equivalent and a useful reference or fallback; both it and `TRAANode` require MSAA off and a `velocity` output, which the custom-skinned Body must supply itself (section 2).
- GTAO defaults are tuned for metre-scale scenes (`radius` 0.25); for skin-scale occlusion on a body, a smaller radius plus `SSSNode`-style contact shadows along the sun is the combination the addons suggest.

### Gaps
- No published millisecond costs for `GTAONode`, `SSAONode`, `SSSNode`, `TRAANode` or `TAAUNode` on an M1 or a phone were found (PR #33368 contains none).
- No community implementation of separable (Jimenez) or Burley screen-space SSS for three.js WebGPU/TSL could be confirmed; the forum could not be opened to look further.
- Not tested: whether rendering a vec4-only `fragmentNode` material into an MRT pass in r187 raises the validation error the spec implies or is masked by three.js in some way; the source reading says it emits a single output.

## 6. Real examples of realistic humans in the browser and how they were made

### Takeaway
No open, locally rendered WebGPU "digital human" with real subsurface scattering was found for 2025 to 2026; the realistic humans shown in browsers are either cloud-streamed (MetaHuman, Unity's Heretic and Time Ghost) or use much simpler shading. Among web engines only Babylon.js ships true screen-space subsurface scattering (Burley diffusion profiles in a pre-pass post-process, with a WGSL version in its source); three.js and PlayCanvas ship none, and Sketchfab's viewer has had a profile-based SSS plus thickness translucency since 2017.

### Cited Findings
- **[S]** three.js r187: `webgpu_materials_sss` and `webgl_materials_subsurface_scattering` (bunny, GDC 2011 translucency); `webgpu_morphtargets_face` (`facecap.glb`, blend-shape face, standard PBR); `webgpu_animation_retargeting_readyplayer` (a Ready Player Me avatar used for retargeting); `webgpu_compute_geometry` (the Lee Perry-Smith head deformed by compute, shaded with `MeshNormalNodeMaterial`). None shades skin with diffusion; none states frame rates. — [examples/files.json at r187](https://github.com/mrdoob/three.js/blob/r187/examples/files.json)
- **[S]** Babylon.js documentation (PBR "Sub Surface" section): three separate effects, refraction, translucency and scattering. Scattering is enabled with `scene.enableSubSurfaceForPrePass().metersPerUnit = 0.01;` and `pbr.subSurface.isScatteringEnabled = true;`; "For this effect to be physically accurate, you have to indicate the ratio between scene units and the real world distance in meters"; diffusion profiles are colours, e.g. skin `pbr.subSurface.scatteringDiffusionProfile = new BABYLON.Color3( 0.75, 0.25, 0.2 );`, "You can have up to 5 different colors registered as diffusion profiles"; warning: "This effect uses a lot of WebGL 2 structures under the hood, so it is only compatible with WebGL 2. Furthermore... the use of subsurface scattering triggers a post-process, and it adds a lot of additional work for the GPU... smaller GPUs won't necessarily have the resources to run this effect." Thickness: `minimumThickness + thicknessTexture.r * maximumThickness`, with translucency intensity packed in the thickness map's g channel. — [Babylon.js docs source, masterPBR.md](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/materials/using/masterPBR.md)
- **[S]** Babylon.js implementation (`subSurfaceScattering.fragment.fx`): a post-process with inputs `textureSampler`, `irradianceSampler`, `depthSampler`, `albedoSampler`, uniforms `metersPerUnit`, `viewportSize`; it evaluates and importance-samples the normalized Burley diffusion profile (`EvalBurleyDiffusionProfile`, `SampleBurleyDiffusionProfile`, with a comment linking zero-radiance.github.io "sampling-diffusion"), uses a Fibonacci disk, `const int _SssSampleBudget = 40`, `SSS_PIXELS_PER_SAMPLE = 4.` (sample count scales with the projected filter area), and `#define SSS_BILATERAL_FILTER true`. A WGSL port of the same file exists under `ShadersWGSL/`. — [GLSL shader](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/core/src/Shaders/subSurfaceScattering.fragment.fx), [WGSL shader](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/core/src/ShadersWGSL/subSurfaceScattering.fragment.fx)
- **[X]** Babylon.js forum extracts: true SSS requires `PBRMaterial` and the pre-pass renderer; enabling it turns off the default post-process MSAA (thread "Bad antialiasing with subsurface scattering"); a 2026 thread reports SSS going black with an intermediate `RenderTargetTexture` and the frame graph; another reports thickness sampling problems on scaled models. — [forum: bad antialiasing with SSS](https://forum.babylonjs.com/t/bad-antialiasing-with-subsurface-scattering/24273), [forum: SSS black with frame graph](https://forum.babylonjs.com/t/pbr-subsurface-scattering-becomes-black-with-an-intermediate-rendertargettexture-and-frame-graph/63870)
- **[X]** Sketchfab: real-time SSS and translucency announced September 2017; per its help centre the SSS texture is a grayscale mask, a "subsurface profile" is two colours, up to 3 profiles per model, translucency is a separate thickness channel that needs shadows enabled, and materials using SSS are limited to dithered or alpha-mask transparency. - **[X]** PlayCanvas: forum answers state that `StandardMaterial` has no native SSS and that it needs a custom shader or overridden shader chunks. — [PlayCanvas forum: mimic SSS](https://forum.playcanvas.com/t/how-can-i-mimic-subsurface-scattering-sss-in-playcanvas-materials/40262), [PlayCanvas forum: subsurface scattering](https://forum.playcanvas.com/t/subsurface-scattering/11915)
- **[X]** Ready Player Me: acquired by Netflix (announced December 2025); public avatar creator, APIs and SDKs shut down on 31 January 2026 according to several vendor write-ups (one competitor's post gives a different timeline). — [Genies: Ready Player Me shutdown](https://genies.com/blog/ready-player-me-shutdown), [PocketGamer.biz: Netflix acquires Ready Player Me](https://www.pocketgamer.biz/netflix-acquires-avatar-creation-platform-ready-player-me)
- **[X]** MetaHuman in a browser is delivered by Pixel Streaming: Unreal renders on a server and sends encoded video over WebRTC. - **[X]** Unity: WebGPU became a supported web backend in Unity 6.1 (April 2025, experimental) and is reported as "no longer experimental" from Unity 6000.6 (September 2026, secondary source); Unity's own WebGPU showcase scenes were Fantasy Kingdom and a spaceship interior. ### Inferences
- The best openly readable template for "industry-practice SSS in a browser" is Babylon.js's pass: a diffuse-irradiance target written during the main pass, plus albedo and depth, then a Burley-profile disk blur with up to 40 samples per pixel and bilateral depth weighting, composited afterwards. Porting its WGSL to a TSL `Fn` (or wrapping it with `wgslFn`) is a bounded job; its documentation's performance warning and the MSAA incompatibility apply equally to a three.js port.
- Sketchfab's and Babylon's parameterisations agree on what the art side needs: a scatter mask, a small number of colour profiles (3 and 5), a thickness map for translucency, and world-scale units. The team's planned maps (albedo, normal, roughness, thickness, curvature) match that, with curvature only needed for a pre-integrated fallback on phones.
- That every high-end "digital human in a browser" found is streamed video suggests there is no public evidence yet that MetaHuman-class skin, hair and eyes run locally at 60 fps in a browser on M1-class hardware; the project would be setting the reference rather than following one.

### Gaps
- No frame rates were reported by any source for skin or SSS demos in a browser (three.js examples, Babylon playgrounds, Sketchfab).
- Needle Engine, Verge3D and Unity-WebGPU digital-human samples were not researched (search budget exhausted); Sketchfab's actual algorithm (texture-space or screen-space) was not confirmed.
- Whether Babylon.js's SSS pre-pass actually runs under its WebGPU engine and frame graph today is unclear: the WGSL shader exists in source, the documentation still says WebGL 2 only, and a 2026 forum thread reports frame-graph problems.
- Any 2025 to 2026 open-source WebGPU digital-human demo: none found.

## 7. Platform limits that matter

### Takeaway
WebGPU is on by default in Safari 26 (macOS, iOS, iPadOS, visionOS), Chrome on Mac/Windows/ChromeOS since 113 and Android 12+ since 121, and Firefox on Windows and Apple Silicon Macs; on Apple GPUs WebKit exposes ASTC and ETC2 always, BC and 32-bit float filtering only where Metal reports them, 16 384-pixel textures from the A13 class up, and timestamp queries where a counter set exists. Two things bite three.js users specifically: a device only gets default limits (8 192-pixel textures, 64 KB uniform bindings, 32 bytes of colour attachments per sample) unless `requiredLimits` is passed, and large generated shaders have hit a WGSL "8192 bytes of variables" pipeline-creation failure in Chrome and Safari (fixed for the reported case in r187).

**Vertex-stage data access and tile-based GPUs**
- **[S]** Core WebGPU allows storage buffers and storage textures in the vertex stage (defaults 8 and 4); compatibility mode defaults both to 0. — [WebGPU spec, limits table](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)
- **[X]** Meta's mobile-GPU guidance (Quest-class tile-based GPUs): the binning pass means the vertex shader "will be re-run per-triangle, per-tile"; "vertex processing is relatively more time intensive on mobile than PC"; and reading a texture from main memory is "~1 order of magnitude slower than reading from a texture tile in GPU memory". These are about Adreno-class tilers, not measurements on Apple GPUs. — [Meta: PC rendering techniques to avoid for mobile VR](https://developers.meta.com/horizon/blog/pc-rendering-techniques-to-avoid-when-developing-for-mobile-vr/), [Meta: GPU-impaired algorithms](https://developers.meta.com/vr/documentation/native/android/gpu-impaired-algorithms/)

### Inferences
- For the M1 target in both Chrome and Safari the game can assume: compute, storage buffers and textures in every stage, ASTC and ETC2 (and, on Macs whose Metal device reports it, BC), half-float filtering, MRT with 8 attachments, 16 384-pixel textures if requested. It should not assume `float32-filterable` or `timestamp-query` on iPhones, and should feature-test both with `renderer.hasFeature()` after `await renderer.init()`.
- Pass `requiredLimits` deliberately and defensively (read `adapter.limits` first, or request only what is known to exist), because a required limit the adapter lacks makes device creation fail. Likely candidates for this project: `maxColorAttachmentBytesPerSample` (if the G-buffer exceeds 32 bytes), `maxTextureDimension2D` (shadow atlas above 8 192), `maxStorageBufferBindingSize` (large skinned buffers), `maxTextureArrayLayers` (more than 256 morph layers).
- The "8192 bytes of function-local variables" WGSL limit is a real ceiling for very large hand-written TSL fragment functions with many `toVar()` temporaries, vec4/mat4 locals and unrolled noise octaves: 8 192 bytes is 512 `vec4f` values. Splitting work into separate `Fn`s (each WGSL function has its own budget), avoiding needless `toVar()`, and moving the noise to baked textures all reduce the risk; the specific r180-r186 regression is fixed in r187.
- A float bone-frame data texture read with `textureLoad` in the vertex shader works in core WebGPU on all the targets, but it is the pattern tilers like least (vertex stage possibly run twice, texture reads from system memory). A storage buffer of bone transforms, or compute skinning once per frame into a vertex-readable buffer, is the lower-risk form on Apple and Android tilers. In compatibility-mode devices (old Android on OpenGL ES 3.1) vertex-stage storage is not available by default, so those devices are better served by the project's WebGL 2 path or the data-texture form.
- iOS reliability needs its own soak testing: both recorded iOS-only failures (#35069 during `compileAsync()`, WebKit 302711 with instancing) do not reproduce on macOS Safari.

### Gaps
- The WebKit blog post for Safari 26.0 and the WebKit bug tracker could not be opened, so nothing here ties a feature or limit to a specific Safari release (26.0, 26.1, 26.2, 27.0); the WebKit findings are from the `main` branch on the day of reading.
- Which Apple devices report `supports32BitFloatFiltering` and `supportsBCTextureCompression` was not verified (from memory, Apple Silicon Macs report both and many iPhones report neither, with newer iPhones gaining BC) **[R]**; the Metal family to chip mapping (Apple6 = A13, Apple7 = A14 and M1) is also from memory **[R]**.
- No published measurement of shader compile or pipeline creation time for large TSL shaders in Safari was found; #33821 measures many small materials, not one large one.
- Android per-GPU limits (Mali, Adreno) for `maxTextureDimension2D` and storage in the vertex stage were not found.

## 8. Performance data: skinned high-poly characters, big fragment shaders, levels of detail

### Takeaway
There is almost no published, device-named performance data for a single high-polygon skinned character in three.js WebGPU; the published three.js numbers are about per-object CPU overhead (WebGPURenderer 4× slower than WebGLRenderer with 20 000 separate meshes on an M1 Pro, and up to 16× slower to initialise 10 000 unique materials), which a one-draw 180 000-triangle body does not trigger. The usable hard numbers are budgets from elsewhere: VRChat's avatar ranks (32 000 to 70 000 triangles on PC, 7 500 to 20 000 on mobile, 75 to 400 bones) and the timings of r187's unwrapper and the OpenSubdiv WASM port.

### Cited Findings
- **[S]** three.js #30560 (open, "High priority"): 20 000 non-instanced cube meshes on an M1 Pro Mac ran at about 60 fps in `WebGLRenderer` and about 15 fps in `WebGPURenderer` (r173, February 2025). In January 2026 a maintainer measured `WebGPURenderer` with its WebGL 2 backend at about 12 fps against 60 fps for `WebGLRenderer` in Chrome on macOS, 28 against 60 in Firefox, and 19 against 57 fps on a Pixel 8a. On r186 (September 2026, M4 Max, Chrome) the WebGL 2 fallback's `render()` took 2.88 ms against 2.20 ms (+31%) for 376 to 383 draws, with 789 `bufferSubData` calls against 0. Diagnosis: one uniform buffer per object, bound and updated every frame. No release fixes the core problem. — [issue #30560](https://github.com/mrdoob/three.js/issues/30560)
- **[S]** three.js #33821: first-render cost with many unique node materials on a MacBook Pro M1 Pro, about 2 100 ms (WebGPU) against about 131 ms (WebGL) for 10 000 meshes; per-instance `MeshBasicNodeMaterial` construction about 300 ms, about 2 000 ms with a custom uniform each. — [issue #33821](https://github.com/mrdoob/three.js/issues/33821)
- **[X]** A three.js forum thread title reports "WebGPURenderer ~2× slower CPU and ~5–10× slower first frame than WebGLRenderer on many-mesh scenes (r183), same on both backends". — [forum topic 91904](https://discourse.threejs.org/t/webgpurenderer-2x-slower-cpu-and-5-10x-slower-first-frame-than-webglrenderer-on-many-mesh-scenes-r183-same-on-both-backends/91904)
- **[S]** Rationale recorded for compute skinning in three.js itself: with vertex-shader skinning "skinning is otherwise recalculated for every pass", whereas a compute pass writes skinned positions and normals once and "beauty and shadow passes reuse it"; also "not every animation needs updating each frame". No timings were given. — [PR #33644](https://github.com/mrdoob/three.js/pull/33644)
- **[S]** Cost structure of built-in vertex work, from the source: skinning on the bone-texture path is 4 texel loads per bone matrix × 4 influences = 16 loads per vertex (32 with velocity), 0 loads on the uniform-buffer path; each active morph target adds 1 to 3 loads per vertex and the loop visits every target; `BatchedMesh` adds 5 or more loads per vertex (indirect id + 4 matrix texels, + colour). — [Skinning.js L27-L47](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Skinning.js#L27-L47), [Morph.js L270-L337](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Morph.js#L270-L337), [Batch.js L37-L68](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Batch.js#L37-L68)
- **[S]** A published avatar budget ladder (VRChat, per avatar). PC: triangles 32 000 (Excellent) then 70 000 (Good, Medium, Poor); texture memory 40 / 75 / 110 / 150 MB; skinned meshes 1 / 2 / 8 / 16; material slots 4 / 8 / 16 / 32; bones 75 / 150 / 256 / 400. Mobile: triangles 7 500 / 10 000 / 15 000 / 20 000; texture memory 10 / 18 / 25 / 40 MB; skinned meshes 1 / 1 / 2 / 2; material slots 1 / 1 / 2 / 4; bones 75 / 90 / 150 / 150; above 20 000 triangles a mobile avatar is "Very Poor" and hidden by default. — [VRChat creator docs, avatar performance ranking](https://github.com/vrchat-community/creator-docs/blob/main/Docs/docs/avatars/avatar-performance-ranking-system.md)
- **[S]** Tooling timings usable for build-time budgeting: `unwrapUVs` 117 ms to 649 ms for a 17 684-triangle head, 336 ms to 546 ms for 53 400 triangles (device unstated); OpenSubdiv WASM about 25 ms for 126 000 output triangles and about 120 ms for 503 000 (author's figures, device unstated). — [PR #34944](https://github.com/mrdoob/three.js/pull/34944), [npm registry: @nasedkinpv/opensubdiv-wasm](https://registry.npmjs.org/@nasedkinpv%2fopensubdiv-wasm)
- **[S]** Level-of-detail tools in r187: `SimplifyModifier` (meshoptimizer-based since r186, async), `THREE.LOD`, examples `webgl_lod`, `webgl_batch_lod_bvh`, `webgl_loader_gltf_progressive_lod`, and the experimental meshlet pipelines (`webgpu_meshlets*`, `MeshletDrawingPipeline`, `VisibilityBufferDrawingPipeline`, `MeshletGeometryUtils`). — [examples/files.json at r187](https://github.com/mrdoob/three.js/blob/r187/examples/files.json), [Migration Guide 185 → 186](https://github.com/mrdoob/three.js/wiki/Migration-Guide)
- **[S]** FSR1's own guidance in the three.js source is a statement about where cost sits: "Only use FSR 1 if your application is fragment-shader bound and cannot afford to render at full resolution. FSR 1 adds its own overhead, so simply shaded scenes will render faster at native resolution without it." — [FSR1Node.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/tsl/display/FSR1Node.js)

### Inferences
- The known three.js WebGPU performance problems (per-object uniform buffers, per-material graph building) scale with the number of objects and unique materials, not triangles. One Body drawn as one mesh with one material sits outside them; the same Body split into many meshes or many material variants would walk into them. Keep the Body, its clothes and its levels of detail to a handful of draws and share node graphs.
- Vertex load of the current design, by arithmetic: 180 000 triangles is roughly 90 000 vertices; skinned from a float data texture in the vertex shader for the beauty pass, each shadow-atlas cascade that contains the body, and any depth or velocity pre-pass, that is 90 000 × passes skinning evaluations per frame, each with at least 16 texel loads. Compute skinning turns that into 90 000 evaluations once, after which every pass reads two `vec4`s per vertex.
- Fragment load is the larger risk at 1440p: a body filling a third of a 2560×1440 frame is about 1.2 million shaded pixels before overdraw, each evaluating several octaves of 3D noise today. Replacing the noise with three or four texture samples from baked maps trades arithmetic for bandwidth, which is the standard trade on Apple GPUs and also shortens the WGSL (compile time, the 8 192-byte local-variable ceiling). No published number quantifies it for TSL; it has to be measured with `timestamp-query` in Chrome on the M1.
- A level-of-detail ladder consistent with the one published budget set: full body about 180 000 triangles for hero view on desktop only; 60 000 to 70 000 for normal desktop gameplay (VRChat PC "Good" ceiling); 15 000 to 20 000 for phones (mobile "Medium" to "Poor"); 7 500 or fewer for distant or crowd instances; beyond that, impostors. With a subdivision cage these are simply cage level 2, level 1, level 0 and a simplified cage, all skinned by the same compute pass. Bones for phone levels should stay near 75 to 150.
- For crowds, r187's own route is compute-skinned instances in one draw (`webgpu_skinning_instancing_individual`), with per-instance palettes; baked animation textures and octahedral impostors are the usual next steps but have no three.js core implementation.

### Gaps
- No source gives triangles per frame, vertex-shader cost with texture-based skinning, or milliseconds per pass for a skinned high-poly character in three.js WebGPU on an M1 or any phone. This must be measured in the project (Chrome with `timestamp-query`; Safari via Instruments, since `timestamp-query` availability there depends on the device's counter sets).
- No published comparison of "many noise evaluations" against "texture lookups" in TSL or WGSL on Apple GPUs was found.
- Searches for web crowd impostor libraries, for M1 triangle-throughput benchmarks, and for other platforms' avatar budgets (Meta, Ready Player Me historical LODs) did not run because the shared search budget was exhausted; the `agargaro/octahedral-impostor` repository exists **[S]** ([README](https://github.com/agargaro/octahedral-impostor)) but its README contained no usable detail.
- The VRChat ladder is a budget for many avatars in one VR scene, not a measured limit for a single hero character in a browser; it is cited as the only published tiered budget found, not as a target.
