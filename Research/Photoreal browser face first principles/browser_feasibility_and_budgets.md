## 1. Texture maps: memory cost, KTX2 / Basis Universal, transcoding, WebGPU limits, phones, virtual texturing

### Takeaway
A four-map set (albedo, normal, roughness/specular, displacement) with mip chains costs about 341 MiB at 4K if every map is left as RGBA8, about 85 MiB if all four are held at 8 bits per pixel (UASTC transcoded to ASTC 4×4 or BC7), and about 64 MiB with single- and two-channel block formats for the data maps; 2K is a quarter of each figure and 8K four times. r187's `KTX2Loader` transcodes in up to four web workers with a 527 KB WebAssembly transcoder and always targets 8 bpp for UASTC; no source that could be opened gives transcode times, no vendor publishes a per-tab memory limit for phones, and no virtual-texturing library exists for three.js.

### Cited Findings

**Formats and bits per pixel**
- **[S]** Basis Universal v2.5 README: ETC1S is "a roughly .3-3bpp low to medium quality supercompressed mode"; UASTC LDR 4×4 is "an 8 bits/pixel LDR high quality mode ... a 19 mode subset of the standard ASTC LDR 4x4 (8bpp) texture format"; "Transcoding UASTC LDR to ASTC LDR and BC7 is particularly fast and simple, because UASTC LDR is a common subset of both BC7 and ASTC". New since v2.0: XUASTC LDR ("supercompressed ASTC with Weight Grid DCT", all 14 ASTC block sizes 4×4 to 12×12, "Typical XUASTC LDR 4×4 (8 bpp in memory) transmission/on-disk bitrate ... is 1.15–3.5 bpp (typical ≈2.25 bpp)") and XUBC7 (supercompressed BC7, "lossless bitrate is ~3.5-5.6 bpp, lossy is ~0.8-3.5 bpp"). Transcode targets listed: "ASTC LDR 4x4 L/LA/RGB/RGBA 8bpp", "ASTC LDR 4x4-12x12 (XUASTC/ASTC), 0.89-8bpp", ASTC HDR 6×6 at 3.56 bpp. — [basis_universal README](https://github.com/BinomialLLC/basis_universal/blob/master/README.md)
- **[S]** Khronos KTX developer guide: "Basis Universal always uses blocks of 4 by 4 pixels"; transcoded sizes per 4×4 block are 16 bytes for ASTC 4×4, BC7, BC3, ETC2 RGBA (8 bpp) and 8 bytes for BC1 and ETC1 RGB (4 bpp); "UASTC textures consist of 4x4 blocks, each block takes exactly 16 bytes"; "Transcoding to ASTC is always lossless (e.g. it would match decoding to RGBA8), transcoding to BC7 is almost lossless"; transcoding UASTC to ETC, BC1/BC3 or PVRTC1 "involves decoding the texture to uncompressed pixels and re-encoding them"; ETC1S "is more suited for color textures (albedo, base color, etc) rather than arbitrary non-color data like normal maps"; for red-green (normal) data the preferred ETC1S targets are EAC RG11 then BC5, and for UASTC RG data ASTC or BC7 first, EAC RG11 or BC5 otherwise. — [KTXDeveloperGuide.md](https://github.com/KhronosGroup/3D-Formats-Guidelines/blob/main/KTXDeveloperGuide.md)
- **[S]** Khronos KTX artist guide, the one worked memory example found: a lamp model with JPG and PNG textures is "about 13 MB, but it increases to 96 MB in GPU memory because the textures must be uncompressed"; the same model with KTX (UASTC for packed and normal maps, ETC1S for base colour and emissive) is a 10 MB file and "becomes 21 MB in GPU memory". Its encoder settings for the high-quality version: `--encode uastc --uastc_quality 4 --uastc_rdo_l .5 --zcmp 22` (`.25` for the normal map, with `--assign_oetf linear`) and `--encode etc1s --clevel 4 --qlevel 255`. JPEG/PNG/WebP "do not stay compressed in memory". — [KTXArtistGuide.md](https://github.com/KhronosGroup/3D-Formats-Guidelines/blob/main/KTXArtistGuide.md)
- **[S]** Babylon.js documentation makes the same two points: ETC1S "does not work as well on data that are not true color data (like normal maps, metallic/roughness maps, etc.)", and Zstandard on UASTC "can lead to smaller .ktx2 file sizes but not smaller GPU compressed textures! The data compressed with Zstandard will be expanded on the CPU side and then transcoded". — [Babylon.js docs, ktx2Compression.md](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/materials/using/ktx2Compression.md)

**How r187 transcodes (where it runs, what it picks)**
- **[S]** `KTX2Loader` builds a worker from `basis_transcoder.js` + `basis_transcoder.wasm` and runs transcoding in a `WorkerPool` whose default size is 4 (`constructor( pool = 4 )`; `setWorkerLimit()` changes it); Zstandard-supercompressed levels are inflated with `zstddec`. In the npm package the transcoder is 527 333 bytes of WebAssembly plus a 57 529-byte JS wrapper. Mip levels come from the file: the texture gets `LinearMipmapLinearFilter` only if the file holds more than one level, otherwise `LinearFilter`. — [KTX2Loader.js L103-L107, L162-L207, L297-L350, L460-L468](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/loaders/KTX2Loader.js), [WorkerPool.js L13](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/utils/WorkerPool.js), [libs/basis](https://github.com/mrdoob/three.js/tree/r187/examples/jsm/libs/basis)
- **[S]** Target ranking in r187 (lower number wins; "high quality > low quality > uncompressed"): UASTC goes to ASTC 4×4 (1), then BC7 (2), ETC2 (3), ETC1 (4), BC3 (5), PVRTC (6), uncompressed RGBA32 (100). ETC1S goes to ETC1/ETC2 (1), ETC1 (2), BC7 (3), BC1/BC3 (4), PVRTC (5), RGBA32 (100), and never to ASTC (`priorityETC1S: Infinity`). So on a desktop GPU with only BC formats an ETC1S file becomes BC7 at 8 bpp, not BC1 at 4 bpp. — [KTX2Loader.js L796-L900](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/loaders/KTX2Loader.js#L796-L900)
- **[S]** The loader also accepts KTX2 files that already hold native GPU formats: its format tables include `VK_FORMAT_ASTC_4x4_*`, `VK_FORMAT_ASTC_6x6_*`, `BC1`, `BC3`, `BC4`, `BC5`, `BC7`, `ETC2_R8G8B8(A8)`, `EAC_R11`, `EAC_R11G11`. On Linux desktop it disables ASTC and ETC targets because "Mesa drivers for AMD and Intel GPUs expose ETC1, ETC2 and ASTC even though the hardware doesn't support these", which would cause "expensive software decompression on the main thread inside the driver". — [KTX2Loader.js L57-L81, L266-L282, L1014-L1018](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/loaders/KTX2Loader.js#L57-L81)
- **[S]** An open pull request, "KTX2Loader: Improve target format selection and examples" (#32966, opened 5 February 2026), shows the ranking is still being revised; "KTX2Loader: Fix ETC1S/UASTC prioritization" (#31871) merged in September 2025. — [PR #32966](https://github.com/mrdoob/three.js/pull/32966), [PR #31871](https://github.com/mrdoob/three.js/pull/31871)

**Compressing at run time instead of shipping compressed files**
- **[S]** spark.js (`@ludicon/spark.js`, Ignacio Castaño) is a "real-time texture compression library for the Web" that takes ordinary images (or a `GPUTexture`, `ImageBitmap`, canvas, `VideoFrame`) and encodes them on the GPU at load time "to native GPU formats like BC7, ASTC, and ETC2"; "only 4x4 LDR formats are supported"; `normal: true` favours BC5 and EAC RG; it generates mipmaps (`mips`, filter `"box"` or `"magic"`), can fill one mip chain over several calls (`outputTexture` + `outputMipLevel`, "a small preview first and the full image later"), and has WebGPU (`Spark`) and WebGL 2 (`SparkGL`) back ends. three.js integration: wrap the result in `THREE.ExternalTexture`, or `registerSparkLoader( gltfLoader, spark )`. Licence: "free for non-commercial use, or until your product reaches $100,000 in lifetime revenue"; the JS is MIT, the shaders are under a EULA. Neither the README nor `API.md` states encode times. — [spark.js README](https://github.com/ludicon/spark.js/blob/main/README.md), [spark.js API.md](https://github.com/ludicon/spark.js/blob/main/API.md)

**WebGPU limits that bound a texture set**
- **[S]** Default limits, re-read in the spec source this session (second number is compatibility mode): `maxTextureDimension2D` 8192 / 4096; `maxTextureArrayLayers` 256; `maxBindGroups` 4; `maxBindingsPerBindGroup` 1000; `maxSampledTexturesPerShaderStage` 16; `maxSamplersPerShaderStage` 16; `maxVertexAttributes` 16; `maxBufferSize` 256 MiB. — [WebGPU spec source, limits table](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)
- **[P]** three.js r187 passes `requiredLimits` through from the `WebGPURenderer` constructor and defaults it to `{}`, so a device gets exactly the defaults above unless the application asks for more; WebKit advertises 16 384-pixel 2D textures, 2 048 array layers, 44 sampled textures and 22 samplers per stage and 11 bind groups from the Apple6 GPU family up, and only the defaults on Apple4 and Apple5. — [WebGPUBackend.js L70-L97](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/WebGPUBackend.js#L70-L97), [WebKit HardwareCapabilities.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/HardwareCapabilities.mm)
- **[P]** Compressed-format support: every Apple GPU profile in WebKit has ASTC and ETC2, BC only where Metal reports it; three.js enables every compression feature the adapter offers; anisotropy up to 16 is applied only when all three filters are linear. — [WebKit HardwareCapabilities.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/HardwareCapabilities.mm), [WebGPUTextureUtils.js L164-L191](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/utils/WebGPUTextureUtils.js#L164-L191)

**What phones tolerate**
- **[X]** No Apple or WebKit document states a memory limit for a tab. Search extracts of WebKit bug reports describe the mechanism as jetsam (the system killing the web-content or GPU process when it passes its memory limit): a 2022 report lists "GPUP crash via Jetsam" as the typical symptom of huge or numerous textures; an October 2025 report says "iOS Safari limits memory usage, it isn't a physical memory limit"; a 2026 report of a kill on an iPhone 17 Pro was confirmed by a WebKit maintainer as "a jetsam (running over memory limit for the process)"; a 2024 report is titled "[WebGPU] IPC copies too much data leading to jetsams on iOS"; a 2026 report notes that after Safari clears the tab "there's completely nothing left to look at". — [WebKit bug 232357](https://bugs.webkit.org/show_bug.cgi?id=232357), [WebKit bug 300782](https://bugs.webkit.org/show_bug.cgi?id=300782), [WebKit bug 312727](https://bugs.webkit.org/show_bug.cgi?id=312727), [WebKit bug 275422](https://bugs.webkit.org/show_bug.cgi?id=275422), [WebKit bug 303203](https://bugs.webkit.org/show_bug.cgi?id=303203)
- **[X]** three.js forum extracts: the threshold "is different per device and, since the memory is shared between cpu/gpu, can be different depending on other processes running on the phone"; one developer stopped tab crashes by "lowering our texture sizes to 512x512". — [forum: issues with complex scene on iOS](https://discourse.threejs.org/t/issues-with-complex-scene-on-ios/46356), [forum: iOS large textures and LOD](https://discourse.threejs.org/t/ios-large-textures-and-level-of-detail-lod-progressive-loading/80463)
- **[S]** One shipped data point: the open MetaHuman-to-GLB pipeline caps every texture at 1 024 pixels, produces a GLB of about 40 MB, and states "Tested in Safari on iPhone X". — [metahuman-to-glb README](https://github.com/creategamecharacters/metahuman-to-glb/blob/main/README.md)
- **[S]** One desktop data point: the hair-fur-sim "Wayne" demo (three.js 0.186.1, WebGPU) loads the Lee Perry-Smith scan's colour and normal maps "at their full 4096²" as JPEG files (2.27 MB and 2.89 MB) with `anisotropy = 8`. — [hair-fur-sim MulletCharacter.ts](https://github.com/evanlask/hair-fur-sim/blob/main/src/examples/MulletCharacter.ts)

**Virtual or streamed texturing**
- **[S]** r187 has no virtual-texturing example or addon: none of the 621 example names contains "virtual" or "stream". — [examples/files.json at r187](https://github.com/mrdoob/three.js/blob/r187/examples/files.json)

- Set against the only published budgets (VRChat mobile 10 to 40 MB, the MetaHuman web pipeline's 1K cap tested on an iPhone X), a phone face fits at 2K only when block-compressed (13 to 21 MiB), and 4K compressed (53 to 85 MiB) is a desktop or recent-flagship setting; 8K is 8 192 pixels, exactly the default WebGPU maximum, and even compressed costs 213 to 341 MiB for one head. Four uncompressed 4K maps (341 MiB) plus render targets are in the range where iOS reports describe tab kills, though no source gives a threshold.
- The default limit of 16 sampled textures per stage is not a constraint for a face (four maps, a scattering LUT, one or two wrinkle sets, shadow and environment maps fit), but each map should stay a separate decision because the forward fragment node pays one sample per map per pixel.
- Displacement is the map that least needs a GPU texture at run time: it can be applied to vertices once at load (or per level of detail) and discarded, leaving three sampled maps.
- For r187 the practical pipeline is: UASTC with RDO and Zstandard for normal and packed data maps, ETC1S or UASTC for albedo, transcoded in the four workers. Because ETC1S on BC-only desktops lands at 8 bpp BC7, ETC1S saves download size there, not GPU memory.
- **[A]** Scale of the transcode job: one 4K map is 1 048 576 blocks at level 0 and about 1.4 million with mips, producing about 21 MiB of output to transcode in WebAssembly and upload; four 4K maps are about 5.6 million blocks. With no published timing, this has to be measured on the target phones.

## 2. Generating maps at load time from code: render-to-texture and compute baking in r187, costs and pitfalls, tiling textures against per-pixel noise

### Takeaway
r187 has everything needed to bake a procedural skin shader into UV-space maps on the GPU at load time (`rtt()` / `QuadMesh`, the UV-space rasterization used by `LightMapper`, compute into `StorageTexture`, and the `unwrapUVs` unwrapper), and since 2025 a GPU block encoder for the browser exists (spark.js), so baked maps no longer have to stay uncompressed. Nobody has published what per-pixel noise costs against texture lookups in TSL; the bake itself is arithmetic-cheap (a 4K bake is about eight 1080p frames of shading).

### Cited Findings
- **[P]** `rtt( node, width, height, options )` / `convertToTexture()` render a node through a `QuadMesh` into a texture (default type `HalfFloatType`; `autoUpdate = false` plus `textureNeedsUpdate = true` bakes once). `LightMapper` (new in r187) rasterizes meshes in UV space with `material.vertexNode = vec4( uv( 1 ).flipY().mul( 2 ).sub( 1 ).add( jitter ), 0, 1 )`, accumulates jittered samples in a half-float target and dilates empty texels in a resolve pass ("atlas charts need at least three texels of padding"). Compute can write a `StorageTexture` with `textureStore()`, WebGPU only. — [RTTNode.js](https://github.com/mrdoob/three.js/blob/r187/src/nodes/utils/RTTNode.js#L336-L365), [LightMapper.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/lighting/LightMapper.js), [webgpu_compute_texture.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_compute_texture.html)
- **[P]** `unwrapUVs( root, { mode: 'lightmap' | 'normal', resolution, padding } )` (r187) builds a UV atlas at run time; the pull request reports 117 ms (lightmap mode) to 649 ms (normal mode, LSCM) for the 17 684-triangle Lee Perry-Smith head, device not stated, and 23% to 41% looser packing than xatlas. — [unwrapUVs.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/utils/unwrapUVs.js#L1-L29), [PR #34944](https://github.com/mrdoob/three.js/pull/34944)
- **[P]** Pitfalls already recorded from the r187 source: every render-target attachment defaults to RGBA half float (8 bytes per texel, so a 4K bake target is 171 MiB with mips unless the type is set to 8-bit); 32-bit float textures are unfilterable on devices without `float32-filterable` and sampled lookups then compile to a multi-load emulation; mipmaps of render targets are generated automatically only when `generateMipmaps` and `mipmapsAutoUpdate` are both true; the official compute-texture example leaves the mipmap filter commented out; `StorageTexture` baking has no WebGL 2 fallback. — [WGSLNodeBuilder.js L852-L861](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/nodes/WGSLNodeBuilder.js#L852-L861), [Textures.js L376-L446](https://github.com/mrdoob/three.js/blob/r187/src/renderers/common/Textures.js#L376-L446), [webgpu_compute_texture.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_compute_texture.html)
- **[S]** A run-time-generated map can now be block-compressed in the browser: spark.js's `encodeTexture( source, options )` accepts a `GPUTexture` as source and returns a BC7, ASTC 4×4, ETC2, BC5 or EAC texture with mips, usable from three.js as an `ExternalTexture` (three.js gained full `ExternalTexture` support in WebGPURenderer in June 2026, commit "WebGPURenderer: Fully support ExternalTexture (#33816)"; r187's `WebGPUTextureUtils` has the `texture.isExternalTexture` branch). — [spark.js README](https://github.com/ludicon/spark.js/blob/main/README.md), [three.js PR #33816](https://github.com/mrdoob/three.js/pull/33816), [WebGPUTextureUtils.js L320](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/utils/WebGPUTextureUtils.js#L320)
- **[S]** Noise available in r187 TSL without writing any: the MaterialX library (`mx_noise_float/vec3`, `mx_perlin_noise_*`, `mx_fractal_noise_float/vec3`, `mx_worley_noise_*`, `mx_cell_noise_*`, `mx_unifiednoise2d/3d`), `triNoise3D`, `hash`, `interleavedGradientNoise`, and the addons `tsl/math/voronoiNoise.js`, `curlNoise.js`, `Bayer.js`, `tsl/utils/RNoise.js`. — [src/nodes/materialx](https://github.com/mrdoob/three.js/tree/r187/src/nodes/materialx), [TriNoise3D.js](https://github.com/mrdoob/three.js/blob/r187/src/nodes/math/TriNoise3D.js), [examples/jsm/tsl/math](https://github.com/mrdoob/three.js/tree/r187/examples/jsm/tsl/math)
- **[S]** One 2026 browser project evaluates all skin and iris detail per pixel with no textures and names the cost of doing so: DERMIS "evaluates pore normals, pigment variation, regional roughness, iris fibers, crypts and sclera variation", and "fine pore and iris detail is filtered using the pixel footprint to reduce shimmer"; it renders by accumulating samples ("stationary views converge over 24 samples", 2 to 8 samples on moving frames) and caps the longest render side at 640 to 2 000 pixels depending on preset. Its author states it is "an experimental procedural renderer, not a scan or a claim of photorealism". — [dermis-cuda README](https://github.com/SamG-Coder/dermis-cuda/blob/main/README.md)
- **[P]** The known WGSL ceiling for large generated fragment functions ("the combined byte size of all variables in this function exceeds 8192 bytes", three.js issue #34672, fixed for the reported case in r187) applies to shaders with many unrolled noise octaves. — [three.js issue #34672](https://github.com/mrdoob/three.js/issues/34672)

### Inferences
- **[A]** Bake cost: a 4 096² map is 16.8 million texels, the pixel count of about eight 1920×1080 frames; a shader that already runs per pixel in real time bakes one such map in a few frames' worth of GPU time. With 16 jittered samples for antialiasing it is about 130 frames' worth, still on the order of seconds at worst. The slow parts are the ones around the bake: unwrap (0.1 to 0.65 s for a 17 684-triangle head in the PR's figures; a 205 000-triangle head is twelve times the triangles and has no published figure), mip generation, optional compression, and the upload.
- A head built by the project's own anatomy code can emit its own UVs with the mesh, which avoids `unwrapUVs` entirely and its looser packing; the unwrapper is then only a fallback.
- Bake targets should be created 8-bit (`UnsignedByteType`, RG for normals) or converted before use; leaving the default RGBA half float at 4K costs 171 MiB per map with mips **[A]**, eight times the block-compressed size.
- With spark.js the load-time pipeline becomes: bake to RGBA8 → encode to BC7/ASTC (albedo), BC5/EAC RG (normal), BC4/EAC R or packed BC7 (roughness and the rest) → release the RGBA8 targets → optionally cache the compressed bytes in IndexedDB so later loads skip both steps. Its licence (free up to $100 000 lifetime revenue) is a product decision, not a technical one.
- Tiling textures against per-pixel noise, argued from the sources rather than measured: (1) a texture is prefiltered by its mip chain and anisotropic filtering, while procedural detail must be band-limited by hand (DERMIS filters by pixel footprint and still accumulates up to 24 samples); (2) a tiling micro-detail normal (pores) at 512² to 1K, block-compressed, costs 0.3 to 1.3 MiB and one sample; (3) every noise octave adds local variables and code to a fragment function that has a compile-size ceiling; (4) the only thing per-pixel noise buys is freedom from UVs and unlimited magnification. A common split follows: bake unique, low-frequency content (colour variation, regional roughness, meso-scale folds) into the UV maps, and add pore-scale detail from one small tiling normal/cavity texture, blended by a mask in the baked maps.

### Gaps
- No published measurement compares several octaves of 3D noise per pixel with texture lookups in TSL/WGSL on an integrated GPU or a phone.
- Not tested in r187: mip generation on a `StorageTexture` after a compute write; which storage-texture formats beyond `rgba8unorm` work in Safari; whether an `ExternalTexture` produced by spark.js works under the WebGL 2 fallback of `WebGPURenderer` (spark's WebGL path returns a `WebGLTexture`).
- `unwrapUVs` has no timing for meshes above 53 400 triangles.

## 3. Morph targets / blendshapes in r187: implementation, limits, cost, alternatives, wrinkle maps

### Takeaway
On both back ends r187 stores every morph target as one layer of an RGBA32F array texture and runs a vertex-shader loop over all targets with one texel fetch per attribute per non-zero target; at the default WebGPU limit that is at most 256 targets, and for a 205 000-triangle head (roughly 103 000 vertices) each target with normals costs about 3.3 MB, so 52 ARKit shapes are about 170 MB before any corrective. For a head that is skinned by its own `positionNode`, the built-in path is the wrong tool: sparse deltas in a storage buffer or a pre-blended delta texture, and a small set of weight uniforms driving two or three wrinkle normal maps in the fragment node, are the buildable alternatives; no three.js example shows either.

### Cited Findings

**r187 implementation**
- **[S]** `src/nodes/accessors/Morph.js` (used by `WebGPURenderer` on WebGPU and on its WebGL 2 back end; its own comment says "for WebGL2/WebGPU"): one `DataArrayTexture` of `FloatType` RGBA per geometry, one layer per target; each vertex takes 1 texel (position), 2 (with normals) or 3 (with colours) per layer; width is capped by a hard-coded `const maxTextureSize = 4096; // @TODO: Use 'capabilities.maxTextureSize'` and rows are added as needed; the CPU builds it as `new Float32Array( width * height * 4 * morphTargetsCount )`. — [Morph.js L88-L199](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Morph.js#L88-L199)
- **[S]** Evaluation: `Loop( morphTargetsCount, ... )` visits every target; the influence comes from `uniformArray( mesh.morphTargetInfluences, 'float' )` (or, for instanced meshes, a `textureLoad` from `mesh.morphTexture` per instance); inside `If( influence.notEqual( 0 ) )` there is one `textureLoad( bufferMap, ivec2( x, y ) ).depth( i )` per attribute. The base is multiplied by 1 for relative morphs, else by `1 - Σ influences`. Normals are morphed only if the geometry has a `normal` attribute and normal morph attributes; colours only with `vertexColors`. — [Morph.js L34-L55, L227-L337](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Morph.js#L227-L337)
- **[S]** The legacy `WebGLRenderer` does the same thing in GLSL: a float `DataArrayTexture` (width capped by `capabilities.maxTextureSize`) and `for ( int i = 0; i < MORPHTARGETS_COUNT; i ++ ) { if ( morphTargetInfluences[ i ] != 0.0 ) transformed += getMorph( gl_VertexID, i, 0 ).xyz * morphTargetInfluences[ i ]; }`. — [WebGLMorphtargets.js L18-L60](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgl/WebGLMorphtargets.js), [morphtarget_vertex.glsl.js](https://github.com/mrdoob/three.js/blob/r187/src/renderers/shaders/ShaderChunk/morphtarget_vertex.glsl.js)
- **[S]** The count limit is the array-texture layer limit: 256 by default in WebGPU (`maxTextureArrayLayers`); three.js does not check it and does not raise it unless `requiredLimits` is passed. — [WebGPU spec source, limits table](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs), [Morph.js L133-L136](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Morph.js#L133-L136)
- **[P]** Order of vertex transformations in `NodeMaterial.setupPosition()`: morph → skinning → displacement → batch → instance → `positionLocal.assign( positionNode )`. Morph targets write no previous-frame position, so morph-driven motion has zero velocity in the built-in `velocity` node. — [NodeMaterial.js L766-L810](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/NodeMaterial.js#L766-L810), [Morph.js imports](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Morph.js#L2-L16)
- **[S]** Morph code is still moving: r187 added colour morphing in TSL (#35141, October 2026); "Morph: Fix individual `morphTargetInfluences` per object" (#33772) was closed in June 2026, before r187; "Morph: Fix instanced meshes with absolute morph targets" (#35435) was opened on 10 November 2026, after the r187 release. — [PR #35141](https://github.com/mrdoob/three.js/pull/35141), [PR #33772](https://github.com/mrdoob/three.js/pull/33772), [PR #35435](https://github.com/mrdoob/three.js/pull/35435)
- **[S]** `GLTFLoader` expands glTF sparse accessors into dense attributes on load (it copies `sparseIndices` / `sparseValues` into a full `BufferAttribute`), so a sparse blendshape in a file is dense again on the GPU. — [GLTFLoader.js L3215-L3301](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/loaders/GLTFLoader.js#L3215-L3301)

**What other web engines do**
- **[S]** Babylon.js: targets live in a `RawTexture2DArray` when the device allows it ("On WebGL2+, Babylon.js uses textures to store the targets, so the only limit is GPU memory"); otherwise in vertex attributes with `MaxActiveMorphTargetsInVertexAttributeMode = 8`; it falls back from the texture when there are more targets than `texture2DArrayMaxLayerCount`; targets with influence 0 are dropped from the active list (`optimizeInfluencers`), and `numMaxInfluencers` / `ConstantTargetCountForTextureMode` bound the shader loop. — [morphTargetManager.ts L22-L27, L145-L172, L508-L568](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/core/src/Morph/morphTargetManager.ts), [Babylon.js docs, morphTargets.md](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/mesh/morphTargets.md)
- **[S]** PlayCanvas takes the pre-blend route: a `MorphInstance` owns render targets and "the pass blending the morph targets into the render targets"; when weights change it collects the active targets and their weights and renders them with a quad pass into a position (and normal) texture, skipping the pass when "render target textures are full of zeros"; the mesh's vertex shader then reads one blended texel per attribute regardless of how many targets are active. — [playcanvas engine, morph-instance.js](https://github.com/playcanvas/engine/blob/main/src/scene/morph-instance.js)

**How many shapes real faces use on the web**
- **[S]** The MetaHuman-to-GLB pipeline: "UE's GLTFExporter strips morph names and outputs ~700 MB when you request the full 858 RigLogic morphs"; it ships 51 ARKit blendshapes instead (baked from the rig's bones and correctives through Sequencer and transferred in Blender), and records the loss: "FBX bake captures bone deformation only. Fine morph correctives (lip squash, wrinkle deltas) are lost (~5-10mm)"; `browInnerUp` is a single bilateral shape. — [metahuman-to-glb README](https://github.com/creategamecharacters/metahuman-to-glb/blob/main/README.md)
- **[S]** TalkingHead (three.js, WebGL) requires "a Mixamo-compatible rig and ARKit and Oculus viseme blend shapes": 52 ARKit shapes plus 15 Oculus visemes; its default update rate is `modelFPS` 30. — [TalkingHead README](https://github.com/met4citizen/TalkingHead/blob/main/README.md)
- **[P]** `webgpu_morphtargets_face` (the `facecap.glb` head) is the only face example in r187 and uses the built-in path with standard PBR. — [webgpu_morphtargets_face.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_morphtargets_face.html)

**Wrinkle maps**
- **[S]** r187 has no wrinkle-map example or node: no example name contains "wrinkle", and the only morph-weight plumbing in `src/nodes` is the `uniformArray( mesh.morphTargetInfluences, 'float' )` inside `Morph.js`, whose array reference is re-pointed per object in an update hook (`influences.array = object.morphTargetInfluences`). — [examples/files.json at r187](https://github.com/mrdoob/three.js/blob/r187/examples/files.json), [Morph.js L250, L347](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Morph.js#L250)

### Inferences
- **[A]** Memory of the built-in path for the project's near head (205 000 triangles, taken as about 103 000 vertices): position only 1.65 MB per target, position + normal 3.3 MB; 52 ARKit targets 86 MB / 171 MB; 150 targets 247 MB / 494 MB; the same bytes exist once more on the CPU while the `Float32Array` is alive. This is unfilterable RGBA32F and cannot be block-compressed. It is outside any phone budget from section 1.
- Cost per frame of the built-in path: the loop runs over all N targets for every vertex in every pass that draws the head (beauty, each shadow cascade, depth or velocity pre-pass); each active target adds 1 or 2 `textureLoad`s per vertex. With 10 targets active and normals, that is about 20 loads × 103 000 vertices × passes; it is the same "vertex stage reads textures" pattern that tile-based phone GPUs handle worst **[P]**.
- Because the head's vertices are produced by the project's own `positionNode` from joint matrices in a float texture, the built-in morph result (written to `positionLocal` before `positionNode` runs) is discarded unless the custom vertex function consumes it; blendshapes therefore have to be part of the custom vertex path anyway. Three shapes for that, in rising effort:
  1. Joints only: drive the face with more joints (jaw, lips, lids, brows, cheeks) through the existing float-texture skinning and no deltas; zero extra memory, lowest fidelity around the mouth and lids. The MetaHuman web pipelines above show what is lost when correctives are dropped (5 to 10 mm).
  2. Sparse deltas: per target a list of (vertex index, delta) for the vertices that move, in one storage buffer, applied in a compute pass that writes the final positions and normals once per frame (the r187 compute-skinning pattern **[P]**). Memory scales with touched vertices; a blink or a lip-corner shape touches a few percent of a head.
  3. Pre-blend to a texture as PlayCanvas does: blend active targets into one RGBA16F delta texture when weights change; the vertex stage then pays one or two fetches however many shapes are active. Works on the WebGL 2 back end, where compute is only emulated by transform feedback.
  PCA or other basis compression of the delta set fits options 2 and 3 (fewer, denser basis vectors) but nothing found documents it for the web.
- Wrinkle maps in a hand-written TSL fragment node need no engine support: create a few `uniform( 0 )` weights (or one `uniformArray`) updated on the CPU from the animation weights (for example brow raise, brow compress, nose wrinkle, smile left, smile right), pack region masks into the channels of one or two mask textures, and compute `n = normalize( mix( nBase, nWrinkleA, saturate( dot( maskA, weightsA ) ) ) )` (two or three alternative normal maps, each with matching cavity/albedo darkening if wanted). The cost is one extra normal-map sample per wrinkle set plus one mask sample, and at 8 bpp each 2K wrinkle normal map is 5.3 MiB **[A]**. With pre-integrated scattering the blended normal also feeds the curvature term, so wrinkles deepen shading without a new pass.
- Morph-driven motion needs its own velocity if the game's temporal upscaler uses motion vectors (keep last frame's positions from the compute pass).

### Gaps
- No published timing of r187 morph targets by count on WebGPU or WebGL 2, on any device.
- No three.js or TSL wrinkle-map implementation was found; the recipe above is derived from how weights and textures work in TSL, not from a reference.
- No web implementation of PCA-compressed or compute-blended blendshapes was found (search budget ran out before a dedicated search).
- The vertex count of the project's head was assumed as half the triangle count; a mesh with split vertices is larger.

## 4. Subsurface scattering in a forward renderer with hand-written node materials: pre-integrated against screen-space

### Takeaway
r187 still ships no diffusion-based skin scattering, but a complete screen-space implementation now exists as an open three.js pull request (#33761, June 2026: a Burley-profile disk blur with 32 taps by default, demonstrated on the Lee Perry-Smith head), and Babylon.js's equivalent selects a WGSL shader under WebGPU. For a single forward pass with a hand-written fragment node, pre-integrated scattering by curvature remains the only option that adds no pass, no attachment and no dependence on temporal antialiasing; the screen-space route costs an extra MRT attachment that the fragment node must write itself, a full-screen pass of 16 to 40 taps per skin pixel, and in the three.js version a temporal resolve.

### Cited Findings

**three.js**
- **[P]** r187 core and addons contain no separable, Burley or pre-integrated skin node; `MeshSSSNodeMaterial` is the 2011 translucency approximation and `SSSNode` is screen-space shadows. — [MeshSSSNodeMaterial.js](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/MeshSSSNodeMaterial.js#L39-L75), [SSSNode.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/tsl/display/SSSNode.js#L11-L45)
- **[S]** New since the earlier notes: pull request #33761 "Examples: Add Screen-Space Subsurface Scattering example" (opened 9 June 2026, state open on 18 November 2026; head commit `ffbd04e` dated 18 June 2026). It adds `examples/jsm/tsl/display/SSSSNode.js` (891 lines), `src/materials/nodes/MeshSubsurfaceNodeMaterial.js` (124 lines) and `examples/webgpu_postprocessing_ssss.html`, whose scene is the Lee Perry-Smith head with its colour map and a scanned shell. It is not in r187. — [three.js PR #33761](https://github.com/mrdoob/three.js/pull/33761)
- **[S]** What that node does (read from the pull-request head): it "blurs the lit scene color using a Burley normalized diffusion profile sampled in screen space"; samples are a precomputed Fibonacci-spiral disk whose radii come from inverting the Burley CDF (Halley's method, 12 iterations); `samples` defaults to 32 with a hard maximum of 64; a 64×64 white-noise texture rotates the disk per pixel; `resolutionScale` "scales the number of diffusion taps per pixel to `round( samples * resolutionScale )`, striding them across the full kernel so the blur radius stays the same and only gets noisier", while "the output always stays full resolution (single pass)"; `jitter = true` advances the rotation each frame and "requires the usage of `TRAANode`"; samples are rejected by depth difference; the result goes to one `HalfFloatType` render target; an optional view-space-normal attachment orients the disk on each pixel's tangent plane; the exit point applies a "Disney Diffuse Fresnel transmission"; references are the SIGGRAPH 2018 "Efficient screen space subsurface scattering" talk and Pixar's approximate BSSRDF note. The example runs `samples = 32`, `resolutionScale = 0.5` (16 taps), `jitter = true` with TRAA, and `AgXToneMapping`. — [three.js PR #33761, SSSSNode.js](https://github.com/mrdoob/three.js/pull/33761/files)
- **[S]** Its inputs: the pass must have an MRT with an `albedo` attachment whose alpha is an SSS slot index (0 = no scattering): `scenePass.setMRT( mrt( { output, albedo: vec4( diffuseColor.rgb, 0.0 ) } ) )`. `MeshSubsurfaceNodeMaterial extends MeshStandardNodeMaterial` writes its slot through `this.mrtNode = mrt( { albedo: vec4( diffuseColor.rgb, this.subsurfaceSlotNode ) } )`. Per-material controls: `scatteringDistanceNode` (per-channel blur radius in world units, default `(0.5, 0.08, 0.03)`, described as human skin with "red blurs ~6× wider than green"), `scatteringColorNode`, `strengthNode`, and `texturingModeNode` (0 `blur(color)`; 1 `sqrt(albedo) * blur(color / sqrt(albedo))`; 2 `albedo * blur(color / albedo)`, "recommended for scanned skin textures", the default). It blurs the whole lit colour, specular included, rather than a separate diffuse-irradiance buffer. — [three.js PR #33761, MeshSubsurfaceNodeMaterial.js](https://github.com/mrdoob/three.js/pull/33761/files)
- **[P]** The r187 constraint for hand-written materials: `material.mrtNode` is merged with the pass MRT only on the built-in lit path; when `fragmentNode` is set the code is `if ( fragmentNode.isOutputStructNode !== true ) fragmentNode = fragmentNode.convert( builder.getOutputType() ); resultNode = this.setupOutput( builder, fragmentNode )`, i.e. a single colour output unless the fragment node is itself an `mrt({...})` struct; WebGPU rejects a pipeline in which a colour target with a non-zero write mask has no matching shader output. Default budget: 8 colour attachments, 32 bytes per sample. — [NodeMaterial.js L525-L598](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/NodeMaterial.js#L525-L598), [WebGPU spec source](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)
- **[P]** `TRAANode` and `TAAUNode` require MSAA to be off and a `velocity` output. — [TRAANode.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/tsl/display/TRAANode.js)

**Babylon.js**
- **[S]** `SubSurfaceConfiguration` creates its post-process with `shaderLanguage: this._scene.getEngine().isWebGPU ? ShaderLanguage.WGSL : ShaderLanguage.GLSL`, so the screen-space pass has a WebGPU code path in source; it requires four pre-pass textures (depth, square-rooted albedo, colour, irradiance), `needsImageProcessing = true`, registers at most 5 diffusion-profile colours ("You already reached the maximum number of diffusion profiles"), and takes `metersPerUnit` (default 1). — [subSurfaceConfiguration.ts L81-L150](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/core/src/Rendering/subSurfaceConfiguration.ts)
- **[P]** Its shader importance-samples the Burley profile on a Fibonacci disk with `_SssSampleBudget = 40` and `SSS_PIXELS_PER_SAMPLE = 4.`, bilateral in depth; the documentation warns that it "adds a lot of additional work for the GPU ... smaller GPUs won't necessarily have the resources to run this effect" and still says WebGL 2 only. — [subSurfaceScattering.fragment.fx](https://github.com/BabylonJS/Babylon.js/blob/master/packages/dev/core/src/Shaders/subSurfaceScattering.fragment.fx), [Babylon.js docs, masterPBR.md](https://github.com/BabylonJS/Documentation/blob/master/content/features/featuresDeepDive/materials/using/masterPBR.md)
- **[X]** A 2026 forum thread on Babylon.js 9.18.2 reports the scattering sphere turning almost black when the scene goes through an intermediate render target and the Frame Graph, "on both WebGPU and WebGL2"; an older thread notes Babylon had subsurface scattering in PBR "but no dedicated skin or hair shader". No performance figures appear in any extract. — [Babylon forum 63870](https://forum.babylonjs.com/t/pbr-subsurface-scattering-becomes-black-with-an-intermediate-rendertargettexture-and-frame-graph/63870), [Babylon forum 8975](https://forum.babylonjs.com/t/how-to-cross-the-valley-of-terror/8975)

**Community implementations found in 2026**
- **[S]** hair-fur-sim (three.js 0.186.1, WebGPU, TSL) has a `SkinMaterial`: `MeshPhysicalNodeMaterial` with a `SkinLightingModel extends PhysicalLightingModel` whose `direct()` adds light through thin skin only: per-vertex thickness (computed on the CPU by searching for the opposite surface, capped at 12 mm, ears only), Beer–Lambert `exp( -thickness / meanFreePath )` with mean free path `(3 mm, 0.9 mm, 0.6 mm)`, a wrap of 0.3, no shadow-map lookup ("an ear lit from behind is in its own shadow on the side we see"), and the cranium as an analytic ellipsoid occluder. It has no lateral diffusion. — [hair-fur-sim SkinMaterial.ts](https://github.com/evanlask/hair-fur-sim/blob/main/src/examples/SkinMaterial.ts)
- **[S]** DERMIS: "Skin diffusion is an artistic screen-space approximation". The MetaHuman-to-GLB viewer applies no scattering: skin is the glTF PBR material with `specularIntensity = 0.65`, a roughness floor of 0.42 and no sheen or clearcoat. — [dermis-cuda README](https://github.com/SamG-Coder/dermis-cuda/blob/main/README.md), [metahuman-to-glb viewer.js](https://github.com/creategamecharacters/metahuman-to-glb/blob/main/5.7/native-glb/stages/04-webview-build/templates/viewer.js)
- **[S]** `nff747/subsurface-scattering-wgsl` (1 star, pushed November 2026) advertises a two-pass separable Jimenez blur as WebGPU compute with a three.js pass and claims "0.34 ms" at 1080p with 17 samples. Its README mixes boilerplate marketing text with the technical part, the benchmark names no GPU and compares against a single-thread CPU loop; the figure should not be relied on. — [subsurface-scattering-wgsl README](https://github.com/nff747/subsurface-scattering-wgsl/blob/main/README.md)

### Inferences
- Cost structure, side by side (no measured milliseconds exist for either in a browser):

  | | Pre-integrated by curvature (what the head does today) | Screen-space diffusion (PR #33761 / Babylon style) |
  | --- | --- | --- |
  | Extra passes | none | one full-screen pass (three.js PR: single pass; Jimenez style: two) |
  | Extra attachments | none | at least one (`albedo` + slot, RGBA8 = 4 bytes per sample); a diffuse-only variant needs a second colour target (8 bytes at RGBA16F) |
  | Per-pixel work | one LUT sample (or a fitted function) per light plus a curvature input | 16 to 40 taps, each a colour and a depth read, on skin pixels |
  | Antialiasing | works with MSAA and alpha-to-coverage | the three.js version needs TRAA at low tap counts, hence no MSAA |
  | Hand-written fragment node | nothing special | must return `mrt( { output, albedo, ... } )` itself, as must every other hand-written material drawn in that pass |
  | Light bleeding across shadow edges and features | approximated (needs a separate shadow-penumbra term) | real, at screen resolution |
  | Phones | free | an extra attachment in tile memory plus a pass; Babylon's own documentation advises against it on small GPUs |

- For this project (one forward pass, hand-written fragment node, custom `finish()` tone step) pre-integrated scattering stays the base on every device. A screen-space pass is a desktop-only upgrade, and the cheapest port is the pull request's node: its disk kernel and CPU-side Burley tables are engine-independent, and the only integration work is making the head's fragment node return the struct and running the pass before the game's own tone step, in linear HDR.
- The pull request's design blurs lit colour including specular and divides by albedo; for a face with two sharp GGX lobes that softens highlights unless specular is written to a separate target and added after the blur, which is what Babylon's irradiance target does. That costs the second attachment noted above.
- Ear and nostril back-lighting is a separate, cheap term in either route: per-vertex or baked thickness with a Beer–Lambert falloff, as hair-fur-sim does in fewer than 20 lines.

### Gaps
- No measured frame cost of screen-space scattering in any web engine on a named device (three.js PR, Babylon, Sketchfab).
- The discussion on PR #33761 (why it has not merged, maintainers' objections, any performance remarks) could not be read; only its code and commit list were.
- Whether Babylon's pass works end to end under its WebGPU engine with the Frame Graph today is unresolved (source says WGSL exists, documentation says WebGL 2 only, a forum extract reports a failure).
- No TSL pre-integrated skin implementation by anyone else was found to compare against the project's own.

## 5. Hair, eyebrows, lashes, stubble and peach fuzz in the browser

### Takeaway
Real strand hair runs in browsers under WebGPU today: one three.js r186 project draws roughly 100 000 strands as camera-facing ribbons expanded in the vertex shader with stochastic MSAA coverage, and a raw-WebGPU port measures 1.29 million strand particles drawn as ribbons in about 6 ms of GPU time on an Apple Silicon Mac. r187 itself has no hair example; its building blocks are alpha-to-coverage (4× MSAA only), hashed alpha testing, a weighted-blended OIT pass added as an addon, and fat lines. Hair cards with alpha-to-coverage are what the shipped MetaHuman web viewers use and are the only approach shown running on a 2017 phone.

### Cited Findings

**What r187 provides**
- **[S]** No example name in r187 contains "hair", "fur" or "strand"; the only source hits for "hair" are unrelated generators. — [examples/files.json at r187](https://github.com/mrdoob/three.js/blob/r187/examples/files.json)
- **[S]** Alpha-to-coverage: the pipeline sets `multisample.alphaToCoverageEnabled = material.alphaToCoverage && sampleCount > 1`; the sample count is clamped to `sampleCount >= 4 ? 4 : 1`, and the WebGPU spec allows only 1 or 4 ("must be either 1 or 4"). On the built-in material path, when `alphaTest` is set together with `alphaToCoverage`, alpha is sharpened with `smoothstep( alphaTest, alphaTest + fwidth( alpha ), alpha )` before a discard at 0; a material with `alphaToCoverage` is not treated as opaque (`isOpaque()` requires `alphaToCoverage === false`). The fallback when antialiasing is off dates from PR #29395 (September 2024). — [WebGPUPipelineUtils.js L212](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/utils/WebGPUPipelineUtils.js#L212), [WebGPUUtils.js L249-L253](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/utils/WebGPUUtils.js#L249-L253), [NodeMaterial.js L884-L911](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/NodeMaterial.js#L884-L911), [NodeBuilder.js L631](https://github.com/mrdoob/three.js/blob/r187/src/nodes/core/NodeBuilder.js#L631), [WebGPU spec source](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs), [PR #29395](https://github.com/mrdoob/three.js/pull/29395)
- **[S]** Alpha hashing: `material.alphaHash = true` discards when `alpha < getAlphaHashThreshold( positionLocal )`, an implementation of Wyman and McGuire's hashed alpha testing (object-space hash at two log-spaced scales chosen from `dFdx/dFdy` of position, `ALPHA_HASH_SCALE = 0.05`); example `webgpu_materials_alphahash`. — [getAlphaHashThreshold.js](https://github.com/mrdoob/three.js/blob/r187/src/nodes/functions/material/getAlphaHashThreshold.js), [examples/files.json at r187](https://github.com/mrdoob/three.js/blob/r187/examples/files.json)
- **[S]** Both of those live in `setupDiffuseColor()`, which runs only when `fragmentNode === null`; a hand-written fragment node gets neither the alpha test nor the hash and must discard itself (the pipeline's alpha-to-coverage flag still applies to whatever alpha it outputs). — [NodeMaterial.js L525-L598, L884-L911](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/NodeMaterial.js#L525-L598)
- **[S]** Order-independent transparency: `OITPassNode` (`oitPass( scene, camera )`, example `webgpu_oit`) implements McGuire and Bavoil's weighted blended OIT. Transparent objects render in a second pass into two targets, an RGBA16F weighted colour sum and an R8 revealage, sharing the opaque depth buffer without depth writes, then composite. Limits stated in the source: "Only transparent materials using `NormalBlending` and no transmission qualify"; "MSAA is only supported with the WebGPU backend"; OIT objects "contribute to the color output but not to custom MRT outputs". The default weight is the paper's equation 9 from eye-space depth; `weightNode` overrides it. — [OITPassNode.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/tsl/display/OITPassNode.js), [webgpu_oit.html](https://github.com/mrdoob/three.js/blob/r187/examples/webgpu_oit.html)
- **[S]** WebGPU lets a fragment shader output `sample_mask`, but not together with alpha-to-coverage (pipeline validation requires `alphaToCoverageEnabled` to be false when `sample_mask` is an output), and compatibility mode forbids `sample_mask` and `sample_index` altogether. three.js has no built-in node for it. — [WebGPU spec source, validating GPURenderPipelineDescriptor](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)
- **[S]** Lines and instancing: `Line2NodeMaterial` draws fat lines as instanced quads (world or screen units, dashes, optional alpha-to-coverage); for `InstancedMesh`, matrices go in a uniform buffer while `count × 64 bytes` fits the uniform-binding limit (1 024 instances at the 64 KB default) and in instanced vertex attributes above that; nothing in the source caps the instance count. — [Line2NodeMaterial.js](https://github.com/mrdoob/three.js/blob/r187/src/materials/nodes/Line2NodeMaterial.js), [Instance.js L43-L55](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/Instance.js#L43-L55)

**Strand hair demos**
- **[S]** hair-fur-sim (Evan Lask; three.js 0.186.1 with WebGPU and TSL; pushed October 2026; "Chrome, Edge, or Safari 26 or later"). "A few thousand guide hairs are simulated ... Hundreds of thousands of drawn hairs follow the guides around them", each drawn "as a thin ribbon". The README states no frame times; a meter in the page shows them live. — [hair-fur-sim README](https://github.com/evanlask/hair-fur-sim/blob/main/README.md), [mulletStyle.ts](https://github.com/evanlask/hair-fur-sim/blob/main/src/hair/groom/styles/mulletStyle.ts), [quality.ts](https://github.com/evanlask/hair-fur-sim/blob/main/src/app/quality.ts), [params.ts](https://github.com/evanlask/hair-fur-sim/blob/main/src/hair/params.ts)

- **[S]** Its fibre shading, in TSL: a "Marschner-style hair BSDF (R / TT / TRT lobes + multiple-scattering diffuse), following the real-time approximation in Karis 2016, 'Physically Based Hair Shading in Unreal'", with Fresnel F0 for keratin (η = 1.55) and a shadow transmittance that "tints the multiple-scattering term: deeper inside = more saturated"; environment light comes from nine spherical-harmonic coefficients projected from the equirectangular HDR map on the CPU (Ramamoorthi and Hanrahan convolution), not from per-point environment-map lookups. — [hair-fur-sim hairBSDF.ts](https://github.com/evanlask/hair-fur-sim/blob/main/src/hair/render/hairBSDF.ts), [hair-fur-sim envSH.ts](https://github.com/evanlask/hair-fur-sim/blob/main/src/hair/render/envSH.ts)
- **[S]** HairyMess Web (raw WebGPU and WGSL, no framework; pushed August 2026; Chrome/Edge 113+, Safari 26+, Firefox 141+). - **[S]** Frostbitten hair WebGPU (Scthe, 2024, 111 stars; Chrome only at the time): strands are software-rasterized in compute shaders with analytical antialiasing and order-independent transparency by depth slices per screen tile, Kajiya-Kay diffuse plus Marschner specular evaluated per strand point rather than per pixel, shadows and AO; "stable <10ms (total frame time) on RTX3060 in the default view" with the Sintel hair model; the fine pass went from 30 ms to 10 ms by configuration (tile size 16 → 8 pixels) and to "~3.3ms" after parallelizing over pixels; the author's remark on tooling: "WebGPU does not offer access to profilers. **Hair cards**
- **[S]** `creategamecharacters/threejs-hair-shader` (MIT, October 2026): one hair-card shader with twin implementations, GLSL patches for `WebGLRenderer` and TSL node materials for `WebGPURenderer`. - **[S]** The MetaHuman-to-GLB viewer (three.js 0.170, `WebGLRenderer`) uses the same scheme for scalp hair, brows, beard and lashes exported as card meshes: it reads `gl.SAMPLES` and uses "alpha-to-coverage primary, two-pass blend fallback", with "per-strand root darkening and tint variance from atlas channels" and "anisotropic specular along strand tangent"; facial-hair cards follow the face blendshapes by inverse-distance propagation. ### Inferences
- The choice of coverage technique is tied to the choice of antialiasing, and r187 forces it: alpha-to-coverage needs 4× MSAA; TRAA/TAAU need MSAA off; `sample_mask` stochastic coverage needs MSAA, cannot be combined with alpha-to-coverage and is absent in compatibility mode. A game that resolves with its own temporal upscaler therefore uses hashed or stochastic per-pixel coverage that changes each frame (hair-fur-sim's `'temporal'` mode, or `getAlphaHashThreshold` with a per-frame offset) and must supply strand motion vectors; a game on MSAA uses alpha-to-coverage or `sample_mask`.
- `OITPassNode` is a poor fit for dense hair: weighted blended OIT is designed for a few overlapping layers, adds two full-screen targets and a pass, and excludes its objects from custom MRT outputs. It suits eyelashes-over-eye or a thin fringe at most. A depth-writing coverage technique keeps hair inside the single forward pass.
- Budget by the one device-named measurement: about 6 ms GPU for 1.29 million ribbon particles at 1280×769 on an M-series Mac implies that brows (a few hundred strands each), lashes (one to two hundred per eye), stubble and peach fuzz (tens of thousands of very short, two- or three-point strands) are small next to scalp hair: 20 000 fuzz strands × 3 points is 60 000 particles, about a twentieth of that test **[A]**. The cost that does not scale down is overdraw of many near-transparent sub-pixel strands, which is why both strand projects clamp to a minimum pixel width and trade strand count for width with distance.
- Strand expansion in the vertex stage reads strand points from a storage buffer or data texture; in compatibility-mode WebGPU and on the WebGL 2 back end that means a data texture and `textureLoad`, which fits the project's existing float-texture skinning. Rooting strands to the skinned, morphed head needs the strand roots to go through the same deformation (hair-fur-sim moves "the hair roots with" the body in compute each frame).
- For phones, the evidence supports cards, not strands, for scalp hair (the only phone-tested viewer uses cards with a 1K atlas), and geometry or cards for brows and lashes; peach fuzz on phones is better folded into the skin shader (a grazing-angle sheen or "asperity" term) than drawn.

### Gaps
- No frame times for strand hair on any phone, and none for the three.js-based project on any device; the one Apple Silicon figure names no chip and uses a small window.
- No measurements of alpha-to-coverage against hashed alpha against `sample_mask` coverage in three.js.
- Per-fibre hair shading in TSL was read in one project only (hair-fur-sim's Karis-style Marschner approximation); no comparison of hair shading models or their cost in a browser was found.
- Eyelash and eyebrow strand counts above are general figures from memory **[R]**, not from a cited source.

## 6. Eyes and teeth in the browser

### Takeaway
No reference eye shader exists for three.js WebGPU/TSL: r187 has no eye example, a GitHub repository search finds none, and the two open 2026 browser humans both state that they do not do corneal refraction. TSL has the pieces (`refract`, `parallaxUV` / `parallaxDirection`, clearcoat, analytic ray–plane or ray–sphere math in a `Fn`), so an eye is a few dozen lines to write but has to be written from the native-engine literature.

### Cited Findings
- **[S]** r187 examples: none named for eyes or teeth; the nearest relevant ones are `webgpu_parallax_uv`, `webgpu_refraction` and `webgl_morphtargets_webcam` (which rotates eyeballs). TSL exports `parallaxDirection` (`positionViewDirection.mul( TBNViewMatrix )`) and `parallaxUV( uv, scale )`, and `refract( I, N, eta )` and `reflect` as math nodes. — [examples/files.json at r187](https://github.com/mrdoob/three.js/blob/r187/examples/files.json), [AccessorsUtils.js L23-L34](https://github.com/mrdoob/three.js/blob/r187/src/nodes/accessors/AccessorsUtils.js#L23-L34), [MathNode.js L913, L1103](https://github.com/mrdoob/three.js/blob/r187/src/nodes/math/MathNode.js#L1103)
- **[S]** A GitHub repository search for "eye shader threejs" on 18 November 2026 returned three unrelated effects (a silk background, a compound-eye Voronoi experiment, a fire eye) and no physically based eye. — [GitHub repository search](https://github.com/search?q=eye+shader+threejs&type=repositories)
- **[S]** MetaHuman-to-GLB viewer (WebGL): the material kind is called `eye_refractive` but is described in the file header as "iris atlas sampling around mesh pole UV + limbus darkening + radial iris/sclera + pupil ramp + veins"; it sets roughness 0.05 and `clearcoat = 1.0`, `clearcoatRoughness = 0.03` ("MH eyes are wet — almost mirror roughness + clearcoat layer"), and reconstructs iris colour from an atlas channel remap, a limbus ramp and an iris/sclera `smoothstep` on radius. No refracted ray is traced. Teeth, saliva, eyelashes, eye-occlusion and cartilage meshes get "flat defaults"; "Eye occlusion mesh has no alpha mask. Currently renders as a flat 40% dark layer over the whole eye". — [metahuman-to-glb viewer.js L9-L12, L1139-L1290](https://github.com/creategamecharacters/metahuman-to-glb/blob/main/5.7/native-glb/stages/04-webview-build/templates/viewer.js), [metahuman-to-glb README](https://github.com/creategamecharacters/metahuman-to-glb/blob/main/README.md)
- **[S]** DERMIS evaluates "iris fibers, crypts and sclera variation" procedurally and states "the eyes do not implement physical corneal refraction". — [dermis-cuda README](https://github.com/SamG-Coder/dermis-cuda/blob/main/README.md)
- **[X]** References outside three.js that describe the technique to port: a Godot shader that bends the view ray with `refract()` at the cornea and intersects the iris plane; CryEngine's eye shader with "iris parallax mapping" and an iris-depth control; an Animal Logic SIGGRAPH submission noting that corneal refraction "plays a significant role in the perceived shape of the iris and the pupil". A TSL parallax-occlusion-mapping material (`threejs-pom`) exists as a possible starting point for iris depth. — [Godot refractive procedural eye](https://godotshaders.com/shader/eye/), [CryEngine eye shader docs](https://www.cryengine.com/docs/static/engines/cryengine-3/categories/1114113/pages/15728675), [Animal Logic eye refraction](https://animallogic.com/wp-content/uploads/2024/08/Eye_Refraction_Siggraph_Submission_.pdf), [threejs-pom](https://gh.mise.run.place/dswhy/threejs-pom)
- **[P]** `MeshPhysicalNodeMaterial` "transmission" refracts the already-rendered framebuffer (`viewportMipTexture`), which is a screen-space effect for glass, not a way to see an iris through a cornea on the same mesh. — [PhysicalLightingModel.js L29-L146](https://github.com/mrdoob/three.js/blob/r187/src/nodes/functions/PhysicalLightingModel.js#L29-L146)

### Inferences
- The eye fits the project's single forward pass as a purely analytic fragment function: refract the view vector at the corneal surface normal (index about 1.376 **[R]**), intersect an iris plane or sphere at the anterior-chamber depth, evaluate the iris (procedural or a small texture) at the hit, add limbus darkening, then a sharp GGX lobe from the smooth cornea normal (the head's second lobe can serve), plus sclera with the same pre-integrated scattering as skin. No texture reads are required; cost is comparable to a few lines of the skin shader.
- The elements the open web viewers lack are the ones that matter in close-up: an eyelid contact shadow (ambient occlusion from the lids over the sclera, which the MetaHuman viewer renders as a flat layer), a tear-line meniscus, and lashes with enough texel density (the 1K cap visibly hurts them there). These are geometry-plus-mask problems, not renderer limits.
- Teeth need no special machinery: the skin scattering term with a tooth profile, strong occlusion from lips and cheeks (a baked or analytic mouth-cavity darkening driven by jaw opening), and a wet specular lobe. No browser reference was found.

### Gaps
- No TSL or WebGPU eye or teeth reference implementation exists that could be read; the technique sources are search extracts of native-engine material.
- No cost measurement of a refractive eye shader in a browser.
- Caustics on the iris and subsurface in the sclera were not researched.

## 7. Lighting a portrait inside a game world: environment, spherical harmonics, shadows, tone mapping

### Takeaway
r187 supplies GGX-prefiltered environment maps (PMREM rebuilt on cube render targets in r187), nine-coefficient spherical-harmonic probes and a probe-grid addon, and three shadow filters under WebGPU (basic, a 5-tap Vogel-disk PCF, VSM), with soft variable-penumbra shadows (PCSS) absent but pluggable through `shadow.filterNode`. Its tone mappers are Reinhard, Cineon, ACES Filmic, AgX and Khronos PBR Neutral; by construction Neutral leaves hue untouched and mid-range base colours exact, while ACES and AgX desaturate, which is what matters for skin when the game's own `finish()` step replaces them.

### Cited Findings

**Environment and probes**
- **[S]** `PMREMGenerator` (common renderer): "Generates a Prefiltered, Mipmapped Radiance Environment Map ... The result is a cube render target whose mip levels store GGX-filtered radiance at increasing roughness"; sharp levels use GGX visible-normal importance sampling with `GGX_SAMPLES = 256`, rough levels integrate a lower-resolution source; targets are half float; `fromScene()` and `fromEquirectangular()` throw unless `await renderer.init()` has completed. Examples: `webgpu_pmrem_cubemap`, `webgpu_pmrem_equirectangular`, `webgpu_pmrem_scene`, `webgpu_pmrem_test`, `webgpu_materials_envmaps_bpcem`. — [PMREMGenerator.js L33-L62, L104-L118, L473-L514](https://github.com/mrdoob/three.js/blob/r187/src/renderers/common/extras/PMREMGenerator.js), [examples/files.json at r187](https://github.com/mrdoob/three.js/blob/r187/examples/files.json)
- **[S]** Spherical harmonics: `LightProbeNode` uploads 9 `vec3` coefficients (`light.sh.coefficients[ i ] × intensity`) and adds `getShIrradianceAt( normalWorld, coefficients )` to irradiance; `getShIrradianceAt` is exported from `three/tsl`, so a hand-written fragment node can call it directly. r187 also ships `LightProbeGrid` (a probe volume with a GPU SH-projection pass) and examples `webgpu_lightprobe`, `webgpu_lightprobe_cubecamera`, `webgpu_lightprobes`, `webgpu_lightprobes_complex`, `webgpu_lightprobes_sponza`. — [LightProbeNode.js](https://github.com/mrdoob/three.js/blob/r187/src/nodes/lighting/LightProbeNode.js), [getShIrradianceAt.js](https://github.com/mrdoob/three.js/blob/r187/src/nodes/functions/material/getShIrradianceAt.js), [LightProbeGrid.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/lighting/LightProbeGrid.js)
- **[S]** hair-fur-sim lights its hair from an SH projection of the environment (`src/hair/render/envSH.ts`) rather than sampling the PMREM per strand point. — [hair-fur-sim source tree](https://github.com/evanlask/hair-fur-sim/tree/main/src/hair/render)

**Shadows**
- **[S]** Under `WebGPURenderer` the filter table is `[ BasicShadowFilter, PCFShadowFilter, null /* PCFSoftShadowMap, removed */, VSMShadowFilter ]`. `PCFShadowFilter` "uses 5 samples distributed via Vogel disk pattern, rotated per-pixel using Interleaved Gradient Noise (IGN) ... combined with hardware PCF (4-tap ...)". A light's shadow can supply its own filter: `const filterFn = shadow.filterNode || this.getShadowFilterFn( renderer.shadowMap.type )`. Cascades and tiling are addons (`CSMShadowNode`, `TileShadowNode`, the latter without VSM support). — [ShadowNode.js L117, L363-L384, L480](https://github.com/mrdoob/three.js/blob/r187/src/nodes/lighting/ShadowNode.js#L117), [ShadowFilterNode.js L44-L116](https://github.com/mrdoob/three.js/blob/r187/src/nodes/lighting/ShadowFilterNode.js#L44-L116), [TileShadowNode.js](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/tsl/shadows/TileShadowNode.js)

**Tone mapping**
- **[S]** `ToneMappingFunctions.js` exports `linearToneMapping`, `reinhardToneMapping`, `cineonToneMapping`, `acesFilmicToneMapping`, `agxToneMapping`, `neutralToneMapping`, each a pure TSL function of `( color, exposure )` that a custom output step can call. ACES: `color * exposure / 0.6`, an sRGB→ACES input matrix, the Stephen Hill RRT+ODT rational fit, an output matrix, clamp. AgX: convert to Rec. 2020, inset matrix, `log2` over −12.47 to +4.03 EV, a sixth-order contrast polynomial, outset matrix, power 2.2, back to sRGB primaries. Neutral: subtract a toe offset (`0.04`, quadratic below 0.08), leave colours unchanged while the peak channel is under `0.8 − 0.04 = 0.76`, above that compress the peak toward 1 and blend toward white with `Desaturation = 0.15`. — [ToneMappingFunctions.js L15-L200](https://github.com/mrdoob/three.js/blob/r187/src/nodes/display/ToneMappingFunctions.js#L15-L200)
- **[S]** Khronos's specification of PBR Neutral states the properties that follow from that formula: output equals input minus 0.04 "for all input colors where 0.08 ≤ R, G, B ≤ 0.8", so "the base color will be exactly reproduced in the output render for a shiny dielectric material facing the camera under unitary-white lighting"; "for all input colors, there are no hue shifts"; it "does not apply any gamut mapping" and assumes Rec. 709 input. — [KhronosGroup/ToneMapping, PBR_Neutral README](https://github.com/KhronosGroup/ToneMapping/blob/main/PBR_Neutral/README.md)
- **[S]** The model-viewer write-up that motivated it: "hue should remain unchanged ... and saturation should be retained as much as possible"; "The primary problem with ACES (and even AgX) tone mapping reported by e-commerce users is their significant loss of saturation"; curves like ACES "not only compress the luma, but also push colors toward white the brighter they are", so "a paper-white object must appear dimmer than 255 under diffuse lighting"; plain clamping shows "extreme hue skews of the highlights". The text concerns product colours, not skin. — [model-viewer tone-mapping page source](https://github.com/google/model-viewer/blob/master/packages/modelviewer.dev/examples/tone-mapping.html)
- **[S]** What the 2026 head demos chose: the three.js screen-space scattering example uses `AgXToneMapping` at exposure 1; the MetaHuman-to-GLB viewer uses `NeutralToneMapping` at exposure 1 with a `RoomEnvironment` PMREM (`pmrem.fromScene( new RoomEnvironment(), 0.04 )`). — [three.js PR #33761](https://github.com/mrdoob/three.js/pull/33761/files), [metahuman-to-glb viewer.js L97-L115](https://github.com/creategamecharacters/metahuman-to-glb/blob/main/5.7/native-glb/stages/04-webview-build/templates/viewer.js)

### Inferences
- A face in a game world with its own sun and sky needs three lighting inputs in the hand-written fragment node, all available as plain TSL: the sun (direct, shadowed), sky irradiance for the diffuse and scattering term (nine SH coefficients evaluated with `getShIrradianceAt`, effectively free), and sky/world radiance for the two GGX lobes (a PMREM cube lookup per lobe, or one lookup at a blended roughness). Regenerating the PMREM when the sky changes costs up to 256 samples per texel per sharp mip level, so it should be amortized over frames or kept at a small cube size; SH can be updated every frame.
- Shadow softness on a face is where the built-in filters are weakest: a fixed 5-tap Vogel PCF gives a constant penumbra, whereas a nose or brow shadow should widen with distance from the occluder. Because the project lights by hand, it can sample its shadow map with its own PCSS (blocker search plus variable-radius Vogel disk; 16 to 32 depth taps on face pixels) without touching three.js; pairing it with a screen-space contact march along the sun covers eyelids, nostrils and lip lines that a shadow map cannot resolve. Pre-integrated skin also wants the penumbra width to drive a scattering tint at shadow edges.
- Tone mapping and skin: with albedo in the 0.2 to 0.6 range and scattering adding red-orange in the terminator, the property that matters is whether mid-range colours are altered. Neutral leaves everything under 0.76 untouched apart from the 0.04 offset and never rotates hue; ACES Filmic compresses and desaturates from well below white and is the operator known for pushing saturated reds and oranges toward yellow **[R]**; AgX desaturates more and holds hue better than ACES **[R]**. Since the game applies its own `finish()` tone step, the useful conclusion is a test, not a pick: render the face under the game's sun at noon and at sunset through the project's curve and through `neutralToneMapping`, and compare against the reference photograph; hue shifts of skin in highlights point at the curve, not the shader.
- The skin shader must output linear scene-referred values and leave all tone and colour-space work to the final step; a screen-space scattering pass, if added, has to run before that step.

### Gaps
- No source compares tone mappers on skin tones specifically (the planned search did not run); the statements about ACES and AgX on skin are from memory and from product-colour documentation.
- No published cost for PMREM regeneration, `LightProbeGrid` updates or PCSS in a browser on a named device.
- The project's own `finish()` curve was not examined in this research.
- Area-light or image-based soft shadows for faces (for example shadowed environment lighting through bent normals) were not researched.

## 8. Existing browser-rendered realistic humans as of November 2026

### Takeaway
The earlier finding still holds in its strict form: no open, locally rendered WebGPU head was found that combines diffusion-profile skin, refractive eyes and hair at a quality comparable to native digital humans. What changed in 2026 is the neighbourhood: MetaHumans now run locally in three.js through open GLB pipelines (WebGL, standard PBR, no scattering, tested on an iPhone X); a three.js pull request renders the Lee Perry-Smith head with screen-space diffusion; two open WebGPU projects draw heads with strand hair; and the avatar platforms that fed browser apps (Ready Player Me, Union Avatars) have shut down. Gaussian-splat avatars are the other locally rendered route, with one measured figure of about 8 ms per avatar.

### Cited Findings

**Mesh-based humans rendered locally**

### Inferences
- The state of the art for an open, locally rendered, mesh-based head in a browser in late 2026 is the sum of separate pieces that nobody has combined: scanned or MetaHuman geometry with 51 blendshapes (WebGL, PBR), a screen-space diffusion pass (three.js PR, WebGPU), strand hair (hair-fur-sim, WebGPU), and nothing for eyes. A head that does pre-integrated scattering, two specular lobes, wrinkle maps, an analytic refractive eye and strand or card hair in one WebGPU forward pass would be ahead of every open example found, on technique if not yet on asset quality.
- The MetaHuman pipelines are the best available yardstick for "what a phone tolerates" in practice: 1K textures, cards for hair, 51 morph targets on a face mesh, standard PBR, 40 MB download, an eight-year-old iPhone. Everything beyond that on phones is unproven by any public example.
- Splat avatars reproduce captured appearance (skin scattering and hair included, baked in) with little shading cost, but they are view-dependent captures: relighting under a game's sun and sky, close-up eye behaviour and art-directed faces are their weak points, and the WebGPU platform that supports animated avatars warns against most Macs. They are an alternative product, not a component for a procedurally built, relit head.
- The disappearance of Ready Player Me and Union Avatars removes the default "good enough" browser avatar source; projects now either build characters themselves, as this one does, or adapt MetaHumans under Epic's licence. MetaHuman licensing was broadened in 2025 to allow use outside Unreal Engine **[R]**; the terms were not re-read here.

### Gaps
- No frame rates or device classes are published for any of the mesh-based heads above.
- Soul Machines, Didimo, Avaturn's renderer, Genies, Needle Engine, PlayCanvas showcase pieces and Unity-WebGPU digital-human samples were not researched (search budget exhausted); Sketchfab could not be opened.
- The Gaussian-avatar papers (Visionary, Instant Skinned Gaussian Avatars, the CVPR 2026 mobile paper, WebSplatter) could not be opened, so their measured numbers are absent apart from one snippet.
- The MetaHuman licence terms that govern running exported characters in a third-party web renderer were not verified.
- A GitHub search is not a census: closed-source commercial work (agency showcases, product configurators with human models) would not appear in it.

## 9. Performance measurement and what is known about per-frame cost

### Takeaway
There is still no published per-frame cost of a skin shader or a large skinned mesh in three.js WebGPU on an integrated GPU or a phone; the usable device-named numbers are for hair (about 6 ms for 1.29 million ribbon particles on an Apple Silicon Mac; under 10 ms a frame for software-rasterized hair on an RTX 3060) and for three.js's per-object CPU overhead. GPU time can be measured in the browser with the optional `timestamp-query` feature, quantized to 100 µs unless Chrome's developer flag is set, and r187's timestamp handling for resumed, layered and nested passes was still being fixed in November 2026.

### Cited Findings

**How to measure**
- **[S]** `timestamp-query` is an optional WebGPU feature; the spec says timestamp values are implementation-defined, may occasionally reset ("unexpected values such as negative deltas ... can safely be discarded"), and "to mitigate security and privacy concerns, their precision must be reduced" by the *coarsen time* algorithm with cross-origin isolation never applying. — [WebGPU spec source, timestamp queries](https://github.com/gpuweb/gpuweb/blob/main/spec/index.bs)
- **[S]** WebGPU Fundamentals: "By default the 'timestamp-query' time values are quantized to 100µ seconds. In Chrome, if you enable `enable-webgpu-developer-features` in about:flags, the time values may not be quantized"; the feature must be requested at device creation and checked with `adapter.features.has( 'timestamp-query' )`. It also warns that "timestamp-query results are not a good measure of performance" in isolation: a compute mip generator that the queries reported as five times faster than a render-pass version did not win a throughput test. Dawn exposes the quantization as the `timestamp_quantization` toggle. — [webgpufundamentals, webgpu-timing.md](https://github.com/webgpu/webgpufundamentals/blob/main/webgpu/lessons/webgpu-timing.md), [Dawn Toggles.cpp](https://github.com/google/dawn/blob/main/src/dawn/native/Toggles.cpp)
- **[P]** WebKit adds `timestamp-query` only when the Metal device has a timestamp counter set, so it cannot be assumed on iPhones; three.js enables timing with `new WebGPURenderer( { trackTimestamp: true } )` when the feature exists, returns results through `renderer.resolveTimestampsAsync( 'render' | 'compute' )`, and r187's `Inspector` addon graphs CPU and GPU time. — [WebKit HardwareCapabilities.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/HardwareCapabilities.mm), [WebGPUBackend.js L298](https://github.com/mrdoob/three.js/blob/r187/src/renderers/webgpu/WebGPUBackend.js#L298), [Renderer.js L3369-L3373](https://github.com/mrdoob/three.js/blob/r187/src/renderers/common/Renderer.js#L3369-L3373)
- **[S]** Timestamp fixes are landing around r187: "WebGPURenderer: Fix timestamp query limits" (#34236, August 2026) and "TimestampQueryPool: Clear timestamps Map on query resolution and dispose" (#34243) predate it; "WebGPUBackend: Fix timestamp queries of resumed and layered render passes" (#35339, 4 November 2026) and "WebGPUBackend: Fix nested timestamps" (#35414, 9 November 2026) were opened after the r187 release, so r187's per-pass GPU times can be wrong for those pass types. — [PR #34236](https://github.com/mrdoob/three.js/pull/34236), [PR #35339](https://github.com/mrdoob/three.js/pull/35339), [PR #35414](https://github.com/mrdoob/three.js/pull/35414)
- **[S]** How 2026 projects measure in practice: HairyMess shows GPU timestamp queries in its HUD "when available" and uses them to rescale strand count when a frame exceeds about 14 ms; spark.js offers `useTimestampQueries` and notes it "requires `timestamp-query` feature and enabling unsafe WebGPU features in the browser"; DERMIS's stress test "waits for GPU completion" and reports "render milliseconds [that] include CPU submission and GPU queue completion", with the caveat "FPS includes browser frame scheduling"; Render-Tech-Lab (three.js TSL research bench) records CPU frame, GPU frame, submit time, P95, P99 and first-frame-minus-steady-state (pipeline compilation stalls), rejects software adapters, and falls back to queue-completion timing. The Frostbitten hair author profiled "manually, by commenting out code". — [hairymess_web README](https://github.com/patrickFuerst/hairymess_web/blob/main/README.md), [spark.js API.md](https://github.com/ludicon/spark.js/blob/main/API.md), [dermis-cuda README](https://github.com/SamG-Coder/dermis-cuda/blob/main/README.md), [Render-Tech-Lab README](https://github.com/pasquelin/Render-Tech-Lab/blob/main/README.md), [frostbitten-hair-webgpu README](https://github.com/Scthe/frostbitten-hair-webgpu/blob/master/README.md)

**Measured numbers that exist**
- **[S]** Hair, Apple Silicon (chip unnamed), 1280×769, 4× MSAA: 138 920 particles: simulation 0.6 to 0.9 ms, ribbons 2 to 3 ms; 1 289 616 particles: simulation about 2 ms, ribbons about 6 ms, lines about 1.8 ms. — [hairymess_web README](https://github.com/patrickFuerst/hairymess_web/blob/main/README.md)
- **[S]** Hair, RTX 3060: software-rasterized strands with OIT, "<10ms (total frame time)"; the fine pass alone about 3.3 ms after optimization; halving the tile size from 16 to 8 pixels took that pass from about 19 ms to about 10 ms. — [frostbitten-hair-webgpu README](https://github.com/Scthe/frostbitten-hair-webgpu/blob/master/README.md)
- **[P]** three.js renderer overhead: 20 000 separate meshes ran at about 15 fps in `WebGPURenderer` against 60 fps in `WebGLRenderer` on an M1 Pro (r173); 10 000 unique node materials took about 2 100 ms to initialize against 131 ms; on r186 the WebGL 2 back end's `render()` was 31% slower than `WebGLRenderer` for about 380 draws. These scale with object and material count, not triangles. — [three.js issue #30560](https://github.com/mrdoob/three.js/issues/30560), [three.js issue #33821](https://github.com/mrdoob/three.js/issues/33821)
- **[X]** One animatable Gaussian avatar: about 7.5 to 8.0 ms in the Visionary benchmark (device unknown). — [Visionary paper](https://arxiv.org/abs/2512.08478)
- **[S]** Macs as a class: the Visionary authors do not recommend macOS below an M4 Max for heavy splat workloads. — [visionary README](https://github.com/Visionary-Laboratory/visionary/blob/main/README.md)

### Inferences
- A measurement plan that the sources support: (1) Chrome on the reference laptop with `trackTimestamp: true` and the `enable-webgpu-developer-features` flag for unquantized per-pass GPU time, checked against a throughput test (raise the number of heads or the resolution until the frame rate drops) because timestamp deltas alone mislead, most of all on tile-based GPUs; (2) on iPhones, where `timestamp-query` may be absent, measure with frame-time percentiles over a fixed camera path plus `device.queue.onSubmittedWorkDone()` latency, and use Safari's Web Inspector and Instruments on a tethered device for GPU time; (3) record first-frame-minus-steady-state separately, since a large hand-written TSL fragment function is a pipeline-compilation cost before it is a per-frame cost; (4) build an A/B switch per feature (noise against baked maps, each specular lobe, scattering LUT, wrinkle blend, shadow filter taps), since no published breakdown exists to rely on.
- With 100 µs quantization, features worth less than a few tenths of a millisecond cannot be resolved from single frames; average over hundreds of frames or use the developer flag.
- Until r188 or later is adopted, per-pass GPU numbers from r187's Inspector should be cross-checked for passes that are resumed, layered (array targets, cascades) or nested.
- The fragment-side budget remains the dominant unknown for a portrait: a face filling a third of a 2560×1440 frame is about 1.2 million shaded pixels **[A]**, and every per-pixel choice in sections 1 to 7 (three or four map samples, one LUT sample, two lobes, one to three wrinkle samples, SH plus one or two PMREM lookups, 5 to 32 shadow taps) multiplies by that.

### Gaps
- No published millisecond cost for any skin shader, any 200 000-triangle skinned mesh, or any morph-target count in three.js WebGPU, on any integrated GPU or phone. The project has to produce these numbers itself.
- Which browsers and devices expose `timestamp-query` in November 2026 (Chrome on Android, Safari 26 on iPhone and Mac, Firefox) could not be confirmed; the planned search did not run and Chrome's and WebKit's documentation could not be opened.
- The bodies of the timestamp pull requests could not be read, so what exactly was wrong in r187 is known only from their titles.
- No source measures tile-memory or bandwidth cost of extra MRT attachments on Apple or Android GPUs in a browser.
