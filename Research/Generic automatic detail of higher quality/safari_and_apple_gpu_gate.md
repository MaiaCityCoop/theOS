## 1. WebKit's own posts and release notes on WebGPU: what shipped in Safari 26 and each later version on macOS and iOS; known limits; the features list; buffer and binding sizes on iPhones; 64-bit atomics; multi-draw

### Takeaway
Safari's WebGPU (shipped 15 September 2025 in Safari 26.0 on macOS, iOS, iPadOS and visionOS) has everything a hardware-rasterised, GPU-driven cluster renderer needs (compute, storage buffers up to hundreds of megabytes, 32-bit atomics, `drawIndirect` and `drawIndexedIndirect`, `indirect-first-instance`, `timestamp-query`, `shader-f16`) and nothing beyond it: no multi-draw, no 64-bit atomics, no mesh shaders, in any shipped version or on WebKit's `main`. What decides the cost is how WebKit implements indirect and indexed draws, which only its source shows: a draw whose pipeline has **no vertex buffers** goes straight to Metal, while a draw with vertex buffers gets an extra GPU validation step per draw, a memory barrier, and on M1-class Macs a split of the render pass after 512 barriers ("severe performance penalty" in WebKit's own log line). Several indirect-draw and frame-pacing bugs were fixed only in Safari 27.2 (26 October 2026), in the 27.3 beta (3 November 2026) or so far only in Safari Technology Preview.

How WebKit executes indirect and indexed draws (the part that decides cost)
- `drawIndirect`: WebKit computes the smallest element count over the vertex buffers the pipeline requires. If the pipeline requires none ("`if (minVertexCount == RenderBundleEncoder::invalidVertexInstanceCount && minInstanceCount == RenderBundleEncoder::invalidVertexInstanceCount) return std::make_pair(indirectBuffer.buffer(), indirectOffset);`") the call goes straight to Metal's `drawPrimitives:indirectBuffer:`. Otherwise WebKit first draws one point with an internal "clamp" vertex shader that reads the arguments, clamps `vertexCount` and `instanceCount` to the vertex buffers' sizes and writes them to a scratch buffer, emits a memory barrier, and draws from the scratch buffer. The same early return and the same clamp exist on the Safari 26.0 and 27.x branches — [RenderPassEncoder.mm, main](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/RenderPassEncoder.mm); [safari-7625-branch](https://github.com/WebKit/WebKit/blob/safari-7625-branch/Source/WebGPU/WebGPU/RenderPassEncoder.mm); [safari-7622-branch](https://github.com/WebKit/WebKit/blob/safari-7622-branch/Source/WebGPU/WebGPU/RenderPassEncoder.mm) (read directly)
- `drawIndexedIndirect` with vertex buffers: two scratch buffers, a point draw to clamp the arguments, a barrier, then a second internal draw of **one point per index** whose vertex shader reads each index and, if any index (plus base vertex) is outside the vertex buffers, zeroes the whole draw and sets a "lost or out-of-bounds read" flag; then another barrier. Without vertex buffers the function returns at its first line and the draw goes straight to Metal — [RenderPassEncoder.mm, main](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/RenderPassEncoder.mm); [Device.mm, main](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/Device.mm) (read directly)
- Plain `drawIndexed` with vertex buffers is validated the same way (one point per index) unless a cached result for that index range is still valid; the cache is invalidated when the buffer is bound as writable storage ("`if (resourceUsage.contains(BindGroupEntryUsage::Storage)) buffer->indirectBufferInvalidated(m_parentEncoder);`") — [RenderPassEncoder.mm, main](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/RenderPassEncoder.mm) (read directly)
- Barriers are counted per render pass against a per-device limit; when the limit is reached the pass is ended and restarted with load actions: "`WTFLogAlways("WebGPU: Splitting render pass on ARM64 - severe performance penalty");`". The limit is unlimited by default, **512 on a Mac whose GPU is below the Apple8 family** ("`else if (![device supportsFamily:MTLGPUFamilyApple8]) baseCapabilities.memoryBarrierLimit = 512;`"), and 0 on Macs without an Apple-family GPU — [RenderPassEncoder.mm, main](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/RenderPassEncoder.mm); [HardwareCapabilities.mm, main](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/HardwareCapabilities.mm) (read directly)
- Which chips are which family: A14 and M1 are Apple7; A15, A16 and M2 are Apple8; A17 Pro, A18, M3 and M4 are Apple9; A19 and M5 are Apple10; M6 is Apple11 — [Metal Feature Set Tables, dated 23 October 2026](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) (read directly)
- On the Safari 27.0 to 27.2 branch the clamped arguments of every indirect draw from one buffer were written to a single scratch slot per buffer; `main` allocates one per draw and explains why: "Scratch must be per-draw, not one slot shared by every draw against this Buffer. ... nothing can order draw N's fetch against draw N+1's clamp store into the same slot" — [RenderPassEncoder.mm, safari-7625-branch](https://github.com/WebKit/WebKit/blob/safari-7625-branch/Source/WebGPU/WebGPU/RenderPassEncoder.mm); [main](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/RenderPassEncoder.mm) (read directly)
- In render bundles, indexed indirect draws are always clamped, with or without vertex buffers ("`bool clamps = data.isIndexed || !(...)`") — [RenderPassEncoder.mm, main](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/RenderPassEncoder.mm) (read directly)

Apple's own performance guidance for WebGPU in Safari (WWDC25, by the Safari engineer who wrote the implementation)
- "Updating buffers with index and indirect usage modes can be especially expensive since validation needs to be performed prior to using the buffer again. Those buffers index either directly or indirectly into vertex buffers, and WebGPU must ensure all the offsets into these buffers are within bounds before any draw commands execute. Only update these type of buffers when needed. This also applies to using a buffer in a bind group with write or read/write access. ... prefer read-only access unless you are writing through the resource in the shader, especially if the resource is an index or indirect buffer." — [Unlock GPU computing with WebGPU, WWDC25 session 236](https://developer.apple.com/videos/play/wwdc2025/236/) (read directly)
- "Command buffer boundaries require synchronization between high-speed on-chip memory and unified on-device memory. If possible, use a single command buffer per update loop ... a general good rule of thumb is that as few command buffers as possible should be used"; "passes don't require synchronization with unified memory. They still consume substantial memory bandwidth, depending on the render target and compute dispatch sizes. So it's best to use as few as possible" — [WWDC25 session 236](https://developer.apple.com/videos/play/wwdc2025/236/) (read directly)
- "Under the hood, render bundles map to Metal's indirect command buffers"; with bundles "validation happens once, when the bundle is created, instead of every time it runs"; bind groups "are implemented with Metal argument buffers, so creating a bind group also creates a new MTLBuffer" — [WWDC25 session 236](https://developer.apple.com/videos/play/wwdc2025/236/) (read directly)
- "On iOS and visionOS specifically, storing data in f16 or compressed formats can really help you avoid getting your program terminated due to memory pressure"; `shader-f16` is "supported on all Apple devices"; "Most calls are one-to-one mapping with Metal framework calls" — [WWDC25 session 236](https://developer.apple.com/videos/play/wwdc2025/236/) (read directly)

### Inferences
- A GPU-driven drawer in Safari should issue its indirect draws from pipelines with **zero vertex buffers** (all vertex data pulled from storage buffers by `vertex_index` and `instance_index`). Then, in every Safari from 26.0 on, each `drawIndirect` or `drawIndexedIndirect` is one Metal call with no validation pass, no scratch buffer and no barrier. This is read from the source, not measured.
- With vertex buffers bound, each indirect draw costs an extra point draw and a barrier (two of each when indexed, plus a vertex-shader run per index), and on an **M1 Mac** (Apple7, below Apple8) a render pass that accumulates 512 barriers is split and its attachments stored and reloaded. More than about 500 clamped non-indexed, or about 250 clamped indexed, indirect draws in one pass would trigger it. M2 and later Macs, and iPhones, have no such limit in the source.
- In Safari 27.0 to 27.2, several indirect draws in one pass from the same indirect buffer through the clamp path share one scratch slot; that is very likely the "GPU hang ... repeated `drawIndirect()` ... using the same buffer" fixed in the 27.3 beta. Zero-vertex-buffer pipelines never enter that path.
- A compute-written index buffer used together with vertex buffers is the worst case in Safari: it is re-validated with one vertex-shader run per index every time it has been bound writable. Used with zero vertex buffers it costs nothing extra.
- Of the fixes still waiting in Technology Preview, "permanently dropping to a fraction of the display refresh rate after a few slow frames" matters most for a 60-frames gate: in shipping Safari (27.2 and earlier, if the bug is present there) a few slow frames may lock the canvas to a lower rate, so a governor that reacts after the fact is not enough; the frame must not go over budget in the first place.
- Buffer sizes are not the constraint people assume: on an iPhone with Safari 26.2 or later the adapter allows a single storage binding of 256 MiB to 1 GiB (about 683 MiB if `maxBufferLength` is 2 GiB, as in the one field report); on a Mac at least 1 GiB (if the device allows it) and at most 2,147,483,644 bytes. But it must be requested: a device created without `requiredLimits` has 128 MiB bindings, 256 MiB buffers and 8 storage buffers per stage.
- When Safari implements `atomic-vec2u-min-max`, Metal's table says it can exist on M2 and later Macs and on iPhones from the A17 Pro (iPhone 15 Pro) on, never on M1 Macs and never on A14 to A16 iPhones. A design that needs 64-bit atomics would exclude the M1, the machine the game is measured on.

## 3. Apple's developer documentation and WWDC material on tile-based deferred rendering: small triangles, vertex buffer memory per frame, partial renders, hidden-surface removal with alpha test and discard (leaf cards), advice for geometry-heavy scenes; published triangle-throughput figures for Apple GPUs (M1 to M5, A-series)

### Takeaway
Apple describes the mechanism precisely and gives almost no numbers. Every triangle submitted in a render pass is vertex-shaded and binned into per-tile lists in system memory (the "tiled vertex buffer") before any pixel is shaded; if that buffer fills, the pass is split ("partial render"). Opaque pixels are then shaded exactly once whatever the draw order; pixels from shaders that `discard` (Apple names "alpha tested foliage") are a second class that must be drawn after all opaque geometry, where draw order matters and overdraw is real. Apple publishes no triangles-per-second figure for any chip; its only written advice on triangle size is one line: "Render fewer very small triangles, especially if you're applying MSAA as well."

### Cited Findings

The pipeline and where geometry goes
- "In the Tiling Phase, for the entire render pass, the GPU will split the viewport into a list of tiles, shade all of the vertices and, finally, bin the transformed primitives into a list of tiles." "The Tiled Vertex Buffer stores the Tiling phase output, which includes the post-transform vertex data, as well as other internal data. This data structure is mostly opaque to you. But it may cause a Partial Render if full. A Partial Render is when the GPU splits the render pass in order to flush the contents of that buffer. So the takeaway is for you to know that the Tiled Vertex Buffer exists, but don't worry too much over it." — [Harness Apple GPUs with Metal, WWDC20 session 10602](https://developer.apple.com/videos/play/wwdc2020/10602/) (read directly)
- "The Apple GPU first processes all the geometry of a render pass in the vertex stage. It transforms and bins your geometry into screen-aligned, tiled vertex buffers that are then passed to the fragment stage. ... The GPU rasterizes all primitives in a tile before shading any pixels using fast, on-chip, tile memory." — [Optimize Metal Performance for Apple silicon Macs, WWDC20 session 10632](https://developer.apple.com/videos/play/wwdc2020/10632/) (read directly)
- The GPU "does not have video memory. So bandwidth could be a problem if the content has not been tuned"; device memory "will store both Metal resources as well as the output from the tiling phase" — [WWDC20 session 10602](https://developer.apple.com/videos/play/wwdc2020/10602/); [Optimize Metal apps and games with GPU counters, WWDC20 session 10603](https://developer.apple.com/videos/play/wwdc2020/10603/) (read directly)
- Tiles are at most 32 × 32 pixels without MSAA and with 2× MSAA, 32 × 16 with 4× MSAA, on every family from Apple2 to Apple11 — [Metal Feature Set Tables, 23 October 2026](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) (read directly)
- "The vertex stage is usually making heavy use of fixed-function hardware, whereas the fragment stage is a heavy user of math and bandwidth. Completely overlapping them allows us to use all the hardware blocks on the GPU simultaneously." — [Metal 2 on A11 - Overview, tech talk 602](https://developer.apple.com/videos/play/tech-talks/602/) (read directly)

Scheduling: when vertex work is free and when it is not
- "Apple GPUs process all vertices of a render pass before any fragments, so stages from the same pass must execute serially. But vertex processing of the next pass should overlap with fragment processing of the current pass. This even occurs across frame boundaries so often times the vertex cost is almost entirely hidden by fragment processing." — [WWDC20 session 10632](https://developer.apple.com/videos/play/wwdc2020/10632/) (read directly)
- "But now let's take a look at what happens when you make vertex work dependent on fragment work of a previous pass. ... This will reduce your overlap and extend execution time by creating a bubble of inactivity in the vertex stage." "Unnecessary dependencies often involve multiple chains of vertex, fragment and compute. In this example, the vertex stage of Render Pass 1 depends on Compute Pass 1. And Compute Pass 1 in turn depends on the fragment stage of Render Pass 0. All these holes in your GPU activity will again hurt your performance." "Metal only tracks dependencies at the resource level and not the data itself." — [WWDC20 session 10632](https://developer.apple.com/videos/play/wwdc2020/10632/) (read directly)
- "Avoid too many small passes. There's setup time between passes, so having small passes adds latency." "Try overlapping GPU tasks. Apple GPUs run vertex, fragment, and compute tasks in parallel whenever possible." — [Analyzing Apple GPU performance using a visual timeline](https://developer.apple.com/documentation/xcode/analyzing-apple-gpu-performance-using-a-visual-timeline) (read directly). Hidden-surface removal, alpha test, discard
- "HSR allows the GPU to minimize overdraw by keeping track of the frontmost visible layer for each pixel. HSR is both pixel perfect and submission order independent." "In this context, overdraw is the number of fragment shader invocations per pixel, and we want to keep it low. On a scene with non-opaque geometry, overdraw will depend on the HSR efficiency. ... You will want to draw the meshes sorted by visibility state. First, opaque. Second, alpha test, discard or depth feedback. And third, and finally, translucent meshes. You should avoid interleaving opaque and non-opaque meshes and also avoid interleaving opaque meshes with different color attachment write masks." "Notice, though, that if we discard or update the depth, we will need to go back to HSR." — [WWDC20 session 10602](https://developer.apple.com/videos/play/wwdc2020/10602/) (read directly)
- "HSR categorizes fragments based on their visibility. First, we have opaque fragments which always occlude or hide everything beneath them. Then we have feedback fragments, which are generated by fragment functions containing a discard statement or that return of depth value. **Alpha tested foliage falls into this category.** And finally we have translucent fragments ... To maximize HSR efficiency draw each type of fragment together and then the order shown. First opaque, then feedback, and finally translucent objects. **Draw ordering within each category only matters for feedback and translucent fragments.** Opaque draws can be in any order" — [WWDC20 session 10632](https://developer.apple.com/videos/play/wwdc2020/10632/) (read directly)
- "HSR is both pixel perfect and submission order independent **for opaque meshes**." "Overdraw, in this context, is the ratio between Fragment Shader invocations and Pixels Stored." - Depth pre-pass: "if you only perform a depth pre-pass for performance, then hidden surface removal serves the same purpose on Apple GPUs. When HSR is maximized, it can reject hidden fragments as well as depth pre-passes can, but without any additional costs. - "A11 and later Apple GPUs also improve fragment discard performance"; "We also made significant improvement over the performance of feedback operations. - On a tile-based renderer "blending and alpha testing [happen] without ever having to load from the full color buffer in memory"; "This architecture allows for alpha tests and blending operation to be performed by the shader core instead of fixed function hardware." — [Bring your Metal app to Apple silicon Macs, WWDC20 session 10631](https://developer.apple.com/videos/play/wwdc2020/10631/) (read directly; the transcript is machine-made and garbled in places)

### Inferences
- The cost of a submitted triangle on an Apple GPU has three parts that hidden-surface removal does not remove: one or more vertex-shader runs, binning into every 32 × 32 tile it touches, and its post-transform data sitting in system memory until the fragment stage reads it back. So the quantity to budget is triangles **submitted after culling**, per pass, and the size of what the vertex stage outputs per vertex (position plus as few varyings as possible). A cluster renderer that selects one pixel of error at a lower internal resolution submits proportionally fewer triangles; that, not overdraw, is its lever on this hardware.
- Apple says partial renders exist and gives no size for the tiled vertex buffer; no page read says at what vertex count it overflows. The only safe reading is that a pass with millions of small triangles can be split, and that each split costs a store and a load of every attachment at the pass's resolution. This is one more reason to keep geometry passes at the internal resolution and attachments few and narrow.
- For opaque geometry a depth pre-pass is wasted work on Apple GPUs (Apple says so); the three.js meshlet pipeline's `depthPrepass` option (section 4) should stay off there.
- Leaf cards are the expensive case by Apple's own classification. An alpha-cut fragment cannot be hidden by a later alpha-cut fragment until its shader has run and discarded or not, so a pixel covered by several layers of cards runs the (at least partial) fragment shader for layers that end up invisible; and "draw ordering ... matters for feedback" means roughly front-to-back submission of the alpha-cut clusters lets depth-written leaves reject what lies behind them. Opaque leaf geometry would be shaded once per pixel regardless of order. Three levers follow, none measured on Apple hardware by any source found: (1) draw all opaque clusters first, then alpha-cut clusters front to back at cluster or tree granularity; (2) make the part of the leaf shader that decides `discard` as cheap as possible and do it first; (3) where the triangle budget allows, replace cards by opaque leaf geometry at near and middle range and by an opaque volume proxy far away, so that most foliage pixels are opaque.
- The GPU-driven chain "depth of frame N-1, then depth pyramid, then cull compute, then draw of frame N" is exactly the vertex-depends-on-compute-depends-on-fragment chain Apple warns about. It cannot be removed, but it can be kept short: build the pyramid from a depth target that is finished early in the previous frame (before post-processing and upscaling), keep the cull in one compute pass, and avoid sharing one buffer or texture between unrelated passes (Metal tracks dependencies per resource).
- Apple's "5,000,000 vertices, 16 ms" is an example in prose. It does say what Apple considers a plausible vertex-bound frame: millions of vertex runs with matrix-heavy 32-bit math cost on the order of the whole frame, and the named remedies are fewer vertices and half-precision math.

### Gaps
- No Apple figure for the tiled vertex buffer's capacity, for the cost of a partial render, or for triangle or vertex throughput of any chip.
- No Apple statement quantifying alpha-test overdraw or small-triangle cost beyond the sentences quoted.
- Apple's developer forum threads on tile memory and on a WebGPU process crash on iPhone (found by search) sit behind a bot check and could not be read.
- A reverse-engineering write-up on the M1's parameter buffer and partial renders (Alyssa Rosenzweig, "The Apple GPU and the Impossible Bug") was found by search only; its host is not reachable — [rosenzweig.io](https://rosenzweig.io/blog/asahi-gpu-part-5.html) (search extract: partial renders happen when there is "too much per-vertex data" and "hurt performance")

## 4. three.js: its WebGPU renderer's documentation for indirect drawing, compute, storage buffers and BatchedMesh; forum threads on virtual geometry and meshlets, including three-virtual-geometry; the library's performance guide and issues

### Takeaway

The meshlet pipelines new in r187 (absent from r184, r185 and r186: those tags return "not found" for the files)
- "A GPU-driven drawing pipeline that renders compatible meshes as meshlets. Geometries are processed once into clusters (meshlets) of 64 triangles with a chain of simplified levels of detail. Every frame, compute shaders select the level of detail per object and cull the objects and clusters against the frustum, and the visible clusters of all objects sharing geometry and material are drawn in one indirect draw through the hardware rasterizer." "Supported are opaque and alpha-tested meshes using front side rendering whose material nodes don't change the geometry, the coverage or the output of the draw. All other objects ... are drawn by the regular pipeline." "Objects are culled on the GPU, but the CPU still traverses the scene and uploads the transforms every frame" unless they sit in a static `BundleGroup`. "This class is experimental and its interface might change." Enabled with `renderer.drawingPipeline = new MeshletDrawingPipeline()` — [three.js docs: MeshletDrawingPipeline](https://threejs.org/docs/pages/MeshletDrawingPipeline.html); [source at r187](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/pipelines/MeshletDrawingPipeline.js) (read directly)
- Options: `lodThreshold = 1` ("The projected error in pixels below which a simpler level of detail is selected"), `shadowLodThreshold = 1` (in shadow-map texels), `minScreenRadius`, `coarseScreenRadius`, `occlusionCulling = true` ("The clusters visible in the last frame are rendered into a depth buffer first, the other clusters are tested against its hierarchical depth. Shadow passes are not occlusion culled"), `depthPrepass = false` ("Reduces the overdraw of expensive materials at the cost of drawing the clusters twice") — [source at r187](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/pipelines/MeshletDrawingPipeline.js) (read directly)
- How it draws: the indirect arguments written by compute are `[ MESHLET_SIZE * 3, min( visible clusters, queue capacity ), 0, 0 ]`, that is a non-indexed, instanced draw of 192 vertices per visible cluster; the vertex stage pulls the triangle by `workItem.y + workItem.w * 64 + vertexIndex / 3`; "Meshlets are padded with degenerate triangles to this size"; the reported triangle count "include[s] the degenerate triangles which pad the clusters". The draw geometry carries real placeholder vertex buffers: `position`, `normal` (and `tangent`) all point at one shared `Float32BufferAttribute` of `PULLED_VERTICES = 65536 * 3` vertices — [source at r187](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/pipelines/MeshletDrawingPipeline.js); [MeshletGeometryUtils.js at r187](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/utils/MeshletGeometryUtils.js) (read directly)
- How levels are made: meshoptimizer's clusterizer and simplifier; six levels with target ratios 1.0, 0.55, 0.25, 0.1, 0.04, 0.015 and error limits 0, 0.004, 0.015, 0.05, 0.14, 0.3, flags `RegularizeLight` or `Regularize`, `Permissive`, `Prune`; "a level which removes less than 15% of the triangles of the previous level is simplified again without preserving the topology"; "Identical vertices are welded first and all levels index the same vertices" — [MeshletGeometryUtils.js at r187](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/utils/MeshletGeometryUtils.js) (read directly)
- Capacity constants: `MAX_INSTANCES = 1 << 24`; "the world matrices of the objects and of the last frame use 128 bytes per object", so objects per render list are limited by `min( maxStorageBufferBindingSize, maxBufferSize ) / 128` (about 1.05 million at the default 128 MiB); cluster budget `CLUSTERS_PER_OBJECT = 8`, at least `1 << 22` clusters; culling runs "one thread per cluster of the visible objects" in workgroups of 64 — [source at r187](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/pipelines/MeshletDrawingPipeline.js) (read directly)
- `VisibilityBufferDrawingPipeline`: "small triangles in software by a compute shader, large triangles by the hardware rasterizer. A resolve pass shades the visibility buffer with the material of the meshes ... with analytic derivatives". `maxRasterSize = 8`: "The maximum screen-space size in pixels of triangles rasterized in software." The compute rasteriser runs "one thread per triangle of a cluster" and writes two 32-bit atomics per pixel, "the depth occupies the high bits, so atomicMax resolves the depth test and the payload together": 16 bits of depth with a 16-bit triangle index, and 15 bits of depth with a 17-bit instance index (`TRIANGLE_INDEX_BITS = 16`, `INSTANCE_INDEX_BITS = 17`). Limits it states: "The visibility buffer stores the triangle in 16 bits, so only the levels of detail whose triangles fit into this range are used"; "render calls with MRT, like the velocity of TRAA, draw all clusters with the hardware pipeline"; "the software rasterizer doesn't discard fragments"; "the software rasterizer doesn't evaluate the alpha of alpha-tested materials"; at most 65,536 hardware-queued triangles per batch — [three.js docs: VisibilityBufferDrawingPipeline](https://threejs.org/docs/pages/VisibilityBufferDrawingPipeline.html); [source at r187](https://github.com/mrdoob/three.js/blob/r187/examples/jsm/pipelines/VisibilityBufferDrawingPipeline.js) (read directly)
- The core hook is new too: `renderer.drawingPipeline` ("The default is a `StandardDrawingPipeline`. This property is experimental"), whose subclasses "implement other strategies like GPU-driven rendering" — [StandardDrawingPipeline.js at r187](https://github.com/mrdoob/three.js/blob/r187/src/renderers/common/StandardDrawingPipeline.js) (read directly)
- Official examples: `webgpu_meshlets`, `webgpu_meshlets_city` (which limits the pixel ratio: "`renderer.setPixelRatio( Math.min( window.devicePixelRatio, 1.5 ) ); // limit the pixel ratio to improve performance on high-DPI displays`"), `webgpu_meshlets_ibl`, `webgpu_meshlets_instanced` ("Instanced Lucy statues of 100k triangles each, culled and simplified per cluster on the GPU"), `webgpu_meshlets_materials`, `webgpu_meshlets_meshes`. ### Inferences
- three.js r187's own meshlet pipeline is a per-object level chain with cluster-level culling, not a cluster hierarchy with per-cluster level choice: "select the level of detail per object", six fixed ratios. It will pop between levels and cannot refine part of a large object. As a model for "raising quality" it is the simple end; as a source of working TSL code for cluster culling, work queues, two-phase occlusion and a 32-bit compute rasteriser inside three.js's material system, it is the most relevant thing published, and it is in the game's own `node_modules`.
- Both open pipelines put placeholder **vertex buffers** on their indirect draws (three.js r187: 196,608 placeholder vertices; three-virtual-geometry: one placeholder vertex). If three.js binds them (whether it does depends on whether the generated shader still references the attributes, which I did not trace), then in Safari: (a) every indirect draw takes WebKit's clamp path, with the 512-barrier pass split on M1 Macs and, up to Safari 27.2, the shared-scratch hazard for several draws from one argument buffer; (b) three-virtual-geometry's indexed draws would additionally be validated with one vertex-shader run per index, and because its index values are payload far larger than its one-vertex placeholder buffer, WebKit's index check ("zero the draw and flag out-of-bounds") could reject the draw outright. Nobody has reported testing either in Safari. A drawer that binds no vertex buffer at all avoids every one of these.
- The r187 meshlet draw is non-indexed: 192 vertex-shader runs per cluster of at most 64 triangles, including the padding triangles. three-virtual-geometry's draw is indexed (about 0.6 to 1 run per triangle, 128-triangle clusters averaging about 111 triangles in its benchmark: 6,794,420 triangles in 61,253 meshlets). On a vertex-bound Apple GPU that difference is the first thing to measure.
- three.js submits one command buffer per `renderer.compute()` call and per render pass, against Apple's advice of one per frame. A culling stage made of several separate `compute()` calls multiplies command buffers; passing all compute nodes of a stage in one call keeps them in one pass and one buffer.
- With many separate draw calls three.js's WebGPU renderer is CPU-bound (its maintainers say so); a cluster renderer inside three.js must stay at a handful of draws per pass, which the GPU-driven shape gives anyway.

### Takeaway
There are four published measurements of dense-geometry WebGPU on Apple GPUs, all by the authors of the software, none controlled, none of a cluster hierarchy in Safari: three-virtual-geometry on an M4 Pro in Chrome (6.5 to 9 million triangles plus shadows at 100 to 230 frames a second), a three.js r187 forest on a base M1 (30 to 35 at 1080p) and an iPhone 16 Pro (40 to 50), the Shade engine on an M1 Pro (32 at full resolution, 47 at 60% internal), and one research paper that ran the same WebGPU workload in Chrome and Safari on one Mac (Safari 8% slower overall, about 30% slower in its compute stage) and on an iPhone 15 Pro Max. Nobody publishes triangle throughput for an iPhone in Safari, and nobody has measured alpha-cut foliage on an Apple GPU; what exists on foliage is Epic's general statement that masked cards cost nearly as much per masked-out pixel as per drawn one.

The traditional card approach (many elements are represented with a single card) with Nanite can be slower than non-Nanite. ... **Masked-out pixels cost nearly as much as drawn pixels.** Geometry foliage has shown to be faster with Nanite than card approaches, both Nanite cards and non-Nanite cards. It also looks better." "Dense forests ... will render much slower than the same scene with all meshes replaced with solid shapes of the same triangle count." — [Working with Nanite-Enabled Content (UE 5.9 documentation)](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-naniteenabled-content) (read directly)
- Epic, why: "Aggregate geometry ... breaks Nanite's level of detail and occlusion culling techniques"; "Geometry that is filled with holes — and worse yet, layers upon layers of geometry filled with holes — causes excessive overdraw because many depth layers need to build up before that area on the screen will block anything behind it. One way to think about this is to consider an 8x8 pixel region on screen and how many depth layers need to be drawn before every pixel is filled." — [Working with Nanite-Enabled Content](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-naniteenabled-content) (read directly)
- Epic's newer answer: "Alpha Masking: Nanite doesn't work well with it since it introduces a lot of overdraw in addition to having to execute a potentially expensive mask function"; instead, modelled leaves as instanced "assemblies", and far away "Nanite Voxels ... near pixel-sized aggregate voxels"; "it will switch to voxels if doing so would result in lower error than using triangles"; voxel clusters "are sorted into depth buckets, and rasterized from front to back to gain some benefits of early Z testing" — [Nanite Foliage (UE 5.9 documentation, experimental)](https://dev.epicgames.com/documentation/en-us/unreal-engine/nanite-foliage) (read directly)
- Epic on vertex sharing: "Ideally, the number of vertices for a mesh should be less than the number of triangles it has. ... more vertices means more data to store. It also means more vertex transform work, and ratios higher than 2:1 fall down some slow rendering paths." — [Working with Nanite-Enabled Content](https://dev.epicgames.com/documentation/en-us/unreal-engine/working-with-naniteenabled-content) (read directly)
- One developer's blog reports that on Apple silicon forward shading through three.js's TSL pipeline "matched or beat" a hand-built visibility buffer for alpha-tested foliage (search extract; the page could not be opened) — [cinevva blog, 6 May 2026](https://app.cinevva.com/blog/2026-05-06-open-world-browser-part-21-visibility-buffer)

## 6. How others reach a full-resolution picture within a frame budget: rendering inside at fewer pixels and building the screen's picture over time; upscalers available to WebGPU

### Takeaway
Every renderer of this kind that publishes numbers draws the world at a quarter to a half of the output's pixels and reconstructs the rest over several frames: Nanite's own demo averaged 2496 × 1404 for a 4K output, Epic's temporal upscaler is documented at 1080p in for 4K out at about half the GPU time and warns against going below 50% per axis, Apple's MetalFX is shown at 2× per axis with eight jittered samples per output pixel as the target. MetalFX is not reachable from WebGPU. What a three.js WebGPU application has today is three.js's own `TAAUNode` (since r184, April 2026; example default 0.5 scale) and FSR 1, or its own pass; the one measured data point for this approach on Apple silicon in a browser is Shade's 32 to 47 frames a second on an M1 Pro.

### Inferences
- MetalFX cannot be used from a web page: it is a Metal framework, and neither the WebGPU specification's feature list nor WebKit's 24 features contains an upscaler. The upscale has to be the application's own WGSL pass (or three.js's node), paid for in the same frame.
- The pixel arithmetic for a 4K canvas (8,294,400 pixels): 50% per axis is 2.07 million internal pixels (25%), 60% is 2.99 million (36%), Nanite's 2496 × 1404 is 3.50 million (42%), 67% is 3.72 million (45%). Epic's and Apple's published practice puts the floor at 50% per axis for a 4K output.
- The cluster system's error threshold should be measured in **internal** pixels. One pixel of error at 50% internal scale is two pixels on the canvas and about a quarter of the triangles of a native-4K selection (triangle counts of a per-pixel selection scale with the pixel count; Nanite's slides say it is "mostly scaling with screen resolution"). The upscaler then recovers detail over frames from jitter, which is how Nanite's demo reached a 4K picture with about seven rasterised triangles per internal pixel (25 million rasterised over 3.5 million pixels, derived).
- An upscaler's own cost is at output resolution and does not shrink with the internal scale. three.js's `TAAUNode` at a 4K canvas holds three half-float RGBA targets at output size (3 × 66 MB, about 199 MB, my arithmetic from its declared targets), samples nine taps of the low-resolution colour plus history, lock and depth per output pixel, and copies 66 MB from resolve to history every frame. On a base M1 that pass is likely to cost several milliseconds (estimate, unmeasured), which is why Shade gained only 47% from cutting 64% of the internal pixels.
- Epic's warnings apply with more force to a cluster system that raises geometric detail: sub-pixel triangles at a reduced internal resolution alias and flicker, and thin geometry (leaf cards, grass) is the first to be missed between jitter positions. The detail system and the temporal pass have to be tuned together: a slightly coarser error threshold while the camera moves fast (history is rejected anyway) and one pixel when it rests is the pattern Epic's text implies, not something a source states.
- The user interface and text should be composited at the canvas's own resolution after the upscale (Apple and Epic both say so).

- No source read ports FSR 2 or 3 to WGSL with numbers; whether one exists was not searched.
- Epic's 1.5 ms figure is for consoles; no figure for an Apple GPU.

## 7. From all of it: a reasoned budget. At a 4K canvas (8.3 million pixels) and 60 frames a second, how many triangles and how many vertex-stage runs a frame can plausibly be afforded on an M-series Mac and on a recent iPhone in Safari, and what in a cluster renderer's design matters most for staying inside it

### Takeaway
My estimate, not anyone's measurement: at a 4K canvas a **base M1 or M2 in Safari can afford roughly 2 to 3.5 million submitted triangles a frame over all passes (main view plus shadows) if the world is drawn inside at about 1080p to 1300p and rebuilt to 4K over time**; machines of the M1 Pro or M4 class about twice that, an M4 Pro about 10 million (that one is close to measured, in Chrome). A current Pro iPhone sits in the base-M1 class at its own, much smaller, canvas (about 3 to 4 million pixels) while cool, and its memory, not its GPU, is the first wall. On the weakest Mac the pixel side, not the triangle side, decides whether 60 holds at 4K: native 4K shading does not fit, and the upscale pass itself is the largest unmeasured item. In the design, four things matter most, in this order: internal resolution with a lean temporal upscale; triangles submitted after culling (every one is vertex-shaded and binned whatever is hidden); draws with no vertex buffers and as few passes and command buffers as possible (WebKit's implementation); and keeping alpha-cut pixels few and ordered.

### Cited Findings
These are the measured anchors the estimate rests on.
- M4 Pro, Chrome 154, three-virtual-geometry, indexed 128-triangle clusters, hardware rasteriser, 1 px error, shadows on: 9.0M + 2.1M (shadow) triangles in 6.26 ms at 1080p and 9.70 ms at 4K; 8.4M triangles without shadows and 649,000 visible instances in 5.65 ms at 1080p and 6.51 ms at 4K; CPU 0.1 to 0.3 ms — [three-virtual-geometry performance guide](https://elad12390.github.io/three-virtual-geometry/guide/performance) (read directly; measured by the author; throughput with frames queued)
- Base M1, three.js r187 meshlet pipeline plus conventional leaves and grass, 1080p: 30 to 35 fps; iPhone 16 Pro, "high settings": 40 to 50 fps — [forum: Forest Environment](https://discourse.threejs.org/t/forest-environment-built-with-three-js-and-webgpu/96126) (read directly; measured by the author)
- M1 Pro, Shade, 3456 × 2234 (7.7 million pixels), 267,302 polygons, full post stack: 32 fps native, 47 fps at 60% internal — [forum: Shade, post 158](https://discourse.threejs.org/t/shade-webgpu-graphics/66969/158) (read directly; measured by the author)
- Same WebGPU workload, MacBook Air M4: Safari 68.6 ms against Chrome 63.7 ms; MacBook Pro M1 112.0 ms; iPhone 15 Pro Max in Safari 38.5 ms on a lighter scene — [WebSplatter, arXiv:2602.03207](https://arxiv.org/html/2602.03207v1) (read directly; measured by the authors)

- Apple: "60 fps is about 16 ms ... the CPU and GPU timelines can overlap so each timeline can take up to 16 ms"; its illustrative vertex-bound frame is 5,000,000 vertices in 16 ms of vertex stage — [Improving your game's graphics performance and settings](https://developer.apple.com/documentation/metal/improving-your-games-graphics-performance-and-settings) (read directly)

### Inferences
Everything below is my estimate unless it says "derived".

The frame
- 60 frames a second is 16.7 ms. A browser adds compositing and its own scheduling, and Safari up to 27.2 may not recover its refresh rate after slow frames (section 1), so I would plan the page's GPU work at 11 to 12 ms on the reference machine and treat the rest as margin. That planning number is a judgement, not a measurement.

Pixels first
- Derived: on the M4 Pro, material shading in three-virtual-geometry's demos costs 0.14 to 0.55 ns per added output pixel, 1.2 to 4.6 ms for all of 4K. A base M1 at a third to a quarter of that machine (section 5) would need roughly 4 to 18 ms for native 4K shading alone. So native 4K shading of the world does not fit on a base M1 except with the very cheapest material; at 50% per axis it is 1 to 4.5 ms, at 60% 1.4 to 6.5 ms.
- The upscale to 4K runs at 8.3 million pixels whatever the internal scale. No one has published its cost on an M1 in a browser. From Shade's result (60% internal bought 47% more frames on an M1 Pro) and Epic's 1.5 ms on a console whose GPU is several times a base M1's (recalled), I would reserve 3 to 5 ms for a temporal resolve plus the final copy to the canvas on a base M1 at 4K and treat that as the first thing to measure. If it measures worse, the fallbacks are fewer taps, a half-float history replaced by a packed 32-bit one, or reconstructing at less than 4K and letting a cheap spatial step finish.
- A base M1 driving a real 4K screen is therefore the hardest target in the gate, harder than any iPhone: it has the fewest GPU cores per output pixel. A MacBook's own panel is far smaller (the 14-inch is 3024 × 1964, 5.9 million pixels, recalled; the 16-inch 3456 × 2234 per the Shade post).

Triangles
- Derived geometry rate on the M4 Pro: about 0.5 to 0.65 ns per submitted triangle with indexed clusters (section 5). Scaled by 3.2 to 4: about 1.5 to 2.6 ns per triangle on a base M1 in Chrome; Safari perhaps 10% more on the raster side and more on the compute side (one paper).
- With 11 to 12 ms planned, 3 to 5 ms for the upscale and canvas, and 1 to 4.5 ms for shading at 50% internal scale, about 4 to 6 ms remain for geometry of all passes on a base M1: **about 2 to 3.5 million submitted triangles a frame, main view and shadows together** (4 to 6 ms at 1.5 to 2.6 ns). The game's own measurement (given to me with the task, not checked by me) points the same way: 1.5 million triangles in 5.4 ms all-in on an M1 in WebKit is 2.8 million in 10 ms. So the plausible budget on the M1 is not much above what the game draws today; the cluster system has to raise quality mainly by **spending the same triangles better** (one pixel of error everywhere instead of ladders with steps of four to nine times), not by drawing several times more.
- M1 Pro, M2 Pro, M3, M4 (roughly twice a base M1): about 5 to 7 million. M4 Pro and Max classes: 10 million and more; the M4 Pro figure is close to measured (9 to 11 million at over 100 frames a second at 4K in Chrome, simple materials).
- These are submitted triangles after culling and level selection, including padding triangles if clusters are padded to a fixed size. Shadow passes count in full: three-virtual-geometry's views add 6% to 43% shadow triangles on top of the main view even with a three-times coarser shadow threshold (`shadowErrorScale = uniform(3)` in its source).

Vertex-stage runs
- A non-indexed, vertex-pulled cluster draw runs the vertex stage three times per triangle (three.js r187: always 192 runs per cluster, padding included); an indexed cluster draw runs it about 0.6 to 1 times per triangle (the first round's meshoptimizer figures: 0.57 to 0.65 vertices per triangle for well-built clusters). For 3 million triangles that is 9 million runs against 2 to 3 million.
- The published anchors do not separate the cost of a vertex run from the per-triangle cost of setup and binning, so no source gives "nanoseconds per vertex run" on an Apple GPU. The game's own figure bounds it from above: if its 1.5 million triangles are three runs each, a run and its share of everything else cost at most 1.2 ns on the M1. On that basis a base M1 can plausibly afford **6 to 10 million vertex-stage runs a frame if each run stays as cheap as the game's are today**, fewer in proportion if the cluster system makes a run dearer (wider fetches, per-cluster transforms, morphing between levels, more varyings). Apple's own remedies for a vertex-bound frame are fewer vertices, half-precision math and tightly packed data.
- Indexed drawing is therefore worth a measurement before the design is fixed. In Safari it is free of validation only when the pipeline has no vertex buffers; a compute-written index buffer (12 bytes per triangle per frame, 36 MB a frame for 3 million triangles, derived) is the price. Where all instances of a draw share one topology (the game's regular "ball" levels), a static index buffer gives the same saving without the per-frame write.

A recent iPhone
- Its canvas at the screen's own resolution is about 3.2 million pixels on an iPhone 16 Pro (1206 × 2622, recalled) and 3.8 million on a Pro Max, 38% to 46% of 4K, so the pixel problem is smaller than on a Mac with a 4K screen.
- The two comparisons found put a current Pro iPhone in the base-M1 class for short runs. I would budget **1.5 to 2.5 million submitted triangles a frame at 60% to 70% internal scale on an iPhone 15 Pro or later, and assume half of that once the phone is warm** (phones throttle; recalled, no source read gives a curve). iPhones before the A17 Pro have smaller GPUs and should be assumed below this.
- Memory is the first wall on the phone: Apple itself warns of termination "due to memory pressure" for WebGPU on iOS, a WebKit bug speaks of the GPU process dying around 650 MB (search extract), and a single 4K-class half-float target is 66 MB while the phone's own canvas-sized one is about 25 MB. The 8 GB gate of the Mac has no meaning there; the cluster data, the instance tables and every render target have to fit in a few hundred megabytes, with storage bindings of at most 256 MiB to 1 GiB each and 128 MiB unless requested.

What in the design matters most (ranked by how much of the budget it decides)
1. **Internal resolution and the temporal rebuild.** Decide the internal scale first (50% to 67% per axis at 4K, by published practice), measure the upscale pass on an M1 in Safari before anything else, measure error in internal pixels, keep every attachment narrow (each half-float 4K target is 66 MB and a full pass over it is bandwidth on a GPU without its own memory), composite interface at canvas resolution after the upscale.
2. **Triangles submitted, not triangles visible.** Hidden-surface removal saves shading, never vertex work or binning. The cluster cut, frustum and occlusion culling per cluster, a floor on on-screen size (nothing under a pixel), and a coarser threshold for shadows are what keep the count inside 2 to 3.5 million. Keep the vertex stage's output small (position plus the minimum; Apple's own dense-geometry design outputs position only and reconstructs the rest per pixel).
3. **WebKit's draw path.** No vertex buffers on any indirect draw; indirect and index buffers bound read-only wherever they are not being written; never more than a few hundred clamped draws in a pass on an M1 if vertex buffers cannot be avoided; one command buffer per frame as far as three.js allows (batch compute nodes into one `compute()` call); few passes; do not rely on render bundles with indirect draws before Safari 27.2.
4. **Pass structure for Apple's scheduler.** Opaque clusters first, alpha-cut second and roughly front to back, translucent last; no depth pre-pass for opaque geometry; build the depth pyramid from a target that is finished early so the next frame's culling and vertex stage can overlap the previous frame's pixel work; no resource shared between unrelated passes.
5. **Alpha-cut foliage.** It is the one content class the hardware cannot de-duplicate per pixel. Reduce layers (aggregate far crowns into opaque proxies; Epic switches to voxels where they have lower error than triangles), make the cut decision the first and cheapest thing the leaf shader does, sort alpha-cut clusters front to back, and test whether opaque leaf geometry at near range costs less than cards on an M1 (Epic found geometry faster than cards in its renderer; unmeasured on Apple GPUs).
6. **Compute that suits Apple GPUs.** Hierarchical selection (cells, then instances, then clusters) so thread counts follow what is visible; compaction with atomic counters or wait-free multi-pass scans, never a chained scan or spin-wait; few atomic writes to buffers (Apple's counter guidance).
7. **No dependence on 64-bit atomics or multi-draw.** Neither is in Safari; the first can never exist on an M1 or on A14 to A16 iPhones. A compute rasteriser for sub-pixel triangles is possible only in the two-word 32-bit form three.js r187 ships (16-bit depth, no alpha test, no velocity output), which fits neither leaf cards nor a temporal upscaler that needs motion vectors. The hardware rasteriser with a budgeted, internal-resolution error threshold is the path for this gate.
8. **Limits requested explicitly.** `requiredLimits` for `maxStorageBufferBindingSize`, `maxBufferSize` and `maxStorageBuffersPerShaderStage` at device creation, with a design that still works at 128 MiB bindings on phones that grant little more than the default.

What is measured and what is not, in one place
- Measured by someone: the M4 Pro cluster figures (Chrome), the M1 and iPhone 16 Pro forest frame rates, the M1 Pro Shade frame rates, Safari against Chrome on one workload, the PlayStation 5 Nanite figures, and (given to me) the game's 1.5 million triangles in 5.4 ms on an M1.
- Derived by me from those: nanoseconds per triangle and per pixel on the M4 Pro, the M1-to-M4 ratio of 2.0 in one render stage, seven triangles per internal pixel in Nanite's demo.
- My estimates: every per-frame budget above, the scaling to a base M1 and to iPhones, the 3 to 5 ms reserved for the upscale, the 11 to 12 ms planning figure, and the ranking.

### Gaps
- The whole budget hangs on four numbers nobody has published and that can only be measured on the owner's devices in Safari: the cost of a temporal upscale to a 4K canvas on a base M1; the cost per submitted triangle and per vertex-stage run of the game's own drawer at 2 to 4 million triangles (does it stay linear, or does the tiled vertex buffer force partial renders?); the overdraw of the leaf cards (fragment-shader invocations against pixels stored, which Xcode's GPU counters report for Safari's GPU process); and the sustained rate of an iPhone after ten minutes.
- No source gives the size at which Apple's tiled vertex buffer overflows, so the triangle budgets above assume no partial renders.
- The relative speed of M-series GPUs rests on one paper's ratio and on recalled core counts; Apple publishes no figures on the pages reachable here.
- iPhone screen sizes, thermal behaviour and the list of iPhones that run iOS 26 and 27 are recalled, not read.
- Whether shipping Safari really exhibits the "drops to a fraction of the refresh rate after a few slow frames" bug on the owner's devices, and from which version it is fixed, is unknown; the fix is listed only for Technology Preview 254.
