## 0. fal.ai as the one API (owner's constraint): API shape, hosts, MCP, pricing, limits, terms, catalogue, and the character pipeline as fal calls

### Takeaway
fal can carry almost the whole character pipeline behind one key (`FAL_KEY`) and one queue protocol: concept and identity-locked reference images, background removal, upscaling, image/multi-view-to-3D from Meshy, Tripo, Hunyuan3D, Rodin and TRELLIS.2, auto-rigging with preset animations (Meshy), remesh/retopology, retexture, text-to-motion, video and lip-sync; what it does not provide is facial blendshapes, a skeleton in your own convention, KTX2/meshopt packing, validation and rendering for QA, which remain headless Blender + glTF tooling. A published fal recipe (image → Meshy rigged GLB → gltf-transform → three.js) quotes about $2–3 per character-plus-companion; from fal's listed prices a single rigged, textured, animated character costs roughly $1–4.5 in fal calls per accepted asset depending on generator and retries, and fal's price for Meshy is about twice Meshy's own credit price.

### Cited Findings

**API shape (read from the client packages)**
- **[READ]** JavaScript client `@fal-ai/client` is at 1.11.0 (published 2026-11-14, MIT); Python client `fal-client` is at 1.0.3 (2026-09-21, Python ≥3.8); the server-side proxy adapter `@fal-ai/server-proxy` is at 1.3.0 (2026-11-14). — [npm @fal-ai/client](https://www.npmjs.com/package/@fal-ai/client); [PyPI fal-client](https://pypi.org/project/fal-client/); [npm @fal-ai/server-proxy](https://www.npmjs.com/package/@fal-ai/server-proxy)
- **[READ]** URL scheme: synchronous run is `https://fal.run/{endpoint_id}`; queued run is `https://queue.fal.run/{endpoint_id}` (POST = submit); status is `GET https://queue.fal.run/{owner}/{alias}/requests/{request_id}/status` (plus `/status/stream` for server-sent status); result is `GET …/requests/{request_id}`; cancel is `PUT …/requests/{request_id}/cancel`. Submit returns `{status:"IN_QUEUE", request_id, response_url, status_url, cancel_url, queue_position}`; statuses are `IN_QUEUE`, `IN_PROGRESS` (with logs), `COMPLETED` (logs, `metrics.inference_time`). — [npm @fal-ai/client 1.11.0, `src/queue.js`, `src/request.js`, `src/types/common.d.ts`](https://www.npmjs.com/package/@fal-ai/client)
- **[READ]** Webhooks: pass `webhookUrl` (JS) / `webhook_url` (Python); the client appends `?fal_webhook=<url>` to the submit URL. The webhook body is `{status:"OK"|"ERROR", payload, error, request_id}`. — [npm @fal-ai/client, `src/queue.js`, `types/common.d.ts`](https://www.npmjs.com/package/@fal-ai/client); [PyPI fal-client 1.0.3, `client.py`](https://pypi.org/project/fal-client/)
- **[READ]** Request headers the client can set: `x-fal-queue-priority` (`low`|`normal`), `x-fal-runner-hint`, `x-fal-request-start-timeout` (seconds; limits queue wait before processing starts), `x-fal-tags` (up to 10 key/value pairs, 1 KB, "to attribute the request's usage and cost to your own dimensions"), and `x-fal-object-lifecycle-preference` (how long generated files live). — [npm @fal-ai/client, `src/headers.js`, `src/queue.d.ts`, `types/common.d.ts`](https://www.npmjs.com/package/@fal-ai/client)
- **[READ]** Client polling defaults: JS `subscribe()` polls with backoff starting at 250 ms, ×1.05 per check, ±20 % jitter, capped at 10 s; Python default poll interval is 0.1 s. Both clients retry transient errors and fall back to backup domains on connection failure. — [npm @fal-ai/client `src/queue.d.ts`](https://www.npmjs.com/package/@fal-ai/client); [PyPI fal-client `client.py`](https://pypi.org/project/fal-client/)
- **[READ]** Python surface: `run`, `submit`, `subscribe`, `status`, `result`, `cancel`, `stream`, `upload`, `upload_file`, `upload_image`, `realtime` (sync and async clients). JS surface: `fal.run`, `fal.subscribe`, `fal.queue.submit/status/streamStatus/result/cancel`, `fal.storage.upload`, `fal.stream`, realtime. — [PyPI fal-client](https://pypi.org/project/fal-client/); [npm @fal-ai/client](https://www.npmjs.com/package/@fal-ai/client)
- **[READ]** File upload: JS calls `POST https://rest.fal.ai/storage/upload/initiate?storage_type=fal-cdn-v3` (or `/initiate-multipart` above a size threshold, default 10 MB parts, 3 attempts per part), then PUTs to the returned `upload_url` and uses the returned `file_url`. Python uploads to `https://v3.fal.media/files/upload` with a CDN token from `https://rest.fal.ai/storage/auth/token?storage_type=fal-cdn-v3`, falling back to `rest.fal.ai/storage/upload/initiate?storage_type=gcs`; its source says "the legacy fal.media CDN has been disabled". Inputs typed `string | Blob | File` are auto-uploaded by the JS client. — [npm @fal-ai/client `src/storage.js`](https://www.npmjs.com/package/@fal-ai/client); [PyPI fal-client `client.py`](https://pypi.org/project/fal-client/)
- **[READ]** Retention control from the client: `storageSettings.expiresIn` accepts `"never" | "immediate" | "1h" | "1d" | "7d" | "30d" | "1y"` or seconds, plus an ACL (`hide`/`forbid`/`allow`), for uploads and for generated objects. — [npm @fal-ai/client `src/storage.d.ts`](https://www.npmjs.com/package/@fal-ai/client)

**Authentication**
- **[READ]** Credentials come from `FAL_KEY`, or `FAL_KEY_ID` + `FAL_KEY_SECRET` (joined as `id:secret`); the request header is `Authorization: Key <credentials>`. In browsers the client expects a proxy (`proxyUrl`) so the key is not exposed. — [npm @fal-ai/client `src/config.js`, `src/request.js`](https://www.npmjs.com/package/@fal-ai/client)

**Pricing model, spend control, limits**
- **[EXTRACT]** fal is pay-per-use from prepaid credits; each model has its own billing unit (per request, per second, per megapixel, per video). Prices are queryable through the Platform API; usage line items and time-bucketed analytics are available by API and dashboard. — [fal docs, pricing](https://fal.ai/docs/documentation/model-apis/pricing.md); [fal docs, pricing estimate](https://fal.ai/docs/platform-apis/v1/models/pricing/estimate.md)
- **[EXTRACT]** Concurrency: new accounts start at 2 concurrent requests `IN_PROGRESS`; the limit rises with credit purchases up to 40, beyond that via sales; requests over the limit queue rather than fail (except when `start_timeout` expires); per-model limits may apply to high-demand models; the official client retries HTTP 429 with exponential backoff. A third-party listing claims a default of 10; fal's docs say 2. — [fal docs, concurrency limits](https://fal.ai/docs/documentation/model-apis/concurrency-limits.md); [fal docs, FAQ](https://fal.ai/docs/documentation/model-apis/faq.md)
- **[EXTRACT]** When the credit balance drops below the account's "lock threshold" the account is locked and API requests are rejected. — [fal docs, FAQ](https://fal.ai/docs/documentation/model-apis/faq.md)
- **[EXTRACT]** No official documentation of a hard spend cap or per-key budget was found; one third-party blog recommends "spend limits and per-key budgets" without saying how fal implements them, and one reviewer says there is no hard cap. — [Activepieces blog](https://www.activepieces.com/blog/fal-ai-pricing-in-2026-is-pay-per-use-not-a-subscription)

### Inferences

**The character pipeline as fal calls plus the minimum non-fal steps** (endpoint parameters are [READ] from the typings above; the sequencing is my design):

1. *Brief (agent, no fal).* Claude writes `character.yaml` (identity anchors, proportions, height in metres, palette, outfit, polygon and texture budgets, skeleton/blendshape convention, licence constraints).
2. *Concept candidates.* `fal-ai/nano-banana-pro` or `openai/gpt-image-2` (text-to-image), 4 variants, full body, neutral A-pose, plain background. Agent ranks with vision; **human approval gate 1** on the chosen concept.
3. *Identity-locked reference sheet.* `fal-ai/nano-banana-pro/edit` (or `bytedance/seedream/v5/lite/edit`, `fal-ai/flux-2-lora-gallery/multiple-angles`) with the approved image in `image_urls`: front, left, back, right (order matters for Tripo: front, left, back, right) plus a face close-up.
4. *Clean inputs.* `fal-ai/birefnet/v2` (model "Portrait"/"General Use (Heavy)") or `fal-ai/bria/background/remove`; optional `fal-ai/seedvr/upscale/image`.
5. *3D generation, three alternative routes:*
   - **A (one call):** `meshy/v7.1/multi-image-to-3d` or `…/image-to-3d` with `pose_mode:"a-pose"`, `topology:"quad"`, `target_polycount`, `enable_pbr:true`, `enable_rigging:true`, `rigging_height_meters`, optional `enable_animation`.
   - **B (cheap geometry, separate rig):** `fal-ai/hunyuan-3d/v3.1/pro/image-to-3d` (multi-view inputs) → `fal-ai/hunyuan-3d/v3.1/smart-topology` → `fal-ai/meshy/rigging`.
   - **C (seeded, reproducible):** `tripo3d/h3.1/multiview-to-3d` with `model_seed`/`texture_seed`, `face_limit` → `tripo3d/tripo/remesh` → `fal-ai/meshy/rigging`.
6. *Animations.* `fal-ai/meshy/rigging/multi-animation` (preset IDs) and/or `fal-ai/hunyuan-motion` (text → FBX, then retarget in Blender).
7. *Optional.* `meshy/v7/retexture` or `fal-ai/trellis-2/retexture`; `fal-ai/kling-video/v3/pro/image-to-video` for a promo/turntable clip; `fal-ai/sync-lipsync/v3` + `elevenlabs/tts/eleven-v4` for talking shots (2D only).
8. *Non-fal minimum (in the agent's container).* Download the GLB from `v3b.fal.media`; headless Blender (`bpy`): import, fix scale/orientation, map or replace the skeleton to the house convention, add/transfer blendshapes, LODs, bake; `gltf-transform`/`gltfpack` + Basis encoder for meshopt + KTX2; glTF Validator; Cycles CPU turntable and pose-sweep renders; Claude vision QA + metrics; **human approval gate 2**; commit GLB + provenance record.

**Cost per character from the listed fal prices (arithmetic on the extracts above; not a quote):**
- Route A, one attempt: 4 concepts × $0.15 = $0.60; 4 reference views × $0.15 = $0.60; Meshy 7.1 textured + rig + one animation $1.52 → about **$2.7**; with a second 3D attempt **$4.2**. Background removal and upscaling prices were not found (expected to be cents).
- Route B, one attempt with cheap images: 8 Seedream 5 Lite images × $0.035 = $0.28; Hunyuan 3.1 Rapid + PBR $0.375 (Pro price not found); rig ≈ $0.20 if standalone rigging matches the in-call add-on (not confirmed) → about **$0.9**; three attempts ≈ $2.
- Add a 5-second Kling 3 Pro clip: + about $0.56.
- This brackets fal's own skill figure of "~$2–3 per generation (4 fal calls)".
- fal's Meshy price is roughly 2× Meshy direct: Meshy's API charges 30 credits (textured) + 5 (rig) + 3 (one animation) = 38 credits, about $0.76 at the $0.02/credit a competitor attributes to Meshy's Pro plan, versus $1.52 on fal. The premium buys one key, one queue protocol and one invoice.

**Spend capping without a documented hard cap:** keep a small prepaid balance with auto-top-up off (the documented lock threshold then acts as a hard stop); tag every request with `x-fal-tags` (character ID, stage); call `pricing`/`pricing/estimate` before each paid step and keep a ledger in the repo; enforce a per-character budget in the pipeline script itself; use `--max-budget-usd` for the Claude side.

**MCP vs CLI vs SDK for Claude Code:** in a headless cloud container the browser OAuth flow of the hosted fal MCP is awkward and its two documented connection forms disagree; the `@fal-ai/client`/`fal-client` SDKs (installable from npm/PyPI, which are reachable) or `genmedia` (needs `genmedia.sh`) driven from Bash give the same capability with files on disk, deterministic scripts and no MCP token overhead. The skills repo is worth vendoring for its endpoint routing and prompt patterns.

**Catalogue churn is a real risk:** the fal skill files still route to Meshy v6 while the typings already list Meshy 7.1; Veo appears to have left the catalogue this week. Pin endpoint IDs in the spec and check `genmedia models --endpoint_id … --status all` before runs.

### Takeaway

## 2. Published agentic 3D workflows and what they achieve

### Takeaway
Research agents that write Blender code and look at renders (BlenderAlchemy, LL3M, VIGA) show the write–render–compare–revise loop works for scenes, materials, layout and simple shapes, and improves with more verification compute, but benchmark results still put them well behind human Blender users; nobody reports code-writing agents producing production-quality organic characters. In practice the community splits the work: a generative 3D model makes the character, the agent orchestrates, cleans up and checks.

### Cited Findings
- **[READ]** BlenderAlchemy (Huang, Yang, Guibas; arXiv 2404.17672): a VLM "edit generator" proposes program edits and a "state evaluator" picks winners over a search with depth and breadth hyperparameters (the shipped example run is `tune_d4_b8`); it edits a Blender script that a fixed base script executes and renders; the shipped demo edits facial shape keys ("blendshapes_face.yaml"); "We have observed the best performance with GPT4V so far"; supports GPT-4V, Gemini and Claude as generator/evaluator. — [BlenderAlchemyOfficial README](https://github.com/ianhuang0630/BlenderAlchemyOfficial)
- **[READ]** LL3M (threedle): "a multi-agent system … to generate 3D assets by writing interpretable Python code in Blender", with planning, retrieval, coding, debugging and refinement agents; phases shown as initial creation, auto refinement, user-guided refinement; renders 5 images per instruction by default; used Blender 4.4; errors are fed back for correction (the README's example error is `key "Specular" not found`). Notice at top: "The model used in the paper, Claude Sonnet 3.7, has been retired. As a result, we have discontinued the LL3M server"; the hosted demo was limited to 5 requests per day per account. — [threedle/ll3m README](https://github.com/threedle/ll3m)
- **[READ]** VIGA (arXiv 2601.11109, MIT): "an analysis-by-synthesis code agent" where one agent alternates Generator (writes and executes scene programs with tools for planning, code execution, asset retrieval, scene queries) and Verifier ("examines rendered output from multiple viewpoints, identifies visual discrepancies"), with a memory of plans, code diffs and render history; "requires no finetuning"; for 3D modes "an NVIDIA GPU with CUDA support is recommended"; it uses SAM and Infinigen's Blender. — [Fugtemypt123/VIGA-release README](https://github.com/Fugtemypt123/VIGA-release)
- **[EXTRACT]** VIGA's reported gains: abstract says it improves one-shot baselines on BlenderGym by 35.32 % and on SlideBench by 117.17 %, and by 124.70 % on its harder BlenderBench; the project page gives +32.65 % average — the two BlenderGym figures conflict. It keeps only recent iterations in context because the latest program already contains earlier successful edits. No iteration count was found. — [arXiv 2601.11109](https://arxiv.org/abs/2601.11109); [VIGA project page](https://fugtemypt123.github.io/VIGA-website)
- **[EXTRACT]** BlenderGym (arXiv 2504.01786, April 2025): 245 hand-built scenes over five editing tasks (procedural geometry 50, lighting 40, procedural materials 40, blend shapes 75, object placement 40), scored with photometric loss, negative CLIP similarity and Chamfer distance; humans are consistently better (placement Chamfer distance 1.532 for humans vs 11.22 for GPT-4o); "even the state-of-the-art VLM system struggles with tasks relatively easy for human Blender users"; more verifier compute improves results, and with ample compute verification beats more generation. — [arXiv 2504.01786](https://arxiv.org/pdf/2504.01786)
- **[EXTRACT]** Hunyuan3D Studio (Tencent, arXiv 2509.12815, 2025) is described as a modular sequential pipeline — concept image, geometry, part segmentation, retopology by autoregressive mesh generation, UV, texturing, animation — passing metadata between modules; I found no 2026 "agent" layer for it. — [arXiv 2509.12815](https://web3.arxiv.org/pdf/2509.12815)
- **[SECONDARY]** Tripo Studio is described (largely in sponsored pieces) as an integrated flow of segmentation, retopology, texturing and auto-rigging that detects biped vs quadruped; a vendor comparison says rigging has polygon limits and supports only biped and quadruped; one blogger's single test got a usable FBX that took a Mixamo walk in Unity. — [Gitconnected post](https://levelup.gitconnected.com/building-game-ready-3d-assets-fast-the-best-ai-generators-for-production-workflows-in-2026-f1f725ff5df0); [Tripo vs Hunyuan (Tripo's own page)](https://www.tripo3d.ai/compare/tripo-vs-hunyuan)
- **[SECONDARY]** Practitioner assessments of Claude + Blender MCP: works well for basic object creation and scene assembly; poor for organic character modelling because sculpt mode is not reachable through MCP; Geometry Nodes scripts are fragile across Blender versions; generated geometry "can look fine yet fail to deform under a rig". Vendor and third-party guides draw the same line: use an AI 3D generator for characters and Blender MCP for scene assembly and scripted operations. — [MindStudio review](https://www.mindstudio.ai/blog/claude-blender-mcp-real-world-performance); [Medium, creativeaininja](https://medium.com/@creativeaininja/claude-drives-blender-through-mcp-now-heres-what-actually-changes-684f28f78c7b); [3D AI Studio guide, updated October 2026](https://www.3daistudio.com/3d-generator-ai-comparison-alternatives-guide/blender-mcp); [Meshy tutorial](https://www.meshy.ai/tutorials/blender-mcp-guide)

### Inferences
- The research systems validate the loop design (generator + verifier, renders from several viewpoints, keep code as the state, keep only recent iterations) more than they validate quality: on benchmarks built from easy edits they still trail humans, and the one hosted system (LL3M) died when its model was retired — a warning about pinning a pipeline to one model version.
- For characters the workable division of labour in November 2026 is: generative model for shape and texture; hosted auto-rig for a first skeleton; agent-written `bpy` for deterministic clean-up; agent vision for triage; a human for likeness, face and deformation sign-off.
- Typical failure points reported or implied: organic modelling by code; topology that renders well but deforms badly; triangle-soup output needing retopology; scale/orientation mismatches; preset rigs limited to bipeds/quadrupeds with no facial rig; Blender API drift breaking generated scripts.

### Gaps

- 3D-GPT and SceneCraft were not examined beyond being cited as related work in BlenderGym; no quantitative results collected.
- No independent benchmark compares generators on hands, faces or joint deformation.
- VIGA's and BlenderGym's exact tables and iteration counts need the PDFs (arXiv blocked).

## 3. Headless post-processing the agent can script

### Takeaway
Everything deterministic in the clean-up chain runs on CPU in a 4 vCPU container: Blender 5.3 installs from PyPI as the `bpy` module, and import, decimate, voxel and QuadriFlow remesh, UV unwrap, Cycles bake, Rigify rig generation, automatic weights, shape keys, glTF/FBX export and Cycles renders all worked in my tests within seconds; EEVEE and Workbench do not work without an OpenGL/Vulkan stack. glTF packing works from npm, with one catch: the npm build of gltfpack cannot compress textures, and gltf-transform's KTX2 commands need the external `ktx` binary.

### Inferences
- What works without a GPU: all mesh, UV, rig, weight, shape-key, bake and export operations; Cycles CPU renders for QA (seconds at 512² with low samples; minutes for high-sample 2K turntables on 4 vCPUs); meshopt compression; ETC1S/UASTC encoding; validation.
- What needs a GPU or extra setup: EEVEE/Workbench (need libEGL plus a GL/Vulkan driver — a software Mesa stack might work but I did not test it); all neural steps (generation, neural rigging, neural retopology), which stay on fal.
- A complete KTX2 route in a locked-down container: `basisu` from npm to encode each texture, then a small gltf-transform script to swap textures to `KHR_texture_basisu`; where GitHub release downloads are allowed, native `gltfpack -cc -tc` or `ktx` + `gltf-transform uastc/etc1s` is simpler.
- A setup script of `uv pip install bpy==5.3.0` + `npm i @gltf-transform/cli gltfpack gltf-validator basisu` fits the five-minute caching limit.
- Rigify's 160 deform bones are far more than a game skeleton needs; for the browser, export only a reduced deform set mapped to the house convention.
- Agent-written `bpy` should pin the Blender version and run a preflight, as LL3M does.

### Gaps
- Not tested: texture baking from a 500k-face generated mesh onto a low-poly retopologised mesh (the expensive bake), weight transfer and blendshape transfer from a template, animation retargeting (e.g. Meshy/Mixamo FBX onto a custom skeleton), and turntable timing at production quality.
- Whether EEVEE runs with software Mesa (llvmpipe/lavapipe) in Claude Code's VM is untested.
- Blender manual pages could not be opened; operator behaviour is from my runs, not from documentation.

## 4. Visual quality control by a vision-language model

### Takeaway
Use the model's eyes as a triage and description tool, not as the judge of record: published evaluations show VLM judges agree with human preference only moderately for 3D geometry, and 2026 studies show even frontier models miss cross-view 3D inconsistencies that people spot easily. Pair every visual check with an objective measurement taken from the mesh or from calibrated renders, and keep a human on face, likeness and deformation.

### Cited Findings
- **[EXTRACT]** GPTEval3D uses GPT-4V pairwise comparisons with Elo ranking for text-to-3D; Hi3DEval (NeurIPS 2025, arXiv 2508.05609) reports higher agreement with human pairwise preference using video-based and native 3D scorers — e.g. geometry plausibility 0.774 vs 0.690 for GPTEval3D and 0.556 for CLIP score (via a third-party summary) — and argues image-only, object-level metrics are insufficient, adding part-level and material-realism checks. — [Hi3DEval, arXiv 2508.05609](https://arxiv.org/pdf/2508.05609); [Liner summary](https://liner.com/en/review/hi3deval-advancing-3d-generation-evaluation-with-hierarchical-validity)
- **[EXTRACT]** 3DGen-Bench (arXiv 2503.21745) collected human preferences in a pairwise arena and trained a CLIP-based and an MLLM-based scorer reported to align well with humans. — [3DGen-Bench, arXiv 2503.21745](https://arxiv.org/pdf/2503.21745)
- **[EXTRACT]** "Multimodal Language Models Cannot Spot Spatial Inconsistencies" (ICLR 2026, arXiv 2604.00799): given two views of a scene and asked to find the object that breaks 3D consistency, state-of-the-art models including GPT-5 and Gemini 2.5 Pro "trail human observers by a wide margin". — [arXiv 2604.00799](https://arxiv.org/abs/2604.00799)
- **[EXTRACT]** MV-RoboBench (ICLR 2026): on a "3D Spatial Consistency" subtask many non-reasoning models score near or below chance (19.07 %); reasoning-enhanced models reach 49–82 %. ViewDiag (arXiv 2606.02742): leading VLMs often give stable, view-invariant answers that are wrong, so consistency of answers is a poor proxy for geometric understanding. SCOPE (ACL 2026): 20,144 spatial questions over 939 scenes testing integration of multiple views. — [MV-RoboBench summary](https://liner.com/review/seeing-across-views-benchmarking-spatial-reasoning-of-visionlanguage-models-in); [ViewDiag listing](https://papers.cool/arxiv/2606.02742); [SCOPE, ACL 2026](https://aclanthology.org/2026.acl-long.1514.pdf)
- **[EXTRACT]** BlenderGym found that spending more on verification improves VLM-system results, and it scores with photometric loss, negative CLIP similarity and Chamfer distance rather than a VLM's opinion. — [arXiv 2504.01786](https://arxiv.org/pdf/2504.01786)
- **[READ]** What Claude sees: an image costs `⌈width/28⌉ × ⌈height/28⌉` visual tokens; Claude 4.7 and later accept up to 2,576 px on the long edge and 4,784 visual tokens per image (1000×1000 = 1,296 tokens; 1920×1080 = 2,691); up to 600 images per request. — [Anthropic docs, vision](https://platform.claude.com/docs/en/build-with-claude/vision)
- **[READ]** MCP for Blender's `look` tool already packages the views an agent needs: auto-framed multi-angle sheets, wireframe, x-ray and animation-strip views "so the AI checks its own work". — [ahujasid/blender-mcp README](https://github.com/ahujasid/blender-mcp)
- **[READ]** fal hosts measurement helpers usable as objective probes: `fal-ai/sam-3/3d-body` returns a body mesh, 3D keypoints, camera parameters and optional body-model parameters from an image; `fal-ai/dwpose` extracts 2D pose; `fal-ai/moondream3-preview/{detect,point,query}` and `fal-ai/florence-2-large/*` do detection and grounding. — [npm @fal-ai/client `src/types/endpoints.d.ts`](https://www.npmjs.com/package/@fal-ai/client)

### Inferences
**Recommended split of checks** (my synthesis; none of this is a published standard):
- *Computed from the file (authoritative):* glTF Validator errors = 0; triangle/vertex counts and texture sizes within the spec's budget; one skin, joints ≤ budget, max 4 influences, weights normalised; required bones and blendshape names present; bounding-box height equals spec height ± tolerance; feet on the ground plane; forward axis; watertightness/non-manifold counts; UV overlap and texel density; bilateral symmetry error.
- *Computed from fixed-camera renders (authoritative with thresholds):* silhouette IoU of front/side/back renders against the approved reference views (after background removal); landmark distances — 2D face/body keypoints from a detector on both the concept image and the render, compared after similarity alignment; CLIP or DINO image similarity between render and concept as a coarse identity/appearance score; LPIPS/SSIM between turntable frames of successive versions as a regression check; per-pose deformation probes (volume change at elbows, knees, shoulders; self-intersection counts) over a scripted pose sweep.
- *VLM judgement (advisory, with a checklist and forced evidence):* extra or fused fingers, duplicated faces on the back of the head (Janus), melted facial features, texture seams and baked-in lighting, floating fragments, wrong pose, clothing fused to the body, "candy-wrapper" twists and collapsing joints in the pose-sweep contact sheet. Ask per-view questions about named regions at high resolution rather than "is this good?".
- *Human only:* likeness and appeal, face in close-up, final deformation sign-off.

Known weaknesses to design around: cross-view inconsistency detection is weak; scale and metric judgements are unreliable from images; a model judging its own pipeline's output tends to accept it; similarity scores (CLIP/DINO) do not see topology or skinning; scores drift when the judge model changes, so log the judge model ID with every verdict.

### Gaps
- No study was found that measures a VLM's accuracy at judging rig deformation, face quality or likeness of generated characters from renders; the recommendations above are engineering judgement.
- No published threshold values (IoU, landmark error) for accepting a generated character were found.
- Claude-specific evidence on 3D asset judgement (Opus 5.5 / Fable 5.2) was not found.

## 5. Orchestration patterns

### Takeaway
Treat generation like a build: a declarative character spec is the single source of truth, every stage is a pure function of hashed inputs with its outputs cached, every paid call writes a provenance record, and two human gates (concept, final asset) sit where taste and risk concentrate. Claude Code supplies the mechanics — skills for the recipe, hooks and permission rules for gates, budget flags and structured output for unattended runs.

### Cited Findings
- **[READ]** Claude Code can run unattended: `claude -p "<prompt>" --allowedTools …`, `--output-format json` (the payload "includes `total_cost_usd` and a per-model cost breakdown"), `--json-schema` for schema-conforming output, `--max-turns`, `--max-budget-usd` ("Stop the run once estimated spend on API calls reaches this amount (print mode only)"), `--mcp-config`, and `--bare` ("recommended mode for scripted and SDK calls"). — [Claude Code docs, headless](https://code.claude.com/docs/en/headless); [Claude Code docs, CLI reference](https://code.claude.com/docs/en/cli-reference)
- **[READ]** Skills are folders with a `SKILL.md` (YAML frontmatter + instructions) and optional supporting files such as scripts, following the Agent Skills open standard; project skills live in `.claude/skills/<name>/SKILL.md` and are committed with the repo. — [Claude Code docs, skills](https://code.claude.com/docs/en/skills)
- **[READ]** Hooks give deterministic gates: `PreToolUse` runs "before a tool call executes. Can block it" by returning a `permissionDecision` of `"deny"`; `PostToolUse` runs after success. — [Claude Code docs, hooks](https://code.claude.com/docs/en/hooks)
- **[READ]** Project-scoped MCP servers go in the repo's `.mcp.json` (`claude mcp add --scope project`), which is what cloud sessions pick up; user-scoped servers do not carry over. — [Claude Code docs, cloud environments](https://code.claude.com/docs/en/cloud-environments); [Claude Code docs, MCP](https://code.claude.com/docs/en/mcp)
- **[READ]** Seeds and identifiers that make regeneration and provenance possible are exposed by the fal endpoints: Tripo `model_seed`/`texture_seed`, Rodin and TRELLIS.2 and Hunyuan-Motion `seed`, Hunyuan 3D returns `seed`, Meshy returns `rig_task_id`, Tripo returns `task_id`; every fal request has a `request_id`; requests can carry cost-attribution tags. — [npm @fal-ai/client `src/types/endpoints.d.ts`, `types/common.d.ts`](https://www.npmjs.com/package/@fal-ai/client)
- **[READ]** Meshy's MCP server "auto-saves to `meshy_output/` with project folders, metadata, and history tracking" and never re-sends a create request after a timeout, to avoid double billing. — [meshy-dev/meshy-mcp-server README](https://github.com/meshy-dev/meshy-mcp-server)
- **[READ]** fal's skills define a "shared resumable runner" with stage plans, and a `game-asset-production` outcome that ends in "engine import metadata" and a manifest. — [fal-ai-community/skills README](https://github.com/fal-ai-community/skills)
- **[SECONDARY]** Practitioner guidance on provenance for AI game assets: store tool version, model ID or hash, inference parameters, source prompts and author in a sidecar JSON with an immutable hash; tag each asset with model version, licence type and human review sign-off; define approval gates for art direction, compliance, technical quality and final publishing; "record provenance at creation time, not right before release". These are blogs, not standards. — [virtuall.pro](https://virtuall.pro/blog/game-assets-ai-pipelines-need-before-production-begins); [macmyths compliance audit guide](https://macmyths.com/how-to-document-ai-generated-code-and-art-for-a-games-compliance-audit/); [Promise Legal](https://blog.promise.legal/ai-game-assets-what-studios-own-2026/)
- **[SECONDARY]** A public example of the scrutiny: Crystal Dynamics described using generative AI for ideation with final assets rebuilt by humans. — [letsdatascience news item](https://letsdatascience.com/news/crystal-dynamics-confirms-using-generative-ai-tools-6fb5cfad)

### Inferences
- **Spec file** (`characters/<id>/character.yaml`): identity anchors and prose brief; proportions and height; palette; outfit; references (hashes of approved images); target budgets (triangles per LOD, texture sizes, bone count); skeleton and blendshape convention version; pinned fal endpoint IDs and parameters per stage; QA thresholds; budget cap; licence/likeness declarations (e.g. "not based on a real person").
- **Content-addressed stages:** key = hash(stage name + endpoint ID + parameters + seeds + input file hashes + tool versions). Outputs stored under that key (the project already stores media by hash for stories); a stage re-runs only when its key changes. Generation is not bit-reproducible even with seeds, so the cached artefact, not the recipe, is the truth; regeneration is an explicit, logged decision.
- **Provenance record per artefact** (sidecar JSON, committed): fal endpoint ID, `request_id`, prompts, seeds, input hashes, output hash, price paid, timestamp, upstream model/vendor and its licence terms at the time, Blender/gltf tool versions, judge model ID and QA scores, human approver and date. This is also the evidence base for Steam's disclosure form and for any copyright claim about human contribution.
- **Human gates:** gate 1 after concept images (cheap to iterate before it, expensive after); gate 2 on the final turntable, pose sweep and metrics. Implement as a stop in the pipeline (the agent opens a PR with renders and waits) rather than a prompt-level promise; a `PreToolUse` hook can deny paid fal calls when the ledger exceeds the cap or when the gate file is missing.
- **Cost caps on three levels:** prepaid fal balance; per-character budget in the ledger checked before each call; `--max-budget-usd` for the agent run.
- **Idempotence:** never blindly retry a create call after a timeout; look up the request by ID first.

### Gaps
- No documented example was found of a shipped game whose asset pipeline does spec-driven regeneration with content hashes and provenance for generated characters; the pattern above is assembled from build-system practice and the fragments cited.
- C2PA/content-credential support for glTF/GLB assets was not researched.
- fal's own "workflow" JSON format (mentioned in its skills) was not examined.

## 7. Legal and policy points an agent must respect (reported, not advice)

### Takeaway
The stable facts as of November 2026: purely AI-generated output is not copyrightable in the US and is doubtful in the EU, so ownership of a generated character rests on contract terms and on documented human contribution; Steam requires disclosure of player-facing generated content; EU transparency duties under Article 50 of the AI Act have applied since 2 August 2026; licences differ by vendor and plan (Meshy free tier is CC BY 4.0; Tencent's open Hunyuan3D weights are not licensed for the EU, UK or South Korea); real people's likenesses should be excluded by design. Several of the texts could only be seen through law-firm summaries, and some dates conflict.

## 8. What the runtime needs (three.js r187, WebGPU)

### Takeaway
three.js r187 already has the whole loader path — GLB with meshopt and KTX2 textures on the WebGPU renderer — so the runtime work is conventions, not plumbing: one skeleton naming and rest-pose convention, one blendshape naming set, units and axes, and material rules, enforced at import by the pipeline so that any generated character is interchangeable with the procedural body. VRM 1.0's humanoid and expression sets are the ready-made convention closest to the project's existing rig.

### Inferences
- **The project's rig already lines up with VRM humanoid.** `TheGame/characters/kit/skeleton/rig.js` defines `root, hips, spine1–3, neck1–2, head, jaw, eye.L/R, lidUp/lidLo, clavicle, upperArm(+Twist), foreArm(+Twist), hand, thigh(+Twist), shin, foot, toes` plus fingers, in metres, y up, z forward, x to the character's left, for a 1.80 m reference in a neutral arms-down pose. Mapping: `hips→hips`, `spine1→spine`, `spine2→chest`, `spine3→upperChest`, `neck1→neck`, `head`, `jaw`, `eye.*→left/rightEye`, `clavicle→Shoulder`, `upperArm→UpperArm`, `foreArm→LowerArm`, `hand→Hand`, `thigh→UpperLeg`, `shin→LowerLeg`, `foot→Foot`, `toes→Toes`; `neck2`, twist bones and eyelid bones are extras outside the standard set. No GLB/KTX2 loader use was found in `TheGame` source by a quick search, so the loader path is new work.
- **Convention to fix once (a "character contract"):** bone names and hierarchy (the house rig, with a published map to VRM humanoid and to Meshy's/Mixamo-style names); rest pose (generators deliver A- or T-pose; the house rig rests arms-down, so the import step must re-pose and re-bind, or the runtime must retarget by bone-local rotations); units and axes (glTF is metres, y up; set height from the spec); max 4 influences; blendshape names (VRM presets as the minimum; ARKit-style 52 if the photoreal face needs them) written to `extras.targetNames`; one skinned mesh or a fixed set of named parts; material slots and texture sets (base colour sRGB, ORM, normal) in KTX2 with multiple-of-four sizes; LOD naming.
- **Loader path:** `WebGPURenderer` → `await renderer.init()` → `KTX2Loader().setTranscoderPath(…).detectSupport(renderer)` → `GLTFLoader().setKTX2Loader(…).setMeshoptDecoder(MeshoptDecoder)`. Normal maps should use UASTC (ETC1S damages them); base colour can use ETC1S.
- **Coexist or replace — three options:** (a) *generated characters as separate GLB actors* driven by the same animation data through a bone-name map — fastest, lowest fidelity coupling, good for non-player characters; (b) *generated surface on the procedural skeleton* — import step transfers the generated mesh onto the house rig (re-skin with automatic weights or weight transfer from the procedural body, blendshapes transferred from the procedural face), so every character shares rig, animation and face logic; (c) *generated appearance only* — use generated images/meshes as references or textures that parameterise the procedural body (shape targets, skin/outfit textures), keeping the procedural pipeline as the only mesh source. Option (b) makes characters interchangeable; option (c) keeps the photoreal face work intact where generators are weakest (faces, hands, deformation).
- Preset rigs from generators have no facial rig, so any talking, blinking or emoting character needs blendshapes added on the import side or the procedural head attached to a generated body.

### Gaps

- Whether fal partner models ever return result URLs on non-fal hosts is unknown.
