## 1. meshoptimizer (Arseny Kapoulkine / zeux): current version, hierarchy-building functions, JavaScript/WebAssembly surface, throughput, licence

### Takeaway
meshoptimizer 1.3 (25 Sep 2026, MIT) is the one maintained open toolkit that contains every building block of a Nanite-style cluster DAG, and since v1.0 (8 Dec 2025) it ships the whole build loop as a single-header library, `demo/clusterlod.h`; natively it processes NVIDIA's 1.6-billion-triangle Zorah scene in about 2.5 to 3.75 minutes on 16 cores. The npm package (1.3.0) exposes the simplifier and the meshlet builders to JavaScript but not `meshopt_partitionClusters` and not `clusterlod.h`, so a hierarchy can be built in a web worker only by writing the grouping step yourself (as two browser projects do) or by compiling `clusterlod.h` to WebAssembly yourself.

### Cited Findings

Functions that build a cluster hierarchy
- `meshopt_buildMeshlets` "tries to balance topological efficiency (by maximizing vertex reuse inside meshlets) with culling efficiency"; `meshopt_buildMeshletsFlex` takes `min_triangles` and `max_triangles` plus a `split_factor` (recommended 2.0) and prioritises spatial locality even if meshlets end up partially filled; `meshopt_buildMeshletsSpatial` "builds clusters using surface area heuristic (SAH) to produce raytracing-friendly cluster distributions"; `meshopt_buildMeshletsScan` greedily aggregates consecutive triangles — [meshoptimizer README](https://github.com/zeux/meshoptimizer/blob/master/README.md)
- `meshopt_partitionClusters` "assigns each cluster to a partition, aiming for a target partition size while prioritizing topological locality"; the README says results "can be used for... hierarchical simplification schemes similar to Nanite". It was added as experimental in v0.23 (Mar 2025), accepted positions and became "~2x faster on typical inputs" in v0.24, and was stabilised in v0.25 — [meshoptimizer README](https://github.com/zeux/meshoptimizer/blob/master/README.md); [meshoptimizer releases](https://github.com/zeux/meshoptimizer/releases)
- `meshopt_simplify` generates "a second index buffer that uses existing vertices in the vertex buffer" and "is not guaranteed to reach the target index count and can stop earlier". Flags: `meshopt_SimplifyLockBorder` blocks collapses on mesh borders so that independently simplified subsets can be combined without cracks; `meshopt_SimplifyErrorAbsolute` switches the error from relative to absolute units; `meshopt_SimplifySparse` improves performance when the indices are a sparse subset of the mesh ("intended for meshlet simplification"); `meshopt_SimplifyPrune` removes isolated components regardless of topological restrictions; `meshopt_SimplifyRegularize` / `RegularizeLight` give more regular triangles at some cost in geometric quality; `meshopt_SimplifyPermissive` allows collapses across attribute discontinuities except for vertices protected through `vertex_lock`; `meshopt_SimplifyPreserveFolds` and `meshopt_SimplifyErrorClamped` are experimental — [meshoptimizer README](https://github.com/zeux/meshoptimizer/blob/master/README.md)
- `meshopt_simplifyWithAttributes` adds attribute values and weights to the error and takes a per-vertex `vertex_lock` array (flags `meshopt_SimplifyVertex_Lock`, `_Protect`, `_Priority`); `meshopt_simplifyWithUpdate` "updates the index buffer as well as vertex positions and attributes in place"; `meshopt_simplifySloppy` "doesn't follow the topology of the original mesh" and generally gives worse quality; `meshopt_simplifyPoints` reduces a point cloud to a given count, optionally weighing colour; `meshopt_simplifyScale` converts the normalised error into object space — [meshoptimizer README](https://github.com/zeux/meshoptimizer/blob/master/README.md)
- When each flag arrived: `SimplifySparse` and `SimplifyErrorAbsolute` in v0.21 (Jun 2024); `SimplifyPrune` in v0.22; `simplifyWithUpdate`, `SimplifyPermissive` and `SimplifyRegularize` in v0.25 (Aug 2025) — [meshoptimizer releases](https://github.com/zeux/meshoptimizer/releases)

What `clusterlod.h` does (read from the header on master)
- It is "a small library/example built on top of meshoptimizer for generating cluster LOD hierarchies", single header (`CLUSTERLOD_IMPLEMENTATION`), MIT, copyright 2016-2026. Public API: `clodDefaultConfig(max_triangles)`, `clodDefaultConfigRT(max_triangles)`, `clodBuild(config, mesh, context, output_callback)`, `clodLocalIndices`, `clodBuildHierarchyBound`, `clodBuildHierarchy(nodes, groups, group_count, node_width, level_count)` — [clusterlod.h](https://github.com/zeux/meshoptimizer/blob/master/demo/clusterlod.h)
- Defaults from `clodDefaultConfig(N)`: `max_vertices = N`, `min_triangles = N/3`, `max_triangles = N`, `partition_size = 16`, `partition_spatial = true`, `cluster_split_factor = 2.0`, `simplify_ratio = 0.5`, `simplify_threshold = 0.85`, `simplify_error_merge_previous = 1.0`, `simplify_error_factor_sloppy = 2.0`, `simplify_error_clamped = true`, `simplify_permissive = true`, `simplify_fallback_sloppy = true`, `optimize_clusters = true` — [clusterlod.h](https://github.com/zeux/meshoptimizer/blob/master/demo/clusterlod.h)
- Loop: `meshopt_generatePositionRemap`, then initial clusters with `meshopt_buildMeshletsFlex` (or `meshopt_buildMeshletsSpatial` in the ray-tracing config), then `while (clusters.size() > 1)`: group with `meshopt_partitionClusters`; lock every vertex that appears in more than one group (through `vertex_lock`, not the `LockBorder` flag); simplify each group to `simplify_ratio` with `meshopt_simplifyWithAttributes` using `meshopt_SimplifySparse | meshopt_SimplifyErrorAbsolute` plus `ErrorClamped` and `Permissive` by default; if still too big, fall back to `meshopt_simplifySloppy` (error multiplied by `simplify_error_factor_sloppy`); if the result is larger than `simplify_threshold` (0.85) of the input the group is emitted as terminal with error `FLT_MAX` (comment: "simplification is stuck; abandon the merge"); otherwise the group error is made monotonic as `max(prev * merge_previous, error) + error * merge_additive` and the result is split into clusters again — [clusterlod.h](https://github.com/zeux/meshoptimizer/blob/master/demo/clusterlod.h)
- `meshopt_simplifyWithUpdate` is not called anywhere in `clusterlod.h` (the hierarchy keeps original vertices) — [clusterlod.h](https://github.com/zeux/meshoptimizer/blob/master/demo/clusterlod.h)
- `demo/nanite.cpp` still exists but is now a test and analysis harness for `clusterlod.h`: it calls `clodBuild` with `clodDefaultConfig(128)`, builds a BVH over groups with node width 8, prints per-level statistics (clusters, groups, percent full clusters, stuck clusters and triangles) and simulates a cut with `bounds.error / (d > camera_znear ? d : camera_znear) * (camera_proj * 0.5f)` against a threshold; it prints no timings. Comments: "For reference, see the original Nanite paper: Brian Karis. Nanite: A Deep Dive. 2021" and "for simplicity, we ignore perspective distortion and use rotationally invariant projection size estimation" — [demo/nanite.cpp](https://github.com/zeux/meshoptimizer/blob/master/demo/nanite.cpp)
- NVIDIA's `vk_lod_clusters` sample (Apache-2.0) uses "a lightly modified copy of meshoptimizer's single header clusterlod.h"; it rasterises through mesh shaders or a compute-shader rasteriser (`--swraster`) for very small clusters, ray-traces through `VK_NV_cluster_acceleration_structure`, and streams groups from RAM to VRAM; its Junkworld scene has "2.0 M instances of 6,712 unique meshes" — [nvpro-samples/vk_lod_clusters](https://github.com/nvpro-samples/vk_lod_clusters)

JavaScript / WebAssembly package (exactly what is exposed)
- Subpath exports of npm 1.3.0: `.`, `./decoder` (`meshopt_decoder.mjs`), `./encoder`, `./simplifier` (`meshopt_simplifier.js`), `./clusterizer` (`meshopt_clusterizer.js`), `./tangents`, `./decoder.cjs` — [npm registry: meshoptimizer](https://registry.npmjs.org/meshoptimizer)
- Each component is an ES module exporting an object with `supported` and a `ready` promise; functions are synchronous and block the caller; "only the decoder has an async, WebWorker-based API" (`useWorkers`, `decodeGltfBufferAsync`) — [meshoptimizer js/README](https://github.com/zeux/meshoptimizer/blob/master/js/README.md)
- `MeshoptSimplifier`: `simplify(indices, positions, stride, target_index_count, target_error, flags?)`, `simplifyWithAttributes(..., attribute_weights, vertex_lock: Uint8Array | null, target_index_count, target_error, flags?)`, `simplifyWithUpdate(...)` (in place, needs `compactMesh` afterwards), `simplifySloppy(..., vertex_lock, ...)`, `simplifyPrune`, `simplifyPoints`, `compactMesh`, `getScale`, and (since v1.0) `generatePositionRemap`. Flags accepted: `'LockBorder'`, `'ErrorAbsolute'`, `'Sparse'`, `'Prune'`, `'Regularize'`, `'RegularizeLight'`, `'Permissive'` — [meshoptimizer js/README](https://github.com/zeux/meshoptimizer/blob/master/js/README.md); [meshoptimizer releases](https://github.com/zeux/meshoptimizer/releases)
- `MeshoptClusterizer`: `buildMeshlets` (`max_vertices` ≤ 256, `max_triangles` ≤ 512), `buildMeshletsFlex`, `buildMeshletsSpatial`, `extractMeshlet`, `computeMeshletBounds`, `computeClusterBounds`, `computeSphereBounds` — [meshoptimizer js/README](https://github.com/zeux/meshoptimizer/blob/master/js/README.md)
- The clusterizer module's source returns exactly `{ ready, supported, buildMeshlets, buildMeshletsFlex, buildMeshletsSpatial, extractMeshlet, computeClusterBounds, computeMeshletBounds, computeSphereBounds }`; `meshopt_partitionClusters` does not appear in it, there is no hierarchy function, the WebAssembly is embedded as a packed string, and the module has no Worker or threading code — [js/meshopt_clusterizer.js](https://github.com/zeux/meshoptimizer/blob/master/js/meshopt_clusterizer.js)
- `MeshoptClusterizer` was added to the JS package in v0.22 (Oct 2024); `simplifyWithUpdate`, `simplifySloppy` and the flags were exposed in v0.25; `buildMeshletsFlex` / `buildMeshletsSpatial` in v1.0 — [meshoptimizer releases](https://github.com/zeux/meshoptimizer/releases)
- Two browser projects already build the hierarchy client-side: Scthe/nanite-webgpu uses "WebAssembly builds of meshoptimizer and METIS" (METIS supplies the grouping), and three-virtual-geometry depends on `meshoptimizer ^1.3.0` only and groups meshlets "about 12 at a time by a 'greedy region-growing partition'" written by its author — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu); [three-virtual-geometry how-it-works](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/how-it-works.md); [npm registry: three-virtual-geometry](https://registry.npmjs.org/three-virtual-geometry)

Throughput and memory
- "Billions of triangles in minutes" (30 Sep 2025): NVIDIA Zorah as glTF is "1.64B triangles, 18.9B triangles with instancing", 36.1 GB on disk. On an AMD Ryzen 7950X (16C/32T, 192 GB DDR5) with 16 threads the cluster-LOD build went from about 9m 20s (raster config) and 7m 10s (ray-tracing config) to 2m 56s (raster) and 2m 35s (ray-tracing, Linux, with a per-thread allocator cache), "around 3.5x speedup from our initial baseline". Integrated in `vk_lod_clusters` with `clusterlod.h`, including serialisation: about 3m 20s. Peak memory about 45 GB after sorting meshes largest-first (54.6 GB before). NVIDIA's own sample earlier took about 30 minutes on 7 threads — [zeux blog source, 2025-09-30](https://raw.githubusercontent.com/zeux/zeux.github.io/master/_posts/2025-09-30-billions-of-triangles-in-minutes.md) (published at zeux.io/2025/09/30/billions-of-triangles-in-minutes/)
- Where the time went: the biggest fix was not algorithmic but removing O(vertex_count) `memset`s per subset in the clusterizers ("only initializing the array entries used by the index buffer"), 9m 20s to 3m 31s; then largest-first scheduling (CPU utilisation 1240–1260% to 1574% on 16 threads), SIMD box merging (about 9% overall on x64; on Apple M4 "on the order of 2x+ speedup for clusterization alone"), a Morton pre-sort (about 5%), and a thread-local arena. The spatial clusterizer took about two-thirds of the ray-tracing build at the 3m 07s stage. The post gives no triangles-per-second-per-thread figure and no simplification-only rate — [zeux blog source, 2025-09-30](https://raw.githubusercontent.com/zeux/zeux.github.io/master/_posts/2025-09-30-billions-of-triangles-in-minutes.md)
- "Billions of triangles redux" (30 Sep 2026): reprocessing the 2026 Zorah scene (about 1.6B triangles, about 32 GB glTF) from scratch takes "~3m 45s across 16 cores of an AMD Ryzen 7950X, running in 105W Eco mode", now including attribute processing and compression. The processed cluster file holds about 3.26B triangles (roughly twice the original, since each DAG level halves the count) in about 54.9 GB before meshlet compression and 47.0 GB after; the meshlet codec brings triangle indices from 9.8 GB to about 2.6 GB, "about 6.5 bits per triangle". The sloppy fallback was used for about 0.01% of simplified groups. Clamped attribute error cut streamed geometry memory by about 30–35% (996 MB to 678 MB at the default camera). 128-triangle clusters with up to 128 vertices. Kapoulkine writes he is "not sure" all engines should adopt clustered LOD — [zeux blog source, 2026-09-30](https://raw.githubusercontent.com/zeux/zeux.github.io/master/_posts/2026-09-30-billions-of-triangles-redux.md)
- In-browser build times reported by three-virtual-geometry (JavaScript plus meshoptimizer WebAssembly, hardware not stated): "About 0.3 s for a 50k-triangle tree" and "a few seconds for a multi-million-triangle mesh"; loading a cached build is "15 to 25 times faster than building"; 13 rock scans built in the browser on first visit take "a few minutes" — [three-virtual-geometry caching guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/caching.md); [three-virtual-geometry performance guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/performance.md)
- Bevy's own converter (meshoptimizer plus METIS) is documented as "very slow, and should be done ahead of time, and not at runtime" — [bevy from_mesh.rs](https://github.com/bevyengine/bevy/blob/main/crates/bevy_pbr/src/meshlet/from_mesh.rs)
- Meshlet size trade-off measured by Kapoulkine: larger meshlets reuse vertices better (best case 64 vertices / 98 triangles has ACMR 0.65, 256 vertices / 450 triangles has 0.57) but cull worse ("occlusion culling efficiency drops from ~80% for a meshlet with size 64 to ~66% for a meshlet with size 256 (triangles)"; backface cone culling drops to 14% at 64 triangles and 3% at 256) — [zeux blog source, 2023-01-16](https://raw.githubusercontent.com/zeux/zeux.github.io/master/_posts/2023-01-16-meshlet-size-tradeoffs.md)

### Inferences
- Derived native throughput for a full DAG build: 1.64B source triangles in 155 s is about 10.6M triangles/s on 16 threads, about 0.66M source triangles/s per thread (ray-tracing config); 176 s gives about 0.58M/s per thread (raster config); the 2026 run with attributes and compression in eco mode gives about 0.44M/s per thread. At those rates a 200,000-triangle asset costs roughly 0.3 to 0.5 s of one native thread and a 10-million-triangle asset roughly 15 to 25 s. These are whole-scene averages on a desktop CPU, not per-mesh measurements.
- The only in-browser figure (three-virtual-geometry, 50k triangles in about 0.3 s, about 170k triangles/s derived) suggests a 200k-triangle asset builds in the order of one second in a worker on a recent Mac, and that small assets are dominated by fixed overhead. A 10-million-triangle asset would be tens of seconds of one worker; assets are independent, so a worker pool scales across them (each worker instantiates its own WebAssembly module; nothing in the package needs shared memory).
- A full hierarchy can be built from JavaScript with the stock npm package because everything except grouping is exposed: `buildMeshletsFlex`, `simplifyWithAttributes` with a `vertex_lock` array (to lock vertices shared between groups, as `clusterlod.h` and Bevy do), `'Sparse'` and `'ErrorAbsolute'` flags, `simplifySloppy` as fallback, `computeClusterBounds`, `computeSphereBounds`, `generatePositionRemap`. Missing from JavaScript: `meshopt_partitionClusters`, `clodBuild`, `clodBuildHierarchy`, `meshopt_spatialClusterPoints`, the meshlet codec, and (not listed in the JS README) the `ErrorClamped` and `PreserveFolds` flags.
- The alternative is to compile `clusterlod.h` plus the meshoptimizer sources to a private WebAssembly module: both are dependency-free C/C++ under MIT and the library already ships its own WebAssembly builds of the same code, so nothing in the sources suggests a blocker; I found no published build of this kind.
- A hierarchy roughly doubles triangle storage (3.26B stored for 1.6B source) and stores vertices per cluster. Derived from the Zorah figures: about 33 bytes per source triangle uncompressed (54.9 GB / 1.64B), about 29 bytes with the meshlet codec. Bevy's bunny (144,042 triangles, 4.5 MB in memory in 0.15) gives about 31 bytes per source triangle, so the two agree. For a 200k-triangle asset that is about 6 to 7 MB before any quantisation of your own.
- "Stuck" simplification is designed for, not eliminated: `clusterlod.h` abandons a merge when it cannot reach 85% and Bevy when it cannot reach 60%, leaving more than one root. With permissive mode and the sloppy fallback, Zorah needed the fallback for only 0.01% of groups, which is the best published evidence that the 2026 library copes with hard meshes.

### Gaps
- No source gives single-thread triangles-per-second for `meshopt_simplify`, `meshopt_buildMeshlets*` or a hierarchy build in isolation; the README has no throughput figures and the v1.0 announcement page (meshoptimizer.org/v1) was unreachable. The per-thread rates above are derived from whole-scene wall-clock times.
- No measurement of the WebAssembly build's speed relative to native was found, nor whether the simplifier and clusterizer modules use WebAssembly SIMD (the README states SIMD only for the decoder).
- I found no issue or roadmap item about exposing `meshopt_partitionClusters` or `clusterlod.h` to JavaScript (GitHub issue search was not available in this session).
- `nanite.cpp` prints no timings, so there are no "nanite.cpp demo" throughput numbers to report.

## 2. Bevy's virtual geometry ("meshlets") by JMS55

### Takeaway
Bevy's meshlet renderer is the most complete open Nanite-style system on wgpu (cluster DAG, BVH culling since 0.17, two-pass occlusion culling, visibility buffer, compute software rasteriser), but it is native-only: it needs 64-bit texture atomics and other wgpu features that WebGPU does not have, supports only the Vulkan and Metal backends, and its author moved to other work after Bevy 0.16. Its public history is the best record of what goes wrong: locked borders stalling simplification, stuck clusters, a hand-waved error metric, per-cluster culling as the bottleneck, and a preprocessing step documented as too slow for run time.

### Cited Findings

The blog series
- JMS55's blog has three virtual-geometry posts: Bevy 0.14 (9 Jun 2024), 0.15 (14 Nov 2024) and 0.16 (27 Mar 2025). There is no virtual-geometry post for 0.17 or later; the posts for 0.17 (20 Sep 2025), 0.18 (27 Dec 2025), 0.19 (12 Apr 2026) and 0.20 (18 Sep 2026) are about Solari, his real-time path tracer — [jms55.github.io source, posts directory](https://github.com/JMS55/jms55.github.io/tree/main/content/posts)

Bevy 0.14 (first version)
- Build: meshlets from `meshopt-rs`, capped at 64 vertices and 64 triangles; grouped with METIS aiming for "roughly 4" meshlets per group; each group simplified with meshoptimizer `simplify()` and re-split. Error is meshoptimizer's QEM value scaled to object space, treated as maximum vertex displacement and accumulated; only positions are considered; the author calls it "handwavy" and says "Perceptual simplification is very much an unsolved problem." The DAG usually does not reach one root: "In practice, my current code can't get to that point for most meshes." — [Virtual Geometry in Bevy 0.14](https://jms55.github.io/posts/2024-06-09-virtual-geometry-bevy-0-14) (read from [source](https://raw.githubusercontent.com/JMS55/jms55.github.io/main/content/posts/2024_06_09_virtual_geometry_bevy_0_14/index.md))
- Runtime: a cluster renders if its own error projects to less than 1 pixel and its parent's does not; a compute pass maps cluster ids to instance and meshlet ids; two-pass occlusion culling against the previous frame's depth pyramid; visibility buffer R32Uint (cluster and triangle ids packed 26 + 6 bits); one fullscreen triangle per material for shading — [Virtual Geometry in Bevy 0.14](https://jms55.github.io/posts/2024-06-09-virtual-geometry-bevy-0-14)
- Drawing: one `draw_indirect` call; a compute pass writes a per-triangle buffer at 4 bytes per triangle and the vertex shader pulls from it. An indexed draw was about 10–20% faster but needed up to 12 bytes per triangle. Rejected alternatives: NaN-padded fixed 64-vertex draws "performed poorly, since dummy triangles consumed fixed-function time"; multi-draw indirect with one sub-draw per cluster performed poorly because of command processing overhead; uploading per-cluster data from the CPU would have cost about 7.63 ms per frame — [Virtual Geometry in Bevy 0.14](https://jms55.github.io/posts/2024-06-09-virtual-geometry-bevy-0-14)
- Measured: 3,092 Stanford bunnies of 144,042 triangles each, RTX 3080, 2240×1260: fill cluster buffers 0.22 ms, cull pass 1 0.49 ms, raster pass 1 1.85 ms, total about 2.78 ms of GPU time without material shading — [Virtual Geometry in Bevy 0.14](https://jms55.github.io/posts/2024-06-09-virtual-geometry-bevy-0-14)

Bevy 0.15 (rewrite, with Kapoulkine's help)
- Software rasteriser in a compute shader, one thread per triangle, writing with `atomicMax()` into a 64-bit visibility word: depth in the upper 32 bits, cluster and triangle ids in the lower 32. Clusters whose screen-space bounding box is "< 64 pixels on both axis" go to software; larger ones and any cluster crossing the near plane go to a hardware draw with a fixed vertex count per cluster (the post gives 64 × 3) in which dummy vertices discard unused triangles. Depends on u64 atomics from wgpu 22 — [Virtual Geometry in Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15) (read from [source](https://raw.githubusercontent.com/JMS55/jms55.github.io/main/content/posts/2024_11_14_virtual_geometry_bevy_0_15/index.md))
- DAG quality fixes: meshlets grew to 255 vertices / 128 triangles; group size went from 4 to 8, which "improved simplification quality a lot"; locking only the vertices on meshlet-group borders instead of using meshoptimizer's `LOCK_BORDER` lets the hierarchy reduce to 1–3 meshlets at the top; normals are passed to `meshopt_simplifyWithAttributes()`. The bunny's DAG went from 7 levels ending at 19 meshlets (0.14) to 12 levels ending at a single meshlet (0.15); fill rate at later levels went from as low as 20% to a worst case of 76%. "For an ideal DAG, we want half as many meshlets at each LOD level." — [Virtual Geometry in Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15)
- Still wrong: UV deformation is not in the error; position/normal weights are "completely arbitrary"; "a lot of the time we still have to deal with stuck triangles that never get simplified when processing complex meshes"; the software rasteriser has no fixed-point math or top-left rule; a scene is limited to 2^25 clusters (1,042 cliff instances already produce 33,570,114) — [Virtual Geometry in Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15)
- Compression: per-meshlet vertex copies, positions as a bitstream quantised to 1/16 cm by default, octahedral normals, tangents derived in the shader; a test mesh dropped from 110 MB to 64 MB in memory; bunny 3.61 MB on disk and 4.5 MB in memory, cliff 49.83 MB on disk and 63.0 MB in memory — [Virtual Geometry in Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15)
- Measured (3,375 bunnies in a 15×15×15 cube, 2240×1260, RTX 3080): total visibility-buffer time 4.97 ms (0.14) to 0.93 ms (0.15), "almost 5x faster"; rasterisation 3.44 ms (hardware, 0.14) to 0.42 ms (software) plus under 0.01 ms (hardware); first culling pass 0.99 ms to 0.19 ms. Cliff scene (847 instances): 2.32 ms total, of which the first culling pass is 1.27 ms. "Culling is the clear bottleneck", because the cluster-selection pass dispatches a thread per cluster — [Virtual Geometry in Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15)
- Kapoulkine's contributions: converter performance and determinism (PRs #13904, #13913, #14038), a depth-pyramid fix, and the LOD selection code from his `nanite.cpp` demo (PR #15846) — [Virtual Geometry in Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15)

Bevy 0.16
- LOD-0 meshlets are now made with METIS instead of `meshopt_buildMeshlets()`, because "Minimizing shared vertices between meshlets when clustering triangles is the same problem as minimizing shared vertices between meshlet groups when grouping meshlets"; with METIS UFactor 1 and a partition count of `number_of_triangles.div_ceil(126)` the old DAG's tiny "stuck" meshlets disappear. The visibility buffer moved to an R64Uint storage texture with texture atomics. Current code on `main` (read 16 Nov 2026)
- `MeshletPlugin` requires "a fairly recent GPU" with `WgpuFeatures::TEXTURE_INT64_ATOMIC`; `required_wgpu_features()` lists `TEXTURE_INT64_ATOMIC`, `TEXTURE_ATOMIC`, `SHADER_INT64`, `SUBGROUP`, `DEPTH_CLIP_CONTROL`, `IMMEDIATES`; "Only the Vulkan and Metal backends are supported"; no MSAA; if a feature is missing the plugin logs an error and exits. Shaders include `cull_instances`, `cull_bvh`, `cull_clusters`, `visibility_buffer_software_raster`, `visibility_buffer_hardware_raster`. `cluster_buffer_slots` costs 4 bytes each and must not exceed 2^25 — [bevy meshlet/mod.rs](https://github.com/bevyengine/bevy/blob/main/crates/bevy_pbr/src/meshlet/mod.rs)
- `MeshletMesh::from_mesh` today: METIS for both triangle-to-meshlet partitioning (seed 17, UFactor 1) and meshlet grouping (UFactor 200); `TARGET_MESHLETS_PER_GROUP = 8`; meshlets up to 256 vertices / 128 triangles; each group simplified toward half its indices with `simplify_with_attributes_and_locks`, flags `Sparse | ErrorAbsolute`, normals as attributes with weights `[0.5; 3]`; a vertex used by more than one group is locked; `SIMPLIFICATION_FAILURE_PERCENTAGE = 0.60` (a group that keeps more than 60% of its triangles is rejected); stuck groups are retried when `passed_tris > stuck_tris / 3` and otherwise appended as a final level; group error is forced to be at least its children's; a BVH8 is built over groups. It does not call `buildMeshletsFlex` or meshopt's `partition_clusters`. Requirements: triangle list, indices, exactly `{POSITION, NORMAL, UV_0}`. Documented as "very slow, and should be done ahead of time, and not at runtime." TODOs mention spatial-proximity weighting and Nanite's group sizes of 8 to 32 — [bevy meshlet/from_mesh.rs](https://github.com/bevyengine/bevy/blob/main/crates/bevy_pbr/src/meshlet/from_mesh.rs)

- JMS55 (Hacker News, early 2025): "For virtual geometry specifically, it makes use of 64-bit integers and atomics, which are not supported on WebGPU at the moment, only the native Vulkan/DirectX/Metal backends." (search snippet) — [HN thread mirror](https://hn.svelte.dev/item/42974461)

### Inferences
- Bevy's meshlets cannot run in any browser today: its 64-bit requirements (`TEXTURE_INT64_ATOMIC`, `SHADER_INT64`) have no WebGPU equivalent, and the code itself restricts the plugin to Vulkan and Metal. (`IMMEDIATES` is the least of the obstacles: gpuweb has an `immediate-data.md` proposal and a search result shows a Chrome "Intent to Ship: WebGPU: Immediates" thread, [blink-dev](https://groups.google.com/a/chromium.org/g/Blink-dev/c/8LdEcW1CkNo), not opened.) What transfers to a browser engine is the design record, not the code.
- The three DAG lessons that every later implementation repeats: (1) lock only vertices shared between groups, never all topological borders (`LOCK_BORDER` on a group stops simplification at seams and open edges); (2) groups of 8 or more clusters simplify much better than groups of 4; (3) accept that some groups will not simplify and give them a defined fate (terminal group or retry), because a threshold test is cheaper than chasing a perfect DAG.
- The per-cluster dispatch that Bevy 0.15 used (one thread per cluster of every instance) is the first thing to break at scale: it was the bottleneck at about 30 million clusters and hit a hard 2^25 limit. For hundreds of millions of instances the selection must be hierarchical (instance cells, then a BVH or level table per mesh), which is what Bevy 0.17 and three-virtual-geometry both do.
- Bevy's draw strategy history is directly relevant to an engine that already vertex-pulls: a compute-written per-triangle list with one indirect draw worked at 4 bytes per visible triangle; fixed-size padded cluster draws wasted fixed-function time on dummy triangles when used for everything, but were kept for the minority of large clusters once small ones went to a software rasteriser.

### Gaps
- I could not confirm from a primary page whether the meshlet feature is still labelled experimental in Bevy 0.18–0.20, or what (if anything) changed in the meshlet code in those releases; the evidence is the code on `main`, the 0.17.3 feature list and the author's August 2026 statement that he might "potentially go back" to it.
- No performance numbers were found for the 0.17 BVH culling.
- No build-time figures for Bevy's converter exist in the sources beyond "very slow".
- No frame times on Apple GPUs (Metal backend) were found.

## 3. Scthe/nanite-webgpu

### Takeaway
A 2024 MIT-licensed browser demo (Chrome only) that does the whole pipeline client-side: meshoptimizer and METIS in WebAssembly build the meshlet DAG, compute shaders cull instances and meshlets, small meshlets go through a WGSL software rasteriser that squeezes 16-bit depth and normals into one u32 because WebGPU has no 64-bit atomics, and distant instances become billboard impostors. Its README is unusually frank that the simplification and error metric are the unsolved parts, and it publishes scene sizes (up to 1.7 billion instanced triangles) but no frame rates.

### Cited Findings
- Features: meshlet LOD hierarchy preprocessed in the browser using "WebAssembly builds of meshoptimizer and METIS", with a file exporter to skip preprocessing on reload; software rasteriser; billboard impostors (12 images around the up axis, blended with dithering, storing diffuse and normal; "Does not handle up/down views"); per-instance and per-meshlet frustum and occlusion culling; a switch between GPU-driven rendering and a "naive CPU implementation"; optional vertex position quantisation; MIT licence — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- Software rasteriser: "WebGPU does not support `atomic<u64>`, so I had to compress the data to fit into 32 bits": depth as `u16` plus octahedron-encoded normals as `2 * u8`. The author calls 16-bit depth "not a great idea" that "produces **tons** of artifacts like z-fighting or leaks". "No visibility buffer. It's not possible with the `atomic<u64>` limitation that I have." — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- Occlusion culling "is just a depth pyramid from the previous frame's depth buffer", with no reprojection and no two-pass culling. "For meshlet culling and LOD selection, I dispatch thread per-meshlet." No BVH over instances: "I just take all instances and frustum + occlusion cull them." Per-meshlet backface cone culling was implemented and then removed (gains "limited"; computing the cones "took 30% of the whole preprocessing step") — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- Demo scenes: Jinx 120×120 instances, 640M triangles (one Jinx: 44k simplified to 3k, 59 root meshlets); Lucy and dragons 70×70 each, 1.7B triangles, about 98% software-rasterised; Lucy 110×110, 1.2B (100k simplified to 86 triangles, one root meshlet); dragons 70×70, 1.2B (250k simplified to 102); bunnies 500×500, 1.2B (5k simplified to 96). The README says software rasterisation is "much faster than hardware" for the 1.7B scene — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- No frame rates or hardware are given: "FPS might fluctuate due to the browser's enforced VSync. Use the 'Profile' button instead." — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- Limitations listed by the author: the error metric is "just a simple projected simplification error" and "not a great metric for Nanite"; "Meshlet simplification is.. simplistic" (a step is rejected if it removes too few triangles; "a lot of the meshlets did not reduce triangles that much"; the Mecha Doll model "stops with 180k triangles left" after the fifth level); no two-pass occlusion culling; no shadows or multiview; no work queue in shaders; "No VRAM eviction of unused LODs and streaming"; "No compression"; memory is preallocated and "is not scalable if you have many **different** objects"; per-instance memory is `instanceCount * bottomLevelMeshletsCount * sizeof(vec2u)` bytes, "not a scalable memory allocation" — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- Platform notes: "WebGPU is only available on Chrome!"; "In Chrome, WebGPU has a 128MB limit for storage buffers (can be raised if needed)" — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- Author's advice: use UE5 for production; without solving simplification and error metrics "you will end up with code similar to mine" — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- Activity: main development July to September 2024 (last documentation update 30 Sep 2024); one later commit on 9 May 2026, "Fix off-by-one bug in software rasterizer output indexing" — [Scthe/nanite-webgpu commits](https://github.com/Scthe/nanite-webgpu/commits/master)

### Inferences
- This repository proves three things for a browser: the DAG can be built client-side in WebAssembly; compute-shader culling of instances and meshlets works in WGSL; and a compute rasteriser with 32-bit `atomicMax` runs but cannot carry a visibility buffer, so it trades depth precision for payload and shows artefacts. It does not prove a frame rate, anything on Safari, or anything at more than about 250,000 instances.
- Its memory model (per instance × bottom-level meshlets) is the opposite of what hundreds of millions of instances need.
- It used old meshoptimizer (2024) without `partitionClusters`, permissive mode or the sloppy fallback, so its stalled hierarchies (180k triangles left on one model) are not evidence about the 2026 library.

### Gaps
- No frame rates, GPU models or preprocessing times are published.
- Whether it runs in Safari 26 or Firefox was not tested by the author (README predates both) and I found no third-party report.

## 4. three.js: implementations and experiments, the facilities that matter, and libraries for automatic discrete LOD

### Takeaway
There is now (since October 2026) one open, installable cluster-LOD library for three.js's WebGPU renderer, `three-virtual-geometry` (MIT, v0.1.3): meshoptimizer builds 128-triangle meshlets in the browser, TSL compute passes select and cull, and each mesh is one indexed indirect draw over storage-buffer data with hardware rasterisation only; its author reports over 100 fps on an M4 Pro in Chrome, but it is weeks old, has 3 stars and publishes no Safari or iOS results. In three.js itself the pieces that matter are `IndirectStorageBufferAttribute` with `geometry.setIndirect()` (one `drawIndirect`/`drawIndexedIndirect` per offset), storage buffers and TSL compute; `BatchedMesh` on the WebGPU backend is a JavaScript loop of one draw call per sub-draw and there is no multi-draw.

### Cited Findings

three-virtual-geometry (Elad Ben-Haim)
- npm `three-virtual-geometry`: "Virtual geometry for three.js WebGPU: automatic cluster LOD and GPU-driven culling for billions of triangles"; MIT; versions 0.1.0 to 0.1.2 on 2026-10-08 and 0.1.3 on 2026-10-10; peer dependency `three >=0.180.0`; dependency `meshoptimizer ^1.3.0` and no METIS. It states it is an independent implementation "based on public descriptions of the technique and the MIT-licensed nanite-webgpu project by Marcin Matuszczyk" — [npm registry: three-virtual-geometry](https://registry.npmjs.org/three-virtual-geometry)
- Build: "`buildVirtualMesh` turns a triangle mesh into a hierarchy (a DAG) of **meshlets**, clusters of up to 128 triangles" using meshoptimizer's `buildMeshlets`; neighbouring meshlets are grouped about 12 at a time by a "greedy region-growing partition"; each group is simplified to half its triangles with meshoptimizer's `simplify` with its outer border locked ("Locking the borders means neighbouring groups always meet exactly, at every level"); repeated until a few meshlets remain, below which the rest is halved down to a few triangles. For foliage it voxelises the full-detail mesh, extracts a surface, simplifies it and keeps whichever candidate has the smaller measured error; separate cards are simplified individually then thinned in pairs — [how-it-works guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/how-it-works.md)
- Selection: "draw(meshlet) = projectedError(meshlet) <= threshold < projectedError(parent)", threshold about one pixel; above a 2.5 px effective threshold, levels blend per pixel within a band using a dither pattern that temporal anti-aliasing averages into a cross-fade. Compute passes "through three.js TSL" per pool: cells, instances, meshlets, prefix, expand. "Instances are sorted along a Morton curve and grouped in cells of 128." Shadow maps get a second, coarser selection. Occlusion culling renders last frame's selection depth-only into a Hi-Z buffer, needs a perspective camera with standard depth and "turns itself off otherwise". A capacity controller reselects at a coarser threshold, up to two retries, when a cut does not fit the draw buffers — [how-it-works guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/how-it-works.md); [repository README](https://github.com/elad12390/three-virtual-geometry)
- Data and drawing: all vertices, meshlets, level tables and instances live in shared storage buffers of up to 128 MB per binding ("a WebGPU limit"); index values encode `drawSlot * 128 + localVertex`; each VirtualMesh is a three.js `Mesh` with an indexed indirect draw over its region of the pool's index buffer, and its `positionNode` decodes indices and fetches attributes from storage buffers, so node materials, lights, shadows, fog and tone mapping work unchanged. "One draw call per mesh, millions of instances." — [how-it-works guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/how-it-works.md); [repository README](https://github.com/elad12390/three-virtual-geometry)
- Self-reported benchmarks (MacBook Pro M4 Pro, Chrome 154, uncapped, 1 px error threshold, shadows on; frame-rate ranges over several camera views): Ruins, 5.7B full-detail triangles, 113k instances, 6.5M–9.0M triangles drawn per frame, 160–230 fps at 1080p and 103–158 fps at 4K; World (6 km), 37.5B, 3.0M instances, 8.3M–9.1M drawn, 147–150 fps at 1080p and 101–120 at 4K; Valley, 1.1B, 152k instances, 159–329 fps; glTF import, 5.1M triangles, 12k instances, 941–964 fps; stress test, 1.0M instances (39.5B), 177–1,404 fps; "at most 0.6 ms of CPU time per frame" — [repository README](https://github.com/elad12390/three-virtual-geometry); [npm registry: three-virtual-geometry](https://registry.npmjs.org/three-virtual-geometry)
- Caching and build cost: builds are stored in IndexedDB keyed by a hash of source data and build options, evicted least-recently-used above 512 MB; "About 0.3 s for a 50k-triangle tree" and "a few seconds for a multi-million-triangle mesh"; a `.vgeo` baked format (meshoptimizer vertex and index codecs plus deflate, "3 to 6 times smaller than the in-memory data") and a `vg-bake` command-line tool — [caching guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/caching.md)
- Stated limits: static meshes only (instances can move), one UV channel, "Hardware rasterization only (no software rasterizer for pixel-sized triangles)". Stated requirements: "three.js r180+ and a browser with WebGPU (Chrome or Edge 113+, Safari 26+, Firefox 141+ on Windows)". For weak GPUs: "raise `errorThreshold` to 1.5 to 2, or set a `triangleBudget`." Repository: 3 stars, 2 forks, 16 commits — [repository README](https://github.com/elad12390/three-virtual-geometry); [performance guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/performance.md)

three.js facilities (read from the `dev` branch, version 0.187.0)
- three.js `dev` is at version 0.187.0 with `./webgpu` and `./tsl` exports — [three.js package.json](https://github.com/mrdoob/three.js/blob/dev/package.json)
- `BufferGeometry.indirect`: "A (storage) buffer attribute which was generated with a compute shader and now defines indirect draw calls." "Can only be used with WebGPURenderer and a WebGPU backend." `setIndirect( indirect, indirectOffset = 0 )`; `indirectOffset` is "The offset, in bytes, into the indirect drawing buffer where the value data begins. If an array is provided, multiple indirect draw calls will be made for each offset." — [three.js BufferGeometry.js](https://github.com/mrdoob/three.js/blob/dev/src/core/BufferGeometry.js)
- `WebGPUBackend._draw()`: with an indirect buffer it calls `passEncoderGPU.drawIndexedIndirect( buffer, indirectOffsets[ i ] )` or `drawIndirect(...)`, one call per offset. For `BatchedMesh` it runs a JavaScript loop over `object._mergedDrawCount` issuing `passEncoderGPU.drawIndexed( counts[ i ], instanceCount, starts[ i ] / bytesPerElement, 0, firstInstance )` per sub-draw. Neither `multiDrawIndirect` nor `chromium-experimental-multi-draw-indirect` appears in the file. `requestDevice` requests every feature the adapter reports — [three.js WebGPUBackend.js](https://github.com/mrdoob/three.js/blob/dev/src/renderers/webgpu/WebGPUBackend.js)

As written, the example renders before it runs the computes, so the count lags one frame — [three.js webgpu_struct_drawindirect example](https://github.com/mrdoob/three.js/blob/dev/examples/webgpu_struct_drawindirect.html)

Libraries for automatic or semi-automatic discrete LOD
- `@three.ez/instanced-mesh` (`InstancedMesh2`, MIT): "an alternative version of `InstancedMesh` with enhanced features for performance and usability": per-instance frustum culling, a dynamic BVH, sorting, per-instance visibility, LOD and shadow LOD. LOD levels are added by hand with their own geometry and a distance (`addLOD(geometryMid, material, 50)`); the README says "Use simplified geometries for distant objects" and does not generate them — [agargaro/instanced-mesh](https://github.com/agargaro/instanced-mesh)

### Inferences
- three-virtual-geometry is the closest existing thing to the engine in question (three.js WebGPU, TSL compute, storage buffers, vertex pulling by decoding an index in `positionNode`, indirect draws), and it shows the whole approach fits inside three.js's public API at r180+. It is also brand new, single-author, tested by its author on one machine in Chrome, and builds on load from glTF rather than from procedurally generated meshes; treat its numbers as a promising self-report, not as evidence for Safari or iPhones.
- Its grouping is a home-made greedy partition with groups of about 12 and plain `simplify` with locked borders; it does not use `partitionClusters`, permissive mode or the sloppy fallback, so its hierarchy quality is probably below `clusterlod.h`'s. That it still reports one-pixel error at over 100 fps suggests the runtime side is less sensitive to DAG quality than the Bevy posts feared, at least for scanned rocks and statues.
- For an engine with very many unique meshes, "one draw call per mesh" over pooled buffers is the scalable shape in three.js today: `setIndirect` with an array of offsets gives several GPU-counted draws from one buffer, while `BatchedMesh` costs one JavaScript-issued draw per visible sub-draw.
- The discrete-LOD libraries do not generate LODs in the browser; the only automatic part available in JavaScript is meshoptimizer's simplifier itself. Index-only LODs that share one vertex array (as batched-mesh-extensions requires, and as Godot and Unity ship) are what `MeshoptSimplifier.simplify` produces natively.

## 5. WebGPU capability status in late 2026 (Chrome, Safari on macOS and iOS, Firefox)

### Takeaway
Compute shaders, storage buffers and single indirect draws (`drawIndirect`, `drawIndexedIndirect`) are core WebGPU and ship in Chrome 113+, Safari 26+ on macOS, iOS, iPadOS and visionOS, and Firefox 141+ on Windows and 147 on Apple-silicon Macs; that is enough for GPU-driven cluster culling and for a handful of draws whose counts the GPU writes. Still missing everywhere as a standard: multi-draw indirect (Chrome-only, experimental, behind a flag), mesh shaders (tagged post-v1) and 64-bit atomics (WGSL atomics are 32-bit; a `vec2u`-based 64-bit min/max proposal exists and Dawn is implementing it experimentally, but it is not shipped).

### Cited Findings

Atomics
- WGSL atomics are 32-bit only: an atomic type is `atomic<T>` where T is `i32` or `u32` (search snippet) — [Tour of WGSL: atomic types](https://google.github.io/tour-of-wgsl/types/atomics/atomic-types)
- Consequence in practice: "WebGPU does not support `atomic<u64>`, so I had to compress the data to fit into 32 bits" — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu). Bevy's software rasteriser writes with `atomicMax()` on a 64-bit word (depth in the upper 32 bits, ids in the lower 32) and therefore needs native features — [Virtual Geometry in Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15)
- The gpuweb proposal `atomic-64-min-max.md` (status line: merged; issue #5071, spec PR #5610, created 2025-09-15) defines a feature `atomic_vec2u_min_max`: `atomic<vec2u>` that "will actually map to a `u64` in all backends", with two built-ins `atomicStoreMin` and `atomicStoreMax` that return nothing, usable in compute or fragment stages and limited to storage buffers (not textures). Motivation: "min/max is useful if one is doing software (compute) GPU rendering". Native requirements cited: Vulkan `shaderBufferInt64Atomics` (about 87.7% of Linux and 31% of Android devices), D3D12 Shader Model 6.6 with `Int64ShaderOps`, and on Apple platforms Metal 2.4, where 64-bit atomics are restricted to min and max on `uint64_t` (the proposal names the Apple 9 GPU family) — [gpuweb proposal: atomic-64-min-max](https://github.com/gpuweb/gpuweb/blob/main/proposals/atomic-64-min-max.md)
- Dawn has commits titled "[dawn] Adding experimental atomic_vec2u_min_max feature for vulkan", "[tint] AtomicVec2u (64bit) for DX12 backend" and "Atomic 64 bit (as vec2u in wgsl) for MSL (metal)" (commit titles from search results; not opened) — [Dawn commit f8bb650](https://dawn.googlesource.com/dawn/+/f8bb650b474fcec02e883472cf4e31abb5f02dcc); [Dawn commit e2f0828](https://dawn.googlesource.com/dawn/+/e2f0828f7c6919dba0521a47c19fc44df88dbadc); [Dawn commit b620b2f](https://dawn.googlesource.com/dawn/+/b620b2fe514a5ee2e6a2d924fd998c514019da87)

Buffer sizes and other limits
- Specification defaults: `maxStorageBufferBindingSize` 134,217,728 bytes (128 MiB) and `maxBufferSize` 268,435,456 bytes (256 MiB) (MDN mirror, search snippet) — [GPUSupportedLimits (MDN mirror)](https://docs.w3cub.com/dom/gpusupportedlimits)
- WebKit `main` computes the adapter's `maxBufferSize` on iOS as the larger of the default and `min(1 GB, maxBufferLength / 3)`, and on macOS as the larger of `min(maxBufferLength, 1 GB)` and `min(INT_MAX, maxBufferLength / 3)`; `maxStorageBufferBindingSize` and `maxUniformBufferBindingSize` are set to the same value ("result->limits.maxStorageBufferBindingSize = maxBufferLength;"). Other limits for Apple6/Apple7/Mac2 families: `maxStorageBuffersPerShaderStage` 44, `maxComputeInvocationsPerWorkgroup` 1024, `maxComputeWorkgroupsPerDimension` 65535, `maxComputeWorkgroupStorageSize` 32 KB, `maxTextureDimension2D` 16384, `maxBindGroups` 11, `maxVertexBuffers` 12, `maxColorAttachments` 8 — [WebKit HardwareCapabilities.mm](https://github.com/WebKit/WebKit/blob/main/Source/WebGPU/WebGPU/HardwareCapabilities.mm)
- One field report: an iPhone 11 Pro Max reported `webgpu: true`, an Apple adapter with f16 support and `maxBufferSize` of 715,827,880 bytes; the same post reports that a 728 MB model download then failed at initialisation (anecdotal; the post's version details look inconsistent) (search snippet) — [HN mirror: "WebGPU feature detection was not enough to run small LLMs on phones"](https://hackernews-dynamic.seasondane.workers.dev/news/48624985)
- In practice projects stay within the default binding size: "In Chrome, WebGPU has a 128MB limit for storage buffers (can be raised if needed)" — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu); three-virtual-geometry starts a new pool when a 128 MB binding is full — [how-it-works guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/how-it-works.md)

### Inferences
- (a) GPU-driven cluster culling is fully available in Safari 26+: it needs only compute shaders, storage buffers, 32-bit atomics (for counters and compaction) and a depth pyramid. Two open projects do exactly this in WGSL/TSL. The constraint is structural, not API: selection must be hierarchical to cope with instance counts, and each storage binding should be assumed to be 128 MiB unless a larger limit is requested and granted (WebKit's adapter maximum is far higher: about 683 MiB on the one iPhone report, which equals a 2 GiB Metal buffer length divided by 3, and up to 1 GB or more on Macs).
- (b) Drawing a changing set of clusters in few draw calls is possible without multi-draw, in three ways that all use only core features: (1) one non-indexed `drawIndirect` whose vertex count the GPU writes, over a compute-written list of visible triangles or clusters, with vertex pulling (Bevy 0.14: 4 bytes per visible triangle); (2) one instanced `drawIndirect` whose instance count the GPU writes, each instance being a fixed-size cluster (`max_triangles × 3` vertices) with degenerate padding (Bevy 0.15's hardware path; wasteful if clusters are poorly filled); (3) one `drawIndexedIndirect` per mesh or pool over a compute-written index buffer (three-virtual-geometry). three.js 0.187 exposes all three through `IndirectStorageBufferAttribute` and `setIndirect`, including several indirect draws from one buffer via an offset array. `indirect-first-instance` appears always-on in WebKit's current source, but should be feature-tested rather than assumed.
- Multi-draw indirect should be treated as unavailable for a Safari target for the foreseeable future: it is Chrome-experimental, its investigation issue is closed as not planned, there is no proposal document, and Metal has no direct equivalent (it would be emulated with indirect command buffers).
- (c) A compute-shader software rasteriser is possible in Safari only with 32-bit `atomicMax`: either pack depth and payload into 32 bits (Scthe: 16-bit depth, visible artefacts, no visibility buffer) or, as an untested alternative that no source here demonstrates, rasterise twice (depth-only `atomicMax` on a u32, then a second pass that writes ids where depth matches). A true 64-bit visibility buffer has to wait for `atomic_vec2u_min_max`, which is specified as a proposal and being implemented in Dawn but has no shipping date in any browser, and whose Metal requirement (64-bit atomic min/max) may exclude older Apple GPUs.
- Mesh shaders are not coming to the web in a time frame that matters; every open browser implementation therefore uses either vertex pulling with indirect draws or compute rasterisation.

## 6. The cost of pixel-sized triangles on hardware rasterisers, especially Apple's tile-based deferred GPUs

### Takeaway
On desktop immediate-mode GPUs the evidence is consistent: a compute rasteriser beats the hardware path for pixel-sized triangles by a wide margin (Nanite's often-quoted average of about 3×; Bevy measured its raster pass falling from 3.44 ms to 0.42 ms when small clusters moved to software). For Apple GPUs I found no authoritative measurement: Apple documents only that every triangle is shaded and binned into a "Tiled Vertex Buffer" that "may cause a Partial Render if full", while the one data point from an Apple GPU (three-virtual-geometry on an M4 Pro, hardware rasterisation only) reports 6.5 to 9 million triangles per frame at 160 to 230 fps.

### Cited Findings
- Nanite routes clusters of small triangles to a software rasteriser that is cited as about three times faster on average than the hardware rasteriser, and clusters whose triangles are larger than about 32 pixels to hardware (secondary sources; the SIGGRAPH 2021 slides could not be opened) — [vrarwiki: Nanite](https://vrarwiki.com/wiki/Nanite); [CuRast paper, arXiv 2604.21749](https://arxiv.org/html/2604.21749v1); primary: [Karis, Stubbe, Wihlidal, "A Deep Dive into Nanite Virtualized Geometry", SIGGRAPH 2021](https://advances.realtimerendering.com/s2021/Karis_Nanite_SIGGRAPH_Advances_2021_final.pdf)
- Bevy 0.15, RTX 3080, 3,375 bunnies at 2240×1260: rasterisation went from 3.44 ms (all hardware, Bevy 0.14) to 0.42 ms software plus under 0.01 ms hardware; clusters under 64 pixels on both axes go to software — [Virtual Geometry in Bevy 0.15](https://jms55.github.io/posts/2024-11-14-virtual-geometry-bevy-0-15)
- Bevy 0.14: padded fixed-size cluster draws "performed poorly, since dummy triangles consumed fixed-function time"; an indexed draw was about 10–20% faster than the non-indexed per-triangle vertex-pulling draw — [Virtual Geometry in Bevy 0.14](https://jms55.github.io/posts/2024-06-09-virtual-geometry-bevy-0-14)
- Scthe: software rasterisation is "much faster than hardware" for the 1.7B-triangle scene, where about 98% of triangles are software-rasterised (Chrome, GPU not stated) — [Scthe/nanite-webgpu](https://github.com/Scthe/nanite-webgpu)
- NVIDIA's `vk_lod_clusters` offers a compute-shader rasteriser (`--swraster`) "for very small clusters" in addition to mesh shaders — [nvpro-samples/vk_lod_clusters](https://github.com/nvpro-samples/vk_lod_clusters)
- Apple GPU, hardware rasterisation only: three-virtual-geometry on a MacBook Pro M4 Pro in Chrome 154 at a 1-pixel error threshold with shadows on reports 6.5M–9.0M triangles drawn per frame at 160–230 fps at 1080p and 103–158 fps at 4K (Ruins), and 8.3M–9.1M at 147–150 fps (World); real scans draw "about 0.4 to 1.5 million triangles at one pixel of error" per frame (self-reported) — [three-virtual-geometry README](https://github.com/elad12390/three-virtual-geometry); [performance guide](https://github.com/elad12390/three-virtual-geometry/blob/main/docs/guide/performance.md)
- Apple, how its GPUs process geometry: "In the Tiling Phase, for the entire render pass, the GPU will split the viewport into a list of tiles, shade all of the vertices and, finally, bin the transformed primitives into a list of tiles." "The Tiled Vertex Buffer stores the Tiling phase output, which includes the post-transform vertex data, as well as other internal data." "But it may cause a Partial Render if full. A Partial Render is when the GPU splits the render pass in order to flush the contents of that buffer." "So the takeaway is for you to know that the Tiled Vertex Buffer exists, but don't worry too much over it." — [Apple, "Harness Apple GPUs with Metal", WWDC20 session 10602](https://developer.apple.com/videos/play/wwdc2020/10602/)
- Apple, on overdraw: "HSR allows the GPU to minimize overdraw by keeping track of the frontmost visible layer for each pixel." "HSR is both pixel perfect and submission order independent." The same talk warns about "the high number of small, translucent triangles which will have a lot of samples per pixel" with MSAA, and notes "the GPU does not have video memory. So bandwidth could be a problem if the content has not been tuned." — [Apple, WWDC20 session 10602](https://developer.apple.com/videos/play/wwdc2020/10602/)
- Apple: "the primitives are binned into screen-aligned small tiles and stored into the memory"; the vertex stage of a future render pass can run in parallel with the fragment stage of the current one — [Apple tech talk 602, "Metal 2 on A11 - Overview"](https://developer.apple.com/videos/play/tech-talks/602)
- Apple's TBDR article describes a TBDR GPU as "processing all of the geometry of a render pass at the same time and shading only the visible primitives" and shows the vertex stage writing to a tiled vertex buffer in external (device) memory; it gives no guidance on triangle size or vertex counts — [Apple: Tailor your apps for Apple GPUs and tile-based deferred rendering](https://developer.apple.com/documentation/metal/tailor-your-apps-for-apple-gpus-and-tile-based-deferred-rendering)
- A Beyond3D forum thread says PowerVR's performance recommendations advise avoiding small triangles to avoid thrashing the parameter buffer, and speculates about SIMD inefficiency with many small edges (forum discussion, search snippet, not authoritative) — [Beyond3D thread](https://forum.beyond3d.com/goto/post?id=2171236)
- Vertex-bound cost and cluster size: with good clustering a 64-vertex meshlet transforms about 0.65 vertices per triangle and a 256-vertex one about 0.57 (ACMR), against 3 per triangle for non-indexed vertex pulling without reuse — [zeux blog source, 2023-01-16](https://raw.githubusercontent.com/zeux/zeux.github.io/master/_posts/2023-01-16-meshlet-size-tradeoffs.md)

### Inferences
- Derived from the three-virtual-geometry report: 9.0M triangles × 160 fps is about 1.4 billion small triangles per second through the hardware rasteriser of an M4 Pro. A 1080p frame has about 2.07 million pixels, so 9.0M drawn triangles is more than four per pixel (the count was taken with shadows on and may include shadow passes, so it is not all main-view geometry). If accurate, a one-triangle-per-pixel budget at 1080p (about 2 million visible triangles, several million submitted) is well within 60 fps on that class of Mac with hardware rasterisation alone. An iPhone GPU is several times smaller and has far less memory bandwidth, and no source measures it.
- On a TBDR GPU the two usual costs of tiny triangles split differently from desktop: fragment overdraw is largely removed by hidden surface removal, but every submitted triangle still costs a vertex shade plus binning and occupies Tiled Vertex Buffer memory, and overflowing that buffer forces partial renders. So on Apple GPUs the quantity to control is submitted triangles per frame (after culling and LOD selection), more than pixel overdraw. This is reasoning from Apple's description, not a measurement.
- Because a software rasteriser in Safari is limited to 32-bit atomics (section 5), the practical route for Safari in late 2026 is hardware rasterisation with a triangle budget and an error threshold of one pixel or slightly more, which is exactly what three-virtual-geometry recommends for weak GPUs ("raise `errorThreshold` to 1.5 to 2, or set a `triangleBudget`").
- Non-indexed vertex pulling pays up to 3 vertex-shader invocations per triangle where an indexed cluster pays about 0.6; Bevy measured the difference at 10–20% of raster time on a desktop GPU. On a vertex-bound mobile GPU the gap may be larger, which argues for indexed draws over a compute-written index buffer, or for keeping vertex shaders very cheap.

### Gaps
- No authoritative Apple statement or third-party measurement of the cost of pixel-sized or sub-pixel triangles (quad overdraw, binning cost, parameter-buffer pressure) on Apple GPUs was found; Apple's public material says only that the Tiled Vertex Buffer exists and can force partial renders.
- The Nanite slides (the primary source for the 3× figure, the 32-pixel threshold and the quad-overdraw argument) could not be opened; the figures here are from secondary sources.
- The searches for ARM Mali and Imagination PowerVR written guidance on minimum triangle size could not be run (search budget exhausted); the Beyond3D item is hearsay.
- No iPhone or iPad measurement of any cluster-LOD renderer exists in the sources.

## 7. Simpler automatic LOD in shipping engines, for comparison (Godot 4, Unity 6, Unreal, Cesium 3D Tiles, Nexus)

### Takeaway
The engines that ship automatic LOD without a cluster hierarchy all do the same simple thing: at import, repeatedly halve the index buffer with a quadric simplifier (Godot and most likely Unity through meshoptimizer-style index-only LODs that share the original vertex buffer), store an error per level, and at run time pick one level per object from a screen-space error threshold of about one pixel. Cesium 3D Tiles and Nexus apply the same screen-space-error rule to a spatial tree of patches rather than to whole objects, which is the middle ground between discrete LOD and a cluster DAG.

### Cited Findings

Godot 4
- "The meshoptimizer library is used for LOD mesh generation behind the scenes." LODs are generated automatically on import for glTF, .blend, Collada and FBX scenes; "Mesh LOD generation can also take a while on complex meshes"; the process "may occasionally introduce rendering issues (especially in skinned meshes)" — [Godot docs: Mesh level of detail](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html) (read from [godot-docs source](https://raw.githubusercontent.com/godotengine/godot-docs/master/tutorials/3d/mesh_lod.rst))
- Selection uses a screen-space metric with a default threshold of 1 pixel, described as tuned to look perceptually lossless; it can be raised per viewport (`get_tree().root.mesh_lod_threshold = 4.0`) and biased per object with LOD Bias; higher camera FOV and lower resolution make selection more aggressive automatically. For MultiMesh and particles the AABB point closest to the camera decides, so "all instances will be drawn with the same LOD level at a given time" — [Godot docs: Mesh level of detail](https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html)
- `ImporterMesh::generate_lods` (master): merges vertices by position and attribute similarity; attributes are normals (and colours) with weight 1.0; loop while more than 24 indices, target half the current triangle count; flags always `SIMPLIFY_SPARSE` ("Does not change appearance, but speeds up subsequent iterations") and `SIMPLIFY_LOCK_BORDER` ("Lock geometric boundary in case the mesh is composed of multiple material subsets"), `SIMPLIFY_PRUNE` while allowed ("Remove small disconnected components"), `SIMPLIFY_REGULARIZE` for deformable meshes; no permissive mode and no sloppy fallback. Error accumulates as `current_error = MAX(current_error * 1.5f, step_error)` ("to limit the switching (pop) distance, we ensure the error grows by an arbitrary factor each iteration"). The loop stops if the result is empty, is at least 75% of the input, or the error exceeds `max_mesh_error = 1.0f`. Each level stores `distance = MAX(current_error * scale, CMP_EPSILON2)` and an index array remapped to the original vertex buffer, so LODs are index-only — [Godot importer_mesh.cpp](https://github.com/godotengine/godot/blob/master/scene/resources/3d/importer_mesh.cpp)
- A Godot issue reports that automatic LOD generation is only applied when importing 3D scenes, not to natively saved or run-time meshes (search snippet) — [godotengine/godot issue #57416](https://github.com/godotengine/godot/issues/57416)

Unity 6 (Mesh LOD, from Unity 6.2)
- "Mesh LOD provides a LOD generator that runs at model import time." "After selecting the triangles to keep for a LOD, the generator stores indices of the triangles in the index buffer of the original mesh. The generator doesn't add any new vertices. All LODs reuse the same vertex buffer." "Each subsequent LOD contains approximately half the number of indices as the previous one. The maximum increase in size of the original index buffer is 100%." The original mesh must have at least 256 triangles; only triangle topology; results can be poor on highly curved meshes or meshes made of many disconnected pieces; a Skinned Mesh Renderer deforms LOD0 whichever LOD is drawn; the range of the index buffer used by a level is a `MeshLodRange`; draw APIs without automatic selection take `forceMeshLod`; combining Mesh LOD with LOD Group "is not recommended" (search snippets of the Unity 6.2 manual) — [Unity manual: Mesh LOD introduction](https://docs.unity3d.com/6000.2/Documentation/Manual/lod/mesh-lod-introduction.html); [Unity manual: Mesh LOD generator](https://docs.unity3d.com/6000.2/Documentation/Manual/lod/mesh-lod-generator.html)
- Unity staff describe the generator as their own and say improving LOD generation is on the roadmap (search snippet) — [Unity Discussions: Mesh LOD 2025](https://discussions.unity.com/t/mesh-lod-2025/1620503)

Unreal Engine (automatic LOD generation, separate from Nanite)
- "The system uses quadratic mesh simplification to help generate the LODs for Static Meshes"; LOD count and reduction come from LOD Group presets (for example SmallProp), and with Auto Compute LOD Distances "the editor will automatically compute screen size values for the static mesh's LODs" (search snippets) — [Epic: Static Mesh Automatic LOD Generation](https://dev.epicgames.com/documentation/unreal-engine/static-mesh-automatic-lod-generation-in-unreal-engine); [Epic: UFbxImportUI bAutoComputeLodDistances](https://docs.unrealengine.com/4.26/en-US/API/Editor/UnrealEd/Factories/UFbxImportUI/bAutoComputeLodDistances/index.html)

Cesium 3D Tiles
- Geometric error is "a nonnegative number that specifies the error, in meters" of a tile's simplified representation; the root has the largest and leaves are at or near 0. Implementations consider "a maximum allowed Screen-Space Error (SSE), the error measured in pixels"; if the SSE of rendering a tile without its children "exceeds the maximum allowed, then the tile is refined and its children are considered for rendering". Refinement is REPLACE (children render "in place of" the parent) or ADD (parent and children render together) — [3D Tiles specification](https://github.com/CesiumGS/3d-tiles/blob/main/specification/README.adoc)
- CesiumJS computes, for a perspective camera: "error = (geometricError * height) / (distance * sseDenominator);" with `height = context.drawingBufferHeight * heightFraction` and `distance = Math.max(this._distanceToCamera, CesiumMath.EPSILON7)`, optionally reduced by a fog-based "dynamic screen space error" term and divided by the pixel ratio; leaf tiles return 0 — [CesiumJS Cesium3DTile.js](https://github.com/CesiumGS/cesium/blob/main/packages/engine/Source/Scene/Cesium3DTile.js)
- A tile's screen-space error "is roughly the number of pixels a sphere with radius equal to the tile's geometric error would cover"; a forum answer stresses that geometric error should be physically based, "derived from the decimation algorithm you're using" (search snippets) — [Cesium3DTileset.maximumScreenSpaceError (Kotlin wrapper docs)](https://jetbrains.github.io/kotlin-wrappers/kotlin-cesium-engine/cesium.engine/-cesium3-d-tileset/maximum-screen-space-error.html); [Cesium forum: Understanding geometric error](https://community.cesium.com/t/understanding-geometric-error/8480)

Nexus (CNR-ISTI Visual Computing Lab)
- "a c++/javascript library for creation and visualization of a batched multiresolution mesh"; features: multiresolution, large models, textures or per-vertex colour, streaming, compression, WebGL. Workflow: `.ply` → `nxsbuild` → `.nxs` → `nxscompress` → `.nxz` (compression saves about 90% of the size). Web use through 3DHOP or three.js, with a minimal example in the repository. C++ tools are GPL (depend on Qt and VCG); the JavaScript is MIT. 394 commits on master — [cnr-isti-vclab/nexus](https://github.com/cnr-isti-vclab/nexus)
- `nxsbuild` "generates a sequence of increasingly coarse partitions of the model, interleaved with simplification steps". Defaults: 32,768 faces per patch (`-f`; lower values give finer resolution control but reduce rendering performance and increase dataset size), 4,096 triangles in the top node (`-t`), quadric decimation (`-d`), decimation factor 0.5 between levels (`-s`), adaptive node splitting 0.333 (`-a`), 2,000 MB RAM budget (`-r`) — [nexus doc/nxsbuild.md](https://github.com/cnr-isti-vclab/nexus/blob/master/doc/nxsbuild.md)

### Inferences
- Comparison at a glance (my synthesis of the findings above and in sections 1 to 4):

| System | Unit that changes detail | How levels are made | Run-time rule | Cracks handled by | Build cost | Runs in a browser |
|---|---|---|---|---|---|---|
| Godot 4 mesh LOD | whole surface | meshoptimizer, index-only, halve until stuck (75%) or error > 1 | error × scale vs. pixel threshold (default 1 px) | none needed (whole object switches); pops | one simplifier pass chain | the same calls exist in `MeshoptSimplifier` |
| Unity 6 Mesh LOD | whole mesh | index-only, each level about half, at most +100% indices | automatic per renderer (details not retrieved) | none needed; pops | import time | not applicable |
| Unreal auto LOD | whole mesh | quadric simplification by LOD Group preset | auto-computed screen sizes | none needed; pops or dither | import time | not applicable |
| Cesium 3D Tiles | tile in a spatial tree | external tiler; geometric error per tile | SSE = geometricError × height / (distance × sseDenominator) vs. max | REPLACE refinement; seams between tiles are the tiler's problem | off-line | yes (CesiumJS) |
| Nexus | patch of about 32k triangles in a multiresolution DAG | partition + quadric halving per level | projected error per patch | patch boundaries consistent by construction | off-line C++ tool (GPL) | yes (WebGL, three.js loader) |
| Cluster DAG (clusterlod.h, Bevy, three-virtual-geometry) | cluster of about 128 triangles | group, lock shared vertices, halve, re-cluster | own error ≤ threshold < parent error, per cluster | locked group borders + monotonic error | about 0.5M triangles/s per native thread (derived) | yes, with compute + indirect draws |

- The discrete index-only scheme is the cheapest thing that is "automatic": about one extra index buffer in total (halving series sums to at most +100%), no extra vertices, no run-time data structure, and it is exactly what meshoptimizer's JavaScript simplifier produces. Its limits are the ones a cluster DAG exists to remove: one level per object (so very large objects are wrong somewhere), popping at switches, and no help once a mesh is larger than the screen.
- Godot's loop is a useful reference recipe for a browser worker because every call it makes exists in the npm package (`simplifyWithAttributes` with `'Sparse'`, `'LockBorder'`, `'Prune'`), and its stop conditions (75% rule, error growth factor 1.5) are simple and documented in code.
- Nexus shows that a patch-based multiresolution structure with 32k-triangle patches has run on WebGL for years without compute shaders; cluster DAGs shrink the patch to about 128 triangles and move selection to the GPU. Patch size is the dial between the two: bigger patches mean fewer selection decisions and draw records but coarser adaptation.

### Gaps
- Unity's run-time selection rule for Mesh LOD (threshold, bias, hysteresis) and the simplifier it uses were not retrieved (docs.unity3d.com unreachable; search budget exhausted).
- Cesium's default `maximumScreenSpaceError` (commonly quoted as 16) and the definition of `sseDenominator` were not confirmed from a primary page in this session; only a second-hand forum mention of 16 was found.
- Nexus: the target-error-in-pixels default of the web renderer, its cache design and the state of its three.js loader in 2026 were not retrieved; the repository page shows no releases or dates.
- Unreal: details of the reduction algorithm beyond "quadric mesh simplification", and current UE 5.x documentation text, are at search-snippet level only.
- No source compares these simple schemes against a cluster DAG with measurements on the same content.
