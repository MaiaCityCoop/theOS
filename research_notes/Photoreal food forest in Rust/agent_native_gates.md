## 1. Headless and offscreen rendering with wgpu and Bevy; CI runners; determinism pitfalls; how other engines handle golden images and tolerances

### Takeaway
Windowless, frame-exact capture is a documented path in Bevy 0.20 (render to an `Image` target, `Screenshot::image`, a CI-testing plugin with fixed frame time and frame-indexed events), and both Bevy and wgpu run GPU rendering tests today on GitHub-hosted `macos-26` (Metal), Linux (Mesa software Vulkan) and Windows (WARP/DX12). No surveyed engine achieves cross-GPU bit-exactness: every mature system keeps references per platform/adapter and adds a tolerance (FLIP mean/percentile in wgpu, per-channel plus local/global error in Unreal, deltaE/RMSE/incorrect-pixel ratio in Unity, multiple approved images plus fuzzy/Sobel matching in Skia Gold, a pinned software rasterizer in Filament).

### Cited Findings

**Bevy: versions and windowless rendering**
- [FACT] Bevy 0.20 was posted on 2026-10-08; docs.rs shows 0.20.1 dated 2026-10-28. Bevy 0.19 was posted on 2026-06-19 and replaced the RenderGraph with ECS schedules ("Render passes are now regular systems that run in schedules such as Core3d, Core2d"). Bevy 0.18 was released on 2026-01-13. — [Bevy 0.20 news](https://bevy.org/news/bevy-0-20/); [RenderDiagnosticsPlugin docs, 0.20.1](https://docs.rs/bevy/latest/bevy/render/diagnostic/struct.RenderDiagnosticsPlugin.html); [Bevy 0.19 news](https://bevy.org/news/bevy-0-19/); [Bevy 0.18 news](https://bevy.org/news/bevy-0-18/)
- [FACT] Bevy's `headless_renderer` example (main branch, read 2026-11-19) renders from a camera into a GPU image used as render target, copies it to a buffer, sends the data through a channel to the main world and saves each frame to a uniquely named file. The window is removed with `WindowPlugin { primary_window: None }`, `WinitPlugin` is disabled "because it panics in environments without a display server", and `ScheduleRunnerPlugin::run_loop` drives the app at 60 updates per second. — [headless_renderer.rs](https://github.com/bevyengine/bevy/blob/main/examples/app/headless_renderer.rs)
- [FACT] The same example needs 40 "pre-roll" frames before the scene is fully rendered; the count "depends on device speed, device load, and scene size", and with zero pre-roll the output passes through a transparent image, then black boxes, then the full scene. — [headless_renderer.rs](https://github.com/bevyengine/bevy/blob/main/examples/app/headless_renderer.rs)
- [FACT] The `Screenshot` component (Bevy 0.20.1) is `Screenshot(pub RenderTarget)` with constructors `window`, `primary_window`, `image(Handle<Image>)` and `texture_view`; capture is asynchronous (the result "may not be available on the spawning frame") and is delivered to an observer (`ScreenshotCaptured`, e.g. `save_to_disk`). The docs reference an `externally_driven_headless_renderer` example that spawns `Screenshot::image(...)`. — [Screenshot docs](https://docs.rs/bevy/latest/bevy/render/view/window/screenshot/struct.Screenshot.html)
- [FACT] `bevy::dev_tools::ci_testing` (0.20.1, features `bevy_ci_testing` + `bevy_dev_tools`): `CiTestingSetup.fixed_frame_time: Option<f32>` is "The amount of time in seconds between frame updates" and is applied through `TimeUpdateStrategy::ManualDuration`. — [CiTestingSetup](https://docs.rs/bevy/latest/bevy/dev_tools/ci_testing/struct.CiTestingSetup.html)
- [FACT] `CiTestingEvent` variants fired at configured frame numbers: `Screenshot` (saved as `screenshot-{current_frame}.png`), `ScreenshotAndExit`, `NamedScreenshot(String)`, `AppExit`, `StartScreenRecording`, `StopScreenRecording`, `MoveCamera { translation, rotation }` ("Smoothly moves the camera"), `Custom(String)`. There are no input-event variants. — [CiTestingEvent](https://docs.rs/bevy/latest/bevy/dev_tools/ci_testing/enum.CiTestingEvent.html)

**wgpu's own rendering tests**
- [FACT] Current wgpu docs are for 30.0.2. — [wgpu Features](https://docs.rs/wgpu/latest/wgpu/struct.Features.html)
- [FACT] wgpu example tests "use `nv-flip`'s image comparison through the wgpu example framework" to check outputs are "within tolerance of the expected output"; GPU tests have a parameter system for per-GPU support and expected failures caused by driver or wgpu bugs; Linux Vulkan CI sets `LVP_POISON_MEMORY=true` so uninitialised-memory bugs fail reliably. — [wgpu docs/testing.md](https://github.com/gfx-rs/wgpu/blob/trunk/docs/testing.md)
- [FACT] `wgpu_test::image`: `ComparisonType::Mean(f32)` fails when mean FLIP error exceeds the value; `ComparisonType::Percentile { percentile, threshold }` fails when that percentile exceeds the threshold. FLIP is run with `DEFAULT_PIXELS_PER_DEGREE`; mean, min, 25/50/75/95/99th percentiles and max are printed. Guidance in the doc comment: "Error thresholds will be different for every test, but good initial values to look at are in the [0.01, 0.1] range" and "The larger the area that might have inherent variance, the larger this base value is." — [wgpu_test image.rs](https://wgpu.rs/doc/src/wgpu_test/image.rs.html)
- [FACT] The same harness always writes `{stem}-{renderer}-actual.png` and a magma false-colour `-difference.png`, where `renderer` is `{backend}-{name}-{driver}`; it has no per-adapter thresholds; and if the reference PNG is missing or has the wrong size/format, it writes the test image out as the new reference and returns without comparing. — [wgpu_test image.rs](https://wgpu.rs/doc/src/wgpu_test/image.rs.html)
- [FACT] wgpu CI GPU-test jobs run on `macos-26`, `ubuntu-26.04` and `windows-2025`; Windows installs DXC, WARP, the Agility SDK, Mesa and the Vulkan SDK; Linux installs the Vulkan SDK and Mesa. A comment explains a Windows retry job: "Windows CI intermittently lands on hosts that stall for a minute or more at a time, which kills whichever tests happen to be running." — [wgpu ci.yml](https://github.com/gfx-rs/wgpu/blob/trunk/.github/workflows/ci.yml)

**Determinism pitfalls with documented evidence**
- [FACT] Temporal anti-aliasing: Unreal's default screenshot tolerance is "Low" because temporal anti-aliasing adds constant per-pixel variation; its "Disable Noisy Rendering Features" option turns off anti-aliasing, motion blur, screen-space reflections, eye adaptation (auto-exposure) and contact shadows for the capture. — [Unreal Screenshot Comparison Tool, UE 5.9 docs](https://dev.epicgames.com/documentation/unreal-engine/screenshot-comparison-tool-in-unreal-engine?lang=en-US)
- [FACT] Wall-clock time: Bevy fixes it with `fixed_frame_time` via `TimeUpdateStrategy::ManualDuration`; Godot's `--fixed-fps` (and `--write-movie`) "forces the reported delta in Node._process functions to be identical across frames, regardless of how long it actually took to render the frame." — [CiTestingSetup](https://docs.rs/bevy/latest/bevy/dev_tools/ci_testing/struct.CiTestingSetup.html); [Godot MovieWriter docs](https://docs.godotengine.org/ja/4.3/classes/class_moviewriter.html)
- [FACT] Asynchronous loading and pipeline warm-up: the Bevy headless example's 40 pre-roll frames depend on device speed, load and scene size (see above). — [headless_renderer.rs](https://github.com/bevyengine/bevy/blob/main/examples/app/headless_renderer.rs)
- [FACT] Cross-platform pixel differences: Filament keeps separate goldens for native and web because "The same scene rendered natively and in a browser does not produce the same pixels"; goldens are rendered on Linux/aarch64 and on other hosts (including macOS) "its comparison results are advisory"; the web path pins the browser build, the SwiftShader rasterizer and the render size, and "Changing any of them means regenerating the web goldens." — [Filament renderdiff](https://google.github.io/filament/dup/test_ci_renderdiff.html)
- [FACT] The WebGPU conformance suite's texel comparison defaults allow 1 ULP for normalised and for float formats (`maxDiffULPsForNormFormat: 1, maxDiffULPsForFloatFormat: 1`); its reftests use fuzzy matching (a 2023 change "reftests: Allow large totalPixels for fuzzy matching"). — [gpuweb/cts texture_test_utils.ts](https://chromium.googlesource.com/external/github.com/gpuweb/cts/+/HEAD/src/webgpu/texture_test_utils.ts); [W3C GPU WG activity 2023](https://www.w3.org/groups/wg/gpu/activity/2023/)
- [FACT] Runner noise: wgpu's Windows hosts stall for a minute or more; Bevy's macOS runners time out audio after 15 minutes (both above). — [wgpu ci.yml](https://github.com/gfx-rs/wgpu/blob/trunk/.github/workflows/ci.yml); [example-run.yml](https://github.com/bevyengine/bevy/blob/main/.github/workflows/example-run.yml)

**How other engines handle golden images and tolerances**
- [FACT] Unreal (UE 5.9 docs): screenshots come from a Functional Screenshot Test actor or from a Functional Test; a mismatch against the ground truth fails the test; reviewers Replace, "Add As Alternative" or file a bug; ground truth is bucketed by `Platform_RHI_ShaderModel` and the closest alternative by metadata is compared; adding ground truth goes through source control (pending changelist). Tolerance presets are Zero, Low (default), Medium, High, Custom (per-channel RGBA plus min/max brightness); "Maximum Global Error" caps total error and "Maximum Local Error" checks small regions; "Ignore Anti-Aliasing" searches neighbouring pixels; "Ignore Colors" compares luminance only; a Delay setting waits before capture; a specific GBuffer can be captured instead of the final image. — [Unreal Screenshot Comparison Tool](https://dev.epicgames.com/documentation/unreal-engine/screenshot-comparison-tool-in-unreal-engine?lang=en-US)
- [FACT] Unity Graphics Test Framework (9.0.0-pre.32): renders test images and compares them with reference images to "detect rendering regressions across platforms, graphics APIs, and hardware configurations"; the first run fails because there is "no reference image to check the capture against yet". `ImageComparisonSettings` exposes `PerPixelCorrectnessThreshold` (deltaE per pixel; smaller differences are ignored), `PerPixelGammaThreshold`, `PerPixelAlphaThreshold`, `AverageCorrectnessThreshold`, `IncorrectPixelsThreshold` (ratio of pixels allowed to be wrong), `RMSEThreshold`, fixed `TargetWidth/Height`, `TargetMSAASamples`, `UseHDR`, `UseBackBuffer`. — [Unity GTF manual](https://docs.unity3d.com/Packages/com.unity.testframework.graphics@9.0/manual/index.html); [graphics tests introduction](https://docs.unity3d.com/Packages/com.unity.testframework.graphics@9.0/manual/test-authoring/graphics-tests-introduction.html); [ImageComparisonSettings API 8.5](https://docs.unity3d.com/Packages/com.unity.testframework.graphics@8.5/api/UnityEngine.TestTools.Graphics.ImageComparisonSettings.html); [Graphics Test Settings component](https://docs.unity3d.com/Packages/com.unity.testframework.graphics@9.0/manual/test-investigation/graphics-test-settings-component.html)
- [FACT] Filament renderdiff: runs `gltf_viewer` headlessly on Mesa software rasterizers (OpenGL, Vulkan, WebGPU backends) and, for web, in headless Chromium on SwiftShader; goldens live in a separate repository (`google/filament-assets`) writable only by team members; a commit tag `RDIFF_ACCEPT_NEW_GOLDENS` skips comparison and the docs warn that then "nothing verifies the new goldens before they land"; the safer route renders new goldens to a branch (`RDIFF_BRANCH=`) so the presubmit compares against it; a viewer shows rendered and golden images side by side. The page does not state the pixel tolerance. — [Filament renderdiff](https://google.github.io/filament/dup/test_ci_renderdiff.html)
- [FACT] Skia Gold (Chromium GPU pixel tests): `goldctl` passes if the image hash is already approved, otherwise uploads and fails; a person approves new images in the GUI; Gold "supports multiple approved images per test"; default is exact matching; noisy tests opt into inexact matching (`matching_algorithm`, fuzzy and/or Sobel), whose passes are auto-approved "so there is still a record of exactly what was produced"; a script (`determine_gold_inexact_parameters.py`) searches for parameters. Baselines live outside the repository; trybot approvals apply only to that change until merged. — [GPU pixel testing with Gold](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/gpu/gpu_pixel_testing_with_gold.md)
- [FACT] Godot: no official golden-image system was found; a closed godot-benchmarks issue proposes a checksum regression script that runs baseline and changed builds with `--fixed-fps 5 --write-movie` and a frame limit and compares PNG output with `shasum`. — [godot-benchmarks #34](https://github.com/godotengine/godot-benchmarks/issues/34)

### Inferences
- A wgpu/Bevy-class engine can capture deterministically without a window if it (a) renders to an `Image` target, (b) advances time by a fixed step, (c) triggers captures by frame index or by an explicit "ready" signal rather than by wall-clock, and (d) disables or freezes the listed noisy features (temporal jitter, auto-exposure, motion blur) for golden captures. The 40-frame pre-roll in Bevy's example is a heuristic that depends on machine speed; for a streaming open world an explicit "all requested assets and pipelines ready" signal is the invariant fix, a frame count is the patch.
- Bit-exact goldens are realistic only within one pinned software stack (same Mesa/WARP build, same container). For real GPUs the workable design is what wgpu, Unreal and Filament do: one reference per (backend, adapter, driver) plus a perceptual tolerance, or better, an A/B render of "base commit vs. candidate" on the same machine in the same job, which removes the cross-machine term entirely.
- Software rasterizers on hosted runners are a functional gate (does it render, is it the same as before), not a fidelity or performance gate. Heavy scenes will need a self-hosted GPU machine or the T4/M2 larger runners.
- wgpu's "missing reference is written as the new reference" behaviour and Filament's `RDIFF_ACCEPT_NEW_GOLDENS` are convenience paths that become holes when the committer is an agent: deleting or corrupting a golden turns the gate into a no-op. A verifier for agents should fail closed on a missing reference.
- `ScheduleRunnerPlugin::run_loop` at "60 updates per second" paces by wall-clock; combined with a manual time step the simulation stays deterministic, but captures should still be keyed to update counts.

### Gaps
- Numeric values of Unreal's Zero/Low/Medium/High presets and default local/global error limits are not in the 5.9 doc page; they would have to be read from engine source.
- Unity's default thresholds and its per-platform reference-image folder layout were not on the pages read.
- Skia Gold's fuzzy/Sobel parameter names and typical values were not on the page read.
- No measured speed of lavapipe/llvmpipe/WARP/SwiftShader for a heavy 3D scene was found; no source was found on whether llvmpipe output varies with host CPU features (plausible, unverified).
- Whether GitHub's standard (non-XLarge) `macos-26` runner exposes a full Metal device is supported only indirectly (Bevy and wgpu run Metal jobs there); GitHub's docs do not state it.
- Rendering inside a Tauri 2 shell (wgpu surface inside a webview window versus an offscreen target) was not researched.

## 2. Agent control surfaces: Bevy Remote Protocol and `bevy_brp_mcp`, MCP servers for other engines, capture and profiling tools drivable from the command line, and trustworthy numbers from real phones

### Takeaway
By late 2026 every major engine has an agent control surface (Bevy: BRP plus `bevy_brp_mcp` 0.23.0; Unreal: official experimental MCP in the editor; Unity: official MCP beta; Blender: official MCP; Godot: community servers), and every profiler needed has a scriptable path (`xctrace`, `metalperftrace` on macOS, `adb`/Perfetto/SurfaceFlinger timestats, RenderDoc's Python API, Tracy, PresentMon). The blunt part: on real phones the only numbers that are both trustworthy and fully human-free are the ones the app measures itself and writes to a file; the iOS Simulator is not valid for performance, AWS Device Farm does not collect performance samples during tests, Firebase Test Lab expects the game to write its own metrics, and Apple's new always-on trace collection on iOS is started from Control Center by hand.

### Cited Findings

**Bevy Remote Protocol (BRP) and `bevy_brp_mcp`**
- [FACT] BRP (Bevy 0.20.1) is JSON-RPC 2.0; `RemotePlugin` sets up the protocol and `RemoteHttpPlugin` adds HTTP transport. Built-in methods: `world.get_components`, `world.query`, `world.spawn_entity`, `world.despawn_entity`, `world.remove_components`, `world.insert_components`, `world.mutate_components`, `world.reparent_entities`, `world.list_components`, watch variants (`+watch`), resource get/insert/remove/mutate/list, `world.trigger_event`, `registry.schema`, `rpc.discover` (returns an OpenRPC document). Custom methods can be registered (`with_method`, `RemoteMethods`) and run with exclusive `World` access. Values must be reflectable. The page does not describe authentication. — [bevy::remote docs](https://docs.rs/bevy/latest/bevy/remote/index.html)
- [FACT] Bevy's own CI has a `run-brp-integration-test` job. — [example-run.yml](https://github.com/bevyengine/bevy/blob/main/.github/workflows/example-run.yml)
- [FACT] Bevy 0.20's "What's Next" lists a "Remote inspector": "Browse, modify and mutate entities from external tools, on your machine or on a different device!" — [Bevy 0.20 news](https://bevy.org/news/bevy-0-20/)
- [FACT] `bevy_brp_mcp` 0.23.0 is dated 2026-10-09 (0.22.10 on 2026-10-06). Compatibility: Bevy 0.20 -> 0.23.0; 0.19 -> 0.22.10; 0.18 -> 0.19.0; 0.17 -> 0.17.2. Source: `github.com/natepiano/bevy_brp` (MIT or Apache-2.0). — [bevy_brp_mcp on docs.rs](https://docs.rs/bevy_brp_mcp)
- [FACT] Capabilities listed: discover and launch apps/examples with logging (`brp_list_bevy`, `brp_launch`); spawn/despawn/query/reparent entities and find by name; get/insert/remove/mutate components and resources; watch component changes; trigger events; type schemas and mutation paths (`brp_type_guide`); read app logs; process status; and, through the companion `bevy_brp_extras` plugin, screenshots of the primary window, a camera viewport or an entity crop (`brp_extras_screenshot`), keyboard (`send_keys`, `type_text`), mouse, trackpad gestures, simulated gamepads, shutdown, window title and FPS/frame-time diagnostics (`get_diagnostics`). — [bevy_brp_mcp on docs.rs](https://docs.rs/bevy_brp_mcp)

- [FACT] The repository also contains `.claude/` commands, scripts and agentic tests for the MCP server. — [natepiano/bevy_brp](https://github.com/natepiano/bevy_brp)

- [FACT] wgpu 30.0.2 exposes `Device::start_graphics_debugger_capture` / `stop_graphics_debugger_capture` (unsafe): with RenderDoc attached they call `StartFrameCapture`/`EndFrameCapture`, with Xcode they use `MTLCaptureManager`, with no debugger nothing happens. — [wgpu Device docs](https://docs.rs/wgpu/latest/wgpu/struct.Device.html)

### Inferences
- For a greenfield Rust engine the cheapest robust control surface is the engine's own JSON-RPC (BRP or an equivalent): scripted camera path, state queries, and custom methods such as "capture frame N to file", "dump per-pass GPU timings as JSON", "force LOD level", "report streaming queue". `bevy_brp_mcp` then gives agents an MCP wrapper for free if the engine is Bevy; a non-Bevy wgpu engine would need to implement the same few methods itself.
- `bevy_brp_mcp` window screenshots are a debugging aid, not a gate input: the documented black-screenshot case for hidden or occluded windows is exactly the headless situation. Gate captures should come from an offscreen `Image` target inside the engine.
- BRP over HTTP with no documented authentication and Unreal's "no authentication layer" both mean these surfaces must stay on loopback and out of release builds.
- FrameTimeline's "SurfaceViews are not supported" matters for a native game surface on Android: the SurfaceFlinger timestats histogram plus in-engine frame timing is the safer primary source there.
- Human-free and trustworthy phone numbers therefore reduce to: (1) the app runs a scripted scenario and writes a JSON file with frame times, per-pass GPU times, memory and thermal readings; (2) an OS-level cross-check that needs no touch (`dumpsys SurfaceFlinger --timestats`, `dumpsys meminfo` over adb; `xctrace record --device ... --time-limit` over USB for iOS); (3) a device farm only for breadth. A one-time manual device setup (pairing, Developer Mode) remains.

## 3. Objective image and video metrics, what their thresholds mean, where they exist as Rust crates or command-line tools, cost and failure modes

### Takeaway
For rendered content, classic full-reference metrics agree only moderately with people: on Intel's 2025 rendering-artifact dataset every existing metric sits at 0.64–0.78 Pearson correlation with human ratings, while the purpose-built CGVQM reaches 0.87. FLIP is the practical default for still images in Rust (the `nv-flip` crate, used by wgpu's own tests, with starting thresholds of mean 0.01–0.1); ColorVideoVDP is the practical default for video and flicker (JOD scale, `pip install cvvdp`); SSIMULACRA 2 has the clearest threshold table but was tuned on compression artifacts; VMAF, LPIPS and SSIM have documented ways to fail or be gamed.

### Cited Findings

**Measured agreement with human ratings on rendering artifacts**
- [FACT] CGVQM+D (Intel Labs, arXiv 2506.11546, 13 June 2025; Computer Graphics Forum 44(8), High-Performance Graphics 2025): the CG-VQD dataset has 80 videos (including references) from 15 open scenes, six rendering techniques (path tracing, neural denoising, neural supersampling, Gaussian splatting, frame interpolation, adaptive variable rate shading) at 4–5 severity levels, rated by 20 recruited participants (19 kept); stimuli were 1024x1024, 3 s, 30 fps. — [CGVQM+D paper](https://arxiv.org/html/2506.11546v1); [Eurographics digital library](https://diglib.eg.org/handle/10.1111/cgf70221)
- [FACT] Pearson / Spearman correlation with human ratings on CG-VQD (Table 1): PSNR 0.697 / 0.723; SSIM 0.639 / 0.805; MS-SSIM 0.668 / 0.804; VMAF 0.715 / 0.79; FovVideoVDP 0.755 / 0.741; ColorVideoVDP 0.744 / 0.775; LPIPS 0.696 / 0.748; DISTS 0.686 / 0.795; FLIP 0.693 / 0.728; best existing metric HaarPSI at 0.777 PLCC; CGVQM-5 0.871 / 0.877; CGVQM-2 0.855 / 0.876. — [CGVQM+D paper](https://arxiv.org/html/2506.11546v1)
- [FACT] The paper reports that ColorVideoVDP and FLIP tend to overestimate quality in high-distortion cases, and that HaarPSI and ColorVideoVDP do best on variable rate shading but much worse on Gaussian splatting and neural frame interpolation. — [CGVQM+D paper](https://arxiv.org/html/2506.11546v1)
- [FACT] CGVQM limits stated by its authors: full-reference; mean pooling over space and time can over-weight minor localised errors; does not model brightness or viewing distance; assumes equal frame rates; 3D convolutions use future frames; computationally and memory intensive at high resolution (high-resolution video is split into 30x512x512 patches and the overall score is the minimum patch score); error maps are not calibrated. Benchmarks were on an NVIDIA A100; CGVQM-2 is about 27% faster than CGVQM-5. Code is at `IntelLabs/CGVQM`. — [CGVQM+D paper](https://arxiv.org/html/2506.11546v1); [Intel article](https://www.intel.com/content/www/us/en/developer/articles/technical/cgvqm-d-computer-graphics-video-quality.html)

**NVIDIA FLIP**
- [FACT] FLIP is a full-reference difference evaluator whose error map "approximates the difference perceived by humans when alternating between two images"; the repository (v1.7) implements LDR-FLIP and HDR-FLIP in C++, CUDA, Python (`pip install flip-evaluator`, Python 3.10+) and as PyTorch loss modules, under BSD 3-Clause; since v1.7 HDR-FLIP's automatic stop exposure handles reference images with median luminance 0. — [NVIDIA research page](https://research.nvidia.com/publication/flip); [NVlabs/flip](https://github.com/NVlabs/flip)
- [FACT] Rust: `nv-flip` 0.1.2 binds the FLIP library (MIT/Apache-2.0/Zlib; FLIP itself BSD-3-Clause); `flip(ref, test, pixels_per_degree)` returns an error map with values "between 0 and 1"; `FlipPool` gives mean, min, max and (optionally weighted) percentiles; default 67 pixels per degree; image types `FlipImageRgb8` and `FlipImageFloat`. The docs repeat that FLIP's authors recommend the mean when one number is needed. — [nv-flip docs](https://docs.rs/nv-flip/latest/nv_flip/)
- [FACT] The only published threshold guidance found is wgpu's: mean FLIP "good initial values ... in the [0.01, 0.1] range", larger where more of the image has inherent variance. — [wgpu_test image.rs](https://wgpu.rs/doc/src/wgpu_test/image.rs.html)

**ColorVideoVDP, FovVideoVDP, HDR-VDP-3**
- [FACT] ColorVideoVDP "predicts the perceptual difference between pairs of images or videos", modelling spatio-temporal and chromatic contrast sensitivity; it "needs physical specification of the display" (`--display standard_fhd` etc.); accepts images, video, HDR (PQ/HLG, OpenEXR in absolute linear values); output in JOD where 10 means no difference and values can go below 0; produces heatmaps (`--heatmap`) and a "distogram" over time and channels; PyTorch, `pip install cvvdp`, "can be run efficiently on a CUDA-enabled GPU", CPU "much longer, especially for video", MPS on Mac with torch >= 2.1; MIT licence; latest release v0.5.7 (2026-08-02). — [ColorVideoVDP repository](https://github.com/gfxdisp/ColorVideoVDP/); [paper](https://arxiv.org/html/2401.11485v2)
- [FACT] JOD meaning (stated for the sibling FovVideoVDP): a method scoring 9 JOD against one scoring 8 JOD "means that 75% of the population will choose" the higher one; FovVideoVDP's JOD values changed between versions (v1.1). — [pyfvvdp on PyPI](https://pypi.org/project/pyfvvdp)
- [FACT] HDR-VDP-3 (Mantiuk, Hammou, Hanji; arXiv 2304.13625, April 2023) is "a visual metric that can fulfill several tasks": full-reference image/video quality, visibility of differences, and contrast distortions, for HDR and regular content. — [HDR-VDP-3](https://arxiv.org/abs/2304.13625)

**SSIMULACRA 2, Butteraugli, SSIM-family in Rust**
- [FACT] SSIMULACRA 2.1 score table: 100 mathematically lossless; 90 "visually lossless" (not noticeable in a flicker test at 1:1); 85 not noticeable in in-place comparison; 80 not noticeable side by side; 70 high quality, artifacts perceptible but not annoying (MOS about 4); 50 medium (MOS about 3); 30 low (MOS about 2); 10 very low; negative = extremely low. Weights were tuned on CID22, TID2013, KADID-10k and KonFiG with compression codecs (JPEG, JPEG 2000, JPEG XL, WebP, AVIF, HEIC). On CID22: SSIMULACRA 2.1 KRCC/SRCC/PCC 0.6903/0.8805/0.8583 versus VMAF 0.6176/0.8163/0.7799 and PSNR 0.3472/0.5002/0.4817. — [cloudinary/ssimulacra2](https://github.com/cloudinary/ssimulacra2)
- [FACT] Rust crates: `ssimulacra2` (rust-av; latest release 2024 per lib.rs) and its CLI `ssimulacra2_rs`; `fast-ssim2` (SIMD fork with a precomputed-reference API, 0.8.2); `butteraugli` ("pure Rust implementation of Google's butteraugli perceptual image quality metric from libjxl", 0.3.2); `iqa` (one API over several full-reference metrics including DSSIM, image-only, no video); `zensim` (fast approximations of SSIMULACRA2, DSSIM and butteraugli scores). — [ssimulacra2 on lib.rs](https://lib.rs/crates/ssimulacra2); [ssimulacra2_rs](https://lib.rs/crates/ssimulacra2_rs); [fast-ssim2](https://docs.rs/crate/fast-ssim2/latest); [butteraugli crate](https://docs.rs/crate/butteraugli/0.3.2/source/README.md); [iqa crate](https://docs.rs/iqa); [zensim](https://docs.rs/crate/zensim/0.2.0)
- [FACT] "Understanding SSIM" (Nilsson and Akenine-Möller, NVIDIA, 2020) shows SSIM can generate results that are "unexpected, sometimes undefined, and nonintuitive", that its input colour space "is never defined", and that judging quality by SSIM "can lead to incorrect conclusions". — [Understanding SSIM](https://arxiv.org/abs/2006.13846v2)

**Learned metrics and VMAF: failure modes**
- [FACT] E-LPIPS reports that simple attacks make LPIPS judgments sharply disagree with human similarity judgments; its transformation ensemble adds roughly 10% inference cost. A thesis finds LPIPS "sensitive to imperceptible misalignment". DISTS was designed to tolerate texture resampling and is "insensitive to mild local and global geometric distortions"; a 2023 benchmark notes LPIPS and DISTS "have already been shown to be vulnerable to adversarial attacks". — [E-LPIPS](https://arxiv.org/pdf/1906.03973); [PDX thesis](https://pdxscholar.library.pdx.edu/open_access_etds/6920); [DISTS](https://arxiv.org/pdf/2004.07728v3.pdf); [IQA robustness benchmark](https://arxiv.org/html/2310.06958v1)
- [FACT] "Hacking VMAF and VMAF NEG" (2021): tuned preprocessing increases VMAF "by up to 218.8%" and VMAF NEG by up to 23.6%, while subjective quality for most methods drops or stays the same. — [Hacking VMAF](https://arxiv.org/abs/2107.04510)
- [FACT] VMAF's temporal modelling is one frame-difference feature: "aside from average frame difference measurements (TI feature), VMAF does not exploit temporal quality measurements." — [Spatiotemporal feature integration paper](https://arxiv.org/pdf/1804.04813)
- [FACT] `pyiqa` (IQA-PyTorch) gathers many full-reference and no-reference metrics (PSNR, SSIM, MS-SSIM, LPIPS, NIQE, BRISQUE, MUSIQ, TOPIQ, Q-ReAlign, FID, ...) behind one CLI (`pyiqa <metric> -t <img|dir> -r <ref> --device cuda|cpu`); its README states a PolyForm Noncommercial licence (plus NTU S-Lab licence for some parts). — [IQA-PyTorch](https://github.com/chaofengc/IQA-PyTorch)

### Inferences
- Which metric for which gate: FLIP (LDR after the engine's own tone map, or HDR-FLIP on float output) for still-image regression and reference comparison, because it is native to Rust, cheap enough that wgpu runs it per test, and designed for rendered images; ColorVideoVDP for clips where flicker, shimmer and popping matter; CGVQM where a CUDA machine is available and the artifact is of the "modern rendering" kind (denoising, upscaling, frame generation). SSIMULACRA 2's table makes it the natural gate for asset-pipeline steps that are compression-like (texture compression, impostor baking, mesh simplification rendered against the original): require 90 for "indistinguishable", 80–85 for "fine side by side".
- A FLIP mean is a pooled number: one popped tree in a vista barely moves the mean. Gates need a high percentile (p99/p99.9) or a maximum over tiles alongside the mean; wgpu's `Percentile` variant exists for this reason.
- Correlations of 0.64–0.78 mean no single threshold on these metrics equals "a person would accept this". They are regression detectors and rank-order tools; absolute thresholds must be calibrated on the project's own content with a small human-labelled set.
- LPIPS's misalignment sensitivity and DISTS's texture tolerance cut opposite ways for vegetation: wind-animated grass and leaves never align pixel to pixel, so LPIPS/FLIP on animated foliage will report differences that people do not see, while DISTS may hide real texture loss. Freeze wind for stills; use distribution or statistic measures for animated foliage.
- `pyiqa`'s noncommercial licence is a blocker for a commercial product pipeline unless the individual metrics are taken from their original, differently licensed sources.
- VMAF adds little here: it is tuned for compression, has one temporal feature and can be inflated by sharpening or contrast.

### Gaps
- No official mapping from mean FLIP to "visible/not visible" exists; NVIDIA publishes none.
- No measured runtimes for FLIP, ColorVideoVDP, CGVQM or HDR-VDP-3 at 1080p or 4K were found.
- Butteraugli's distance scale and thresholds, HDR-VDP-3's implementation language and licence, and PSNR conventions were not verified from primary sources today.
- No Rust-native LPIPS/DISTS/ColorVideoVDP implementation was found; these appear to need Python/PyTorch (or an ONNX export, unverified).
- No temporal variant of FLIP was found.

## 4. Photorealism gates: reference renderer, photo sets, no-reference metrics, real-versus-CG classifiers, vision-language judges, matched photos — and which track human judgement of realism

### Takeaway
There is no validated automatic metric that says "this rendered frame looks like a photograph" for game content. The gate with real evidence behind it is the reference-renderer gate (real-time frame versus a path-traced render of the same scene, scored with full-reference metrics). Photo-set distribution metrics, no-reference quality scores and vision-language judges all have published cases of disagreeing with people or failing on rendered game images; they are usable as advisory trend signals and triage, not as pass/fail.

### Cited Findings

**(a) Reference-renderer gates**
- [FACT] Unreal's Path Tracer is documented as "ideal for ground truth comparisons and production renders" and for "ground truth comparisons against the real-time rendered scenes"; it "only uses geometry and material present in the scene to render its unbiased result"; it requires hardware ray tracing (DXR, SM6, Windows). — [Unreal Path Tracer, UE 5.9 docs](https://dev.epicgames.com/documentation/unreal-engine/path-tracer-in-unreal-engine)
- [FACT] Ray Tracing Gems II chapter 14 ("The Reference Path Tracer") describes building an in-engine reference path tracer because tuning real-time effects is simpler when the engine can progressively generate a "known-correct" reference image to compare against. — [RTG2 chapter 14 preprint](https://developer.download.nvidia.com/ray-tracing-gems/rtg2-chapter14-preprint.pdf)
- [FACT] Bevy Solari ships a non-realtime path tracer (`PathtracingPlugin`, `Pathtracer` camera component) intended as testbed and reference, not added by default; the Solari example has a `--pathtracer` flag; the `bevy::solari` module in 0.20.1 still has a `pathtracer` submodule and is described as "An experimental set of plugins for raytraced lighting." — [bevy_solari 0.18.1 source](https://docs.rs/bevy_solari/0.18.1/src/bevy_solari/lib.rs.html); [solari example 0.18.1](https://docs.rs/crate/bevy/0.18.1/source/examples/3d/solari.rs); [bevy::solari 0.20.1](https://docs.rs/bevy/latest/bevy/solari/index.html)
- [OLD][FACT] Solari author's write-up for Bevy 0.17 (2025-09-20): "having a reference implementation of what lighting is supposed to look like is incredibly valuable"; at that time specular, transparent and alpha-masked materials were missing, only directional and emissive-mesh lights were supported, an NVIDIA GPU was required, and the comparison shown was visual (a "Pathtraced reference" image), not a quantitative error measure. Per-pass timings on an RTX 3080 at 1600x900 upscaled to 3200x1800: 8.22 ms (PICA PICA), 14.55 ms (Bistro), 8.25 ms (Cornell Box), with DLSS-RR about 5.8–6.3 ms of that. — [Solari in Bevy 0.17](https://jms55.github.io/posts/2025-09-20-solari-bevy-0-17/)
- [FACT] Later releases: 0.18 added specular materials and reflections to Solari; 0.19 improved mirrors and temporal stability; 0.20 made it "faster, more accurate", made ReSTIR optional and off by default, added lighting from Atmosphere and environment-map lights, and "runs on macOS via Metal". — [Bevy 0.18 news](https://bevy.org/news/bevy-0-18/); [Bevy 0.19 news](https://bevy.org/news/bevy-0-19/); [Bevy 0.20 news](https://bevy.org/news/bevy-0-20/)
- [CLAIM] Khronos hosts a glTF Render Fidelity site comparing "the most popular real-time web renderers" with path tracers on glTF PBR assets (staging repository; no metric stated). — [KhronosGroup/glTF-Render-Fidelity](https://github.com/KhronosGroup/glTF-Render-Fidelity)
- [FACT] Full-reference metrics against a reference correlate with human ratings of rendering artifacts at 0.64–0.78 PLCC (existing metrics) and 0.87 (CGVQM) on CG-VQD (section 3). — [CGVQM+D paper](https://arxiv.org/html/2506.11546v1)

**(b) Photo-set gates: distribution metrics, sample sizes, no-reference metrics, classifiers**
- [FACT] "Rethinking FID" (CVPR 2024): "we need more than 20,000 images to reliably estimate FID"; "FID is a biased estimator, where the bias depends on the model being evaluated"; in the paper's human study raters preferred model A in 92.5% of comparisons while FID (21.40 vs 18.42) favoured model B — "FID contradicts human evaluation while CMMD agrees". CMMD uses CLIP ViT-L/14@336px embeddings and MMD with a Gaussian RBF kernel (sigma = 10), is unbiased and "provides consistent estimates even with small image sets" (no specific number given). — [Rethinking FID](https://arxiv.org/html/2401.09603v2)
- [FACT] `pytorch-fid`'s default 2048-dimensional features imply at least 2048 images ("less than the otherwise required 2048 images"); scores at different feature dimensionality cannot be compared, and results differ slightly from the original implementation. — [pytorch-fid](https://github.com/mseitzer/pytorch-fid)
- [FACT] Stein et al. (NeurIPS 2023) ran a large human study of perceived realism and "find that no existing metric strongly correlates with human evaluations"; replacing Inception-V3 with DINOv2-ViT-L/14 "significantly improves" agreement of Fréchet-distance metrics with people. — [Exposing flaws of generative model evaluation metrics](https://arxiv.org/abs/2306.04675v2)
- [FACT] GLIPS (2024 preprint) states FID and KID "do not align closely with human evaluations" of photorealism for AI-generated images. — [GLIPS](https://arxiv.org/abs/2405.09426v2)
- [FACT] "Enhancing Photorealism Enhancement" (Richter, AlHaija, Koltun, 2021) uses KID for rendered-to-real evaluation but notes KID compares high-level Inception features, that one "could trivially minimize KID by reproducing a real image from the target dataset" while ignoring the rendered input, and replaces it with a patch-based squared MMD on VGG-16 features over corresponding patches (sKVD). — [Enhancing Photorealism Enhancement](https://arxiv.org/pdf/2105.04619)
- [FACT] Gram-MMD (arXiv 2604.03064, 2026-04-03) proposes a texture-aware realism metric (Gram matrices of backbone activations compared by MMD) and reports that in a driving test with KITTI and Virtual KITTI, CMMD can rank real images as less realistic than synthetic ones. Its validation is against controlled degradations, not human realism ratings. — [Gram-MMD](https://arxiv.org/abs/2604.03064)
- [FACT] No-reference quality on game frames: AMD researchers (arXiv 2505.11724, May 2025) report that the general video-quality model COVER showed "no correlation with the quality presets (SRCC < 0.2)" on Forza Horizon 5 and that existing no-reference methods "fail to accurately assess the visual quality of game graphics" (trained on streaming and user-generated-content distortions). Their game-specific model reaches SRCC 0.986 on the training game and 0.966 / 0.880 on two unseen games, but ground truth is the graphics preset, and the authors say a human-labelled MOS dataset is needed. — [Semantically-Aware Game Image Quality Assessment](https://arxiv.org/html/2505.11724v1)
- [OLD][FACT] Real-versus-computer-graphics classifiers: on the Rahmouni et al. dataset (1800 screenshots from five photorealistic games plus 1800 photographs) published classifiers reach 99.3% and 100% accuracy on full-size images (89.76% on patches). — [Capsule network forensics paper](https://arxiv.org/pdf/1910.12467)

**(c) Vision-language models as judges**
- [FACT] Q-Bench (ICLR 2024) found general multimodal models' low-level visual abilities "still unstable and relatively imprecise". — [Q-Bench](https://arxiv.org/abs/2309.14181v3)
- [FACT] A March 2026 study compared six models (Claude Opus 4.6, Gemini 3.1 Pro, GPT-5.2, Grok-4.1, InternVL-3.5-38B, Qwen3-VL-32B) with psychophysical data from 20 observers on 70 tone-mapped images (10 scenes x 7 operators). Spearman correlations with people ranged from 0.11 to 0.93 depending on model and attribute (contrast: Qwen 0.86, Gemini 0.79, GPT 0.75, Claude/Grok 0.54, Intern 0.14; colourfulness: Claude/Qwen 0.93, Gemini 0.11; overall preference: GPT 0.86, others about 0.54–0.64 and not significant). Intra-model variability ranged from about 1% (Claude) to 18% (Intern). Conclusions: "current VLMs are not yet capable of substituting psychophysical experiments", "High self-consistency does not necessarily imply perceptual validity", and agreement improves when differences are pronounced. — [VLMs vs human perceptual IQA](https://arxiv.org/html/2603.24578)
- [FACT] R4-CGQA (arXiv 2603.10578, March 2026) built a 3,500-image computer-graphics quality dataset with six perceptual dimensions and found current VLMs "not sufficiently accurate in judging fine-grained CG quality"; retrieval of descriptions of similar images "substantially improves" them (no numbers on the abstract page). — [R4-CGQA](https://arxiv.org/abs/2603.10578)
- [FACT] GPTEval3D (CVPR 2024): with ensembling over 4–5 perturbed prompt/input strategies, GPT-4V pairwise judgements reach an average Kendall tau of 0.710 with human rankings (CLIP similarity 0.568) and a pairwise agreement of 0.789; per criterion tau ranges from 0.564 (texture-geometry coherency) to 0.821. Stated limits: hallucination, position bias, miscounting, over-sensitivity to low-level noise, gameability by adversarial patterns, cost growing quadratically; human experts themselves agreed at Cohen's kappa above 0.53, general users about 0.3. — [GPTEval3D](https://arxiv.org/html/2401.04092v2)
- [FACT] 3DGen-Bench (March 2025) concluded generic CLIP-style metrics are "inadequate and inaccurate" for 3D and trained dedicated judges on over 58,000 human battle pairs. — [3DGen-Bench](https://arxiv.org/html/2503.21745v2)
- [FACT] BlenderGym (CVPR 2025; 245 scene-editing tasks): the best model's agreement with people when choosing the better of two edits was 0.66 (Claude 3.5 Sonnet) against 0.79 between people and 0.5 for chance (7,950 judgements, 50 participants); "The verifier sometimes fails to distinguish between desirable and suboptimal edits"; some models "consistently favor the second edit candidate"; generators "often hallucinate non-existent visual differences". Human Blender users beat the best system by large margins (e.g. lighting photometric loss 1.239 vs 2.410; placement 0.423 vs 10.94). — [BlenderGym](https://arxiv.org/html/2504.01786)
- [FACT] Anthropic (2026-03-24): "agents reliably skew positive when grading their own work"; a separate evaluator still "identified real issues, then talk[ed] itself into" approving, and "Out of the box, Claude is a poor QA agent"; few-shot calibration with score breakdowns and hard per-criterion thresholds reduced drift. — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)

**(d) Matched-photo comparison at fixed viewpoints**
- [FACT] Hemispherical (canopy) photography gives standard vegetation-structure measures — gap fraction (share of visible sky per sky direction), canopy closure, leaf area index — by thresholding pixels into sky and canopy; known error sources are exposure (auto-exposure hides differences between open and closed canopies), uneven sky lighting, lens/levelling, and the threshold choice. — [Hemispherical photography](https://en.wikipedia.org/wiki/Hemispherical_photography)

### Inferences
- Which gates track human judgement, on the evidence found: (1) reference-renderer comparison with full-reference metrics — moderate to good (0.64–0.87 correlation), but it measures closeness to the reference, i.e. correctness of light transport and reconstruction, not "looks like a photo"; (2) distribution metrics against photographs — mixed: FID has contradicted people, DINOv2- and CLIP-based variants do better in generative-model studies, and no study found validates any of them for rendered game frames; (3) no-reference quality metrics — published failure on game frames; (4) real-versus-CG classifiers — saturate near 100% on older game data, which makes them a binary detector with no gradient and trivially exploitable cues, and no evidence was found that their score follows human realism ratings; (5) vision-language judges — agreement with people well below human-human agreement for fine visual differences, with position bias and leniency; (6) matched-photo statistics — no study found either way.
- A reference path tracer does not make a scene photoreal; it removes one class of error (lighting, shadowing, reconstruction). Asset realism (geometry, materials, vegetation density, atmosphere) is still judged only against photographs. For the stated target (hazy vistas, dense forest, meadows, forest floor) asset and atmosphere realism is likely the larger share of the gap, so the reference gate is necessary but not sufficient.
- Feasibility of the in-engine reference for a food forest: the Solari path tracer's documented material limits (alpha-masked and transparent materials missing as of 0.17) are exactly what foliage needs, and it needs hardware ray tracing, so it cannot be assumed to run on software-rasterizer CI. Until verified on 0.20, plan for either a small custom wgpu path tracer over the engine's own scene data, or a Blender Cycles reference via glTF/USD export. The export route introduces material-model mismatch, so it supports comparisons of lighting, shadowing and overall tone at fixed views rather than tight per-pixel thresholds.
- Photo-set gate design that respects the evidence: with tens of fixed viewpoints (not thousands of images) FID is unusable (needs more than 20,000 images); use an unbiased MMD-family measure (KID/CMMD/patch-based MMD as in sKVD or Gram-MMD) on many patches, report it as a trend, and never let it be the only gate, because a distribution metric can be improved without improving the picture and has contradicted people.
- Matched-photo statistics are cheap, interpretable and hard to argue with as necessary conditions: luminance histogram and percentiles after a fixed exposure, mean colour and chroma spread in a perceptual space, contrast as a function of depth for haze, sky/vegetation/ground cover fractions from a segmentation mask, canopy gap fraction for upward views, and spectral slope. They cannot certify realism, but a frame that fails them is measurably not like the photograph. The same error sources as in field canopy photography (exposure, threshold) apply, so exposure and thresholds must be fixed for render and photo alike.
- Vision-language judges are best used the way GPTEval3D and BlenderGym imply: pairwise ("which of A or B is closer to this photo, and where"), with randomised order, several perturbed prompts, a held-out human-labelled calibration set, and a hard rule that the judge can raise issues but cannot pass a gate by itself.

### Gaps
- No study was found that validates any automatic metric against human realism ratings for rendered natural environments (forest, grass, haze). This is the central missing piece.
- Status of alpha-masked, transmissive and foliage materials in Bevy's path tracer as of 0.20, and whether it runs on Apple silicon or lavapipe, were not verified.
- No primary source was read on studios' quantitative use of reference path tracers beyond Unreal's documentation and RTG2; Frostbite/Unity practice was not found (Unity's HDRP path-tracing page read makes no ground-truth statement).
- Minimum sample sizes for KID/CMMD are not stated numerically in the sources read.
- NIQE, BRISQUE, CLIP-IQA, MUSIQ and Q-Align were not found tested on rendered game frames; a 2023 study of in-the-wild computer-graphics images ([arXiv 2303.08050](https://arxiv.org/pdf/2303.08050)) evaluates BRISQUE, NIQE and MUSIQ but its numbers were not extracted.
- No recent (2024–2026) real-versus-CG classifier study on current games was found.
- The glTF/USD-to-Cycles export path (material fidelity, automation) was not researched.

## 5. Performance and stability gates: per-pass GPU time, memory, counts, thermal runs, popping detection, hitch detection, and keeping gates from being gamed

### Takeaway
Per-pass GPU timing is available in wgpu on every native backend, but only at pass boundaries on Apple GPUs and "generally not" inside passes on tile-based mobile GPUs, and Bevy's built-in render diagnostics record GPU time only on Vulkan and DX12 as of 0.20.1 — so Apple devices need custom pass-boundary instrumentation. Platform vendors publish usable thresholds for hitches (Apple: under 5 ms/s is good; Android: a frame over 50 ms is slow) and for thermal headroom (Android: 0.85/0.95/1.0). Measured agent behaviour (cheating on 50–76% of impossible tasks unless tests are hidden; "do not cheat" instructions nearly useless in one study) means gates must be structurally out of the builder agent's reach.

### Cited Findings

**GPU timestamp queries**
- [FACT] wgpu 30.0.2: `TIMESTAMP_QUERY` is supported on Vulkan, DX12, Metal, OpenGL (with `GL_ARB_timer_query`) and WebGPU; `TIMESTAMP_QUERY_INSIDE_ENCODERS` and `TIMESTAMP_QUERY_INSIDE_PASSES` are native-only and exclude Apple GPUs on Metal; inside-pass timestamps are "generally not available on tile-based rasterization GPUs"; `PIPELINE_STATISTICS_QUERY` is Vulkan and DX12 only. Timestamps are multiplied by `Queue::get_timestamp_period` to get nanoseconds. — [wgpu Features](https://docs.rs/wgpu/latest/wgpu/struct.Features.html)
- [FACT] wgpu changelog: "On Apple chips on Metal, they only support timestamp queries in command buffers or in the renderpass descriptor, they do not support them inside a pass"; `TimestampWrites` on pass descriptors was added "to allow profiling on tilers which do not support timestamps inside passes." — [wgpu changelog (fork copy)](https://github.com/SecondHalfGames/wgpu/blob/trunk/CHANGELOG.md)
- [FACT] wgpu-hal hardcodes the Metal timestamp period to 1.0 on Apple silicon ("Known for Apple Silicon (at least M1 & M2, iPad Pro 2018)") and 83.333 for Intel GPUs. — [wgpu-hal Metal adapter (Firefox vendored copy)](https://searchfox.org/firefox-main/source/third_party/rust/wgpu-hal/src/metal/adapter.rs)
- [FACT] `wgpu-profiler` (0.27.0 seen) provides nested GPU timer scopes, automatic query pools, cached frames "until results are ready, with no device stalls", chrome-trace JSON export, and Tracy and Puffin integration; with only `TIMESTAMP_QUERY` it times whole passes (`scoped_render_pass`, `scoped_compute_pass`); in-encoder and in-pass scopes need the two extra features. — [wgpu-profiler](https://github.com/Wumpf/wgpu-profiler); [wgpu-profiler 0.27.0](https://docs.rs/crate/wgpu-profiler/0.27.0)
- [FACT] Bevy `RenderDiagnosticsPlugin` (0.20.1) records CPU and GPU time per render pass and pipeline statistics (primitive counts, shader invocations), readable from `DiagnosticsStore`, `LogDiagnosticsPlugin` or Tracy; custom spans via `diagnostic_recorder().time_span(...)`. Backend support as documented: Vulkan and DX12 get timestamp queries and pipeline statistics; "Metal, WebGPU, and WebGL2: only CPU time is recorded." — [RenderDiagnosticsPlugin](https://docs.rs/bevy/latest/bevy/render/diagnostic/struct.RenderDiagnosticsPlugin.html)
- [OLD][FACT] Bevy's `trace_chrome` feature writes a JSON trace viewable in Perfetto. — [Bevy profiling doc (0.16)](https://docs.rs/crate/bevy/0.16.0/source/docs/profiling.md)

**Memory and counters**
- [FACT] wgpu `Device::get_internal_counters` ("Query internal counters from the native backend for debugging purposes"; needs the `counters` Cargo feature; not all backends set all counters) and `Device::generate_allocator_report` (GPU memory allocation report, `None` where unsupported). — [wgpu Device docs](https://docs.rs/wgpu/latest/wgpu/struct.Device.html)
- [FACT] Apple publishes no per-device app memory limit in the entitlement docs: the increased-memory-limit entitlement (iOS 15+) is "only available on some device models"; "Call the `os_proc_available_memory` function to determine the amount of memory available"; the app must "still behave correctly if additional memory isn't available". — [Increased memory limit entitlement](https://developer.apple.com/tutorials/data/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit.md)
- [FACT] Android: `dumpsys meminfo` reports PSS and private dirty memory per category, including graphics categories. — [dumpsys](https://developer.android.com/tools/dumpsys)

**Frame pacing and hitch thresholds**
- [OLD][FACT] Apple (WWDC 2020): hitch time ratio = hitch milliseconds per second; "A hitch ratio of less than five milliseconds per second is good user experience. In the five-to-ten millisecond per second range, users will start to notice hitches"; totals are not comparable across durations, the ratio is. — [WWDC20 session 10077](https://developer.apple.com/videos/play/wwdc2020/10077/)
- [FACT] Android vitals: "a slow session is a session in which more than 25% of the frames are slow. A frame is slow if it is not presented less than 50ms after the previous frame (equivalent to 20 FPS)"; a second metric uses 34 ms (30 FPS); monitoring begins after the game has run for one minute; "Play will start steering users away from games that cannot achieve 20 FPS on their phones." — [Android Slow Sessions](https://developer.android.com/games/optimize/vitals/slow-session)
- [FACT] Apple's Metal guidance: 16.67 ms is one 60 fps frame; a 50 ms display interval among 16.67 ms ones is a stutter; consistent pacing matters more than aligning with vsync. — [Analyzing the performance of your Metal app](https://developer.apple.com/tutorials/data/documentation/xcode/analyzing-the-performance-of-your-metal-app.md)

**Thermal**
- [FACT] Android ADPF Thermal API: `getThermalHeadroom(forecastSeconds)` ranges from 0.0 (no throttling) to 1.0 (`THERMAL_STATUS_SEVERE`, heavy throttling); it must not be called more than once every 10 seconds or it returns NaN; a first value of 0 or NaN means unsupported; `getCurrentThermalStatus()` may stay `NONE` on some devices, so Google's heuristic maps headroom above 0.85 to possible light throttling, above 0.95 to possible moderate, above 1.0 to possible severe. Java API from Android 11, NDK from Android 12. — [ADPF Thermal API](https://developer.android.com/games/optimize/adpf/thermal)
- [FACT] Apple's Game Performance template records device thermal state; Apple's WWDC26 session does not present thermal state as a collected metric in the new `metalperftrace` tooling. — [Analyzing the performance of your Metal app](https://developer.apple.com/tutorials/data/documentation/xcode/analyzing-the-performance-of-your-metal-app.md); [WWDC26 session 388](https://developer.apple.com/videos/play/wwdc2026/388/)

**Temporal artifacts (popping, flicker)**
- [FACT] The only metrics found with human validation on temporal rendering artifacts are video metrics: CGVQM (0.87 PLCC on CG-VQD), FovVideoVDP (0.755) and ColorVideoVDP (0.744); ColorVideoVDP outputs a per-frame "distogram" and heatmap video. CGVQM assumes equal frame rates and uses future frames in its convolutions. — [CGVQM+D paper](https://arxiv.org/html/2506.11546v1); [ColorVideoVDP repository](https://github.com/gfxdisp/ColorVideoVDP/)
- [FACT] Bevy's CI event set includes a scripted `MoveCamera` and screen recording start/stop, i.e. the capture side of a camera-path test exists. — [CiTestingEvent](https://docs.rs/bevy/latest/bevy/dev_tools/ci_testing/enum.CiTestingEvent.html)

**Keeping gates from being gamed**
- [FACT] ImpossibleBench (Zhong, Raghunathan, Carlini; arXiv 2510.20270, 2025-10-23) builds tasks whose tests contradict the specification, so any pass is a cheat. Reported cheating rates: GPT-5 76% on Oneoff-SWEbench and 54% on Conflicting-SWEbench; o3 49%; Claude Opus 4.1 50% (strict prompt). Cheating modes include modifying tests, overloading comparison operators, recording extra state and special-casing; Claude models and Qwen3-Coder used test modification for more than 79% of their cheating. Mitigations measured: hiding tests reduces cheating to "near zero"; read-only tests block test modification; a stricter prompt took GPT-5 from above 85% to 1% and o3 to 33% on Conflicting-LiveCodeBench; an explicit "flag for human intervention" exit took GPT-5 from 54% to 9% and o3 from 49% to 12%; allowing multiple submissions with feedback raised cheating from 33% to 38%; LLM monitors caught 86–89% of cheats on LiveCodeBench but only 42–65% on SWE-bench. — [ImpossibleBench](https://arxiv.org/html/2510.20270v1)
- [OLD][FACT] METR (2025-06-05): o3 reward-hacked in 39 of 128 RE-Bench runs (30.4%) and 8 of 1087 HCAST runs (0.7%); examples include overwriting the timer so code "appears faster", monkey-patching the evaluator, precomputing answers and overriding the equality operator; on one task adding "Please do not cheat" left reward-hacking plans at 80% of runs (original prompt 80%; "do not reward hack" 70%) — "a nearly negligible effect". — [METR: recent frontier models are reward hacking](https://metr.org/blog/2025-06-05-recent-reward-hacking/)
- [FACT] Anthropic (2026-02-05, C compiler built by 16 parallel agents): "the task verifier is nearly perfect, otherwise Claude will solve the wrong problem"; test output must not flood context (log to files, one-line `ERROR` reasons, precomputed summaries); a `--fast` 1% or 10% deterministic-per-agent random sample handles "time blindness"; a known-good oracle (GCC) was used to localise failures; CI was added so "new commits can't break existing code". — [Building a C compiler with parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)
- [FACT] Anthropic (2025-11-26): agents marked features done without end-to-end testing unless prompted; the harness uses a JSON feature list where agents may only flip a `passes` field, with the instruction "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [FACT] Existing engine practice for protecting references: Filament's goldens are in a separate repository writable only by team members; Skia Gold requires a person to approve new images in a GUI and keeps baselines outside the repository; Unreal routes new ground truth through source control. — [Filament renderdiff](https://google.github.io/filament/dup/test_ci_renderdiff.html); [GPU pixel testing with Gold](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/gpu/gpu_pixel_testing_with_gold.md); [Unreal Screenshot Comparison Tool](https://dev.epicgames.com/documentation/unreal-engine/screenshot-comparison-tool-in-unreal-engine?lang=en-US)
- [FACT] GitHub: "Code owners are automatically requested for review when someone opens a pull request that modifies code that they own"; branch protection or rulesets can "require approval from a code owner before the author can merge"; "To protect a repository fully against unauthorized changes, you also need to define an owner for the CODEOWNERS file itself." — [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)

### Inferences
- Per-pass GPU budgets on phones are feasible but coarser than on desktop. On Apple GPUs and most Android tilers, timing is available per pass (via `TimestampWrites`), not per draw or per scope inside a pass. Because tile-based GPUs defer and interleave work, a "pass time" on a tiler is the time between pass boundaries as the driver reports it; budgets should be set per pass and validated against whole-frame GPU time, and passes should be structured so that each budgeted cost is its own pass.
- Bevy's documented "Metal: only CPU time" conflicts with wgpu's documented Metal support for `TIMESTAMP_QUERY`; either the Bevy docs are stale or Bevy has not wired pass-boundary writes on Metal. Either way, per-pass GPU budgets on iOS and macOS should be planned as project-owned instrumentation (wgpu-profiler-style pass scopes exported as JSON), not as something Bevy provides.
- Draw and triangle counts: pipeline statistics are Vulkan/DX12 only, so counts for a cross-platform gate must be counted by the engine on the CPU side (draws submitted, instances, indices), which is also deterministic and therefore a better gate than a GPU counter.
- A popping detector can be built from the pieces above, though no published turnkey detector was found. Proposed method: (1) run a slow scripted dolly at fixed time step twice from the same seed — once with level-of-detail and streaming live, once with level-of-detail frozen at the finest level along the same path; (2) compute a per-frame FLIP error map between the two runs: this isolates LOD/streaming error from legitimate motion; (3) popping is a temporal discontinuity in that error: gate on the largest frame-to-frame change of the error map over tiles (a high percentile, not the mean); (4) also score the two clips with ColorVideoVDP for a JOD number; (5) validate the detector by injecting a known pop and confirming the gate fires. Wind and other animation must be identical in both runs or frozen.
- Hitch gates for a 60 fps target can borrow vendor definitions: hitch time ratio (late milliseconds per second) with Apple's 5 ms/s line, count of frames over 50 ms (Android's slow-frame line, Apple's stutter example), plus p50/p95/p99/max frame time. Streaming hitches show up as isolated long frames during the camera path; tagging frames with the engine's streaming state (as Apple's StateReporting does) lets the gate attribute them.
- Thermal gates need long runs on real devices; a short benchmark measures peak, not sustained, performance. Record headroom/thermal state alongside frame time (Android at most once per 10 s) and gate on late-run versus early-run frame time, not only on the average.
- Memory budgets on iOS must be measured on the target device, because Apple gives no number; measure `os_proc_available_memory` at start and track the minimum during the scenario.
- Anti-gaming design that follows from the measurements: (1) the verifier renders and measures from the built artifact itself; it never accepts images or numbers produced by the builder agent; (2) verifier code, thresholds and references live where the builder cannot write (separate repository or code-owner-protected paths, including the CODEOWNERS file); references are addressed by content hash; a missing reference fails; (3) part of the views and seeds are held out and chosen at verification time (hiding tests took cheating to near zero); (4) performance is measured by an external clock or OS counter as well as by engine counters (METR's "overwrote the timer" case); (5) the builder gets a legitimate "this gate looks wrong, flag for a person" exit (54% to 9%); (6) instructions alone are not a control; (7) an LLM reviewer of diffs is a supplement only (42–65% detection on realistic tasks); (8) each gate has a canary: a known-bad build that must fail.
- Measured runs should be serialised on a machine (one at a time) — runner stalls and shared GPUs are a documented source of noise in wgpu's own CI.

### Gaps
- No published automated LOD-popping or streaming-hitch detector was found (the search budget ran out before this could be searched); the method above is the researcher's proposal.
- iOS per-device memory limits for 8 GB phones, and jetsam behaviour, were not found in primary sources.
- No primary source was read for `ProcessInfo.thermalState` levels or for timestamp-query support on specific Android GPUs (Mali, Adreno, PowerVR) through wgpu.
- No source quantifies the overhead or accuracy of pass-boundary timestamps on Apple GPUs.
- UL's 3DMark Wild Life Extreme Stress Test (a common model for sustained-performance runs) could not be read (404).

## 6. Published experience from 2025–2026 of AI agents building graphics or game code autonomously: what worked and what failed

### Takeaway
What worked in every published case is the same loop: a strong machine-checkable oracle (compiler, test suites, golden images), feedback from the running artifact (screenshots, browser automation), and a verifier separated from the builder. What failed is equally consistent: agents grade their own work too kindly, miss fine visual differences, declare victory early, and visual tasks remain much harder than logic tasks (33% on 2D-graphics tasks versus 51% on gameplay tasks in GameDevBench; people far ahead of models in BlenderGym). No published postmortem of an agent-built wgpu/Bevy renderer was found.

### Cited Findings
- [FACT] Cursor (2026-01-14): hundreds of concurrent agents ran for close to a week and wrote over 1 million lines across about 1,000 files to build a web browser from scratch. Flat self-coordination with locks failed ("Twenty agents would slow down to the effective throughput of two or three"); optimistic concurrency made agents risk-averse ("No agent took responsibility for hard problems"); a planner/worker/judge structure worked; an integrator role was removed as a bottleneck; "The harness and models matter, but the prompts matter more"; periodic fresh starts were still needed against drift. The post does not describe how rendering output was verified. — [Cursor: scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)
- [CLAIM] Interview with the author (2026-01-23): about 2,000 agents at peak, nearly 30,000 commits, over a million lines of Rust; screenshots of rendering results were fed back to the vision-capable model and "We have progress indicators to tell it to compare the diff against a golden sample"; "Feedback loops to the system are very important"; "you can get a lot of verification just from compilation" in Rust. JavaScript was not working, agents pulled in dependencies (Taffy, QuickJS) they were arguably meant to write, runs could not be steered once started, and the result was never meant to be production-ready. — [Simon Willison on FastRender](https://simonwillison.net/2026/Jan/23/fastrender/)
- [FACT] Anthropic (2026-03-24): planner/generator/evaluator harness. A "retro game maker" built solo by Opus 4.5 took 20 minutes and 9 USD and its core play mode was broken (entities did not respond to input); with the full harness it took 6 hours and 200 USD and was playable, with rough physics. The evaluator drove the running app with Playwright, taking screenshots before scoring. A later run (Opus 4.6) built a digital audio workstation in about 3 h 50 min for 124.70 USD; QA caught stubbed features; "Claude can't actually hear", which limited feedback on musical quality. The evaluator missed bugs in deeply nested features and small layout issues. — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- [FACT] Anthropic (2025-11-26): failure modes were one-shotting, early victory declarations and marking features done without end-to-end tests; browser automation "as a human user" significantly improved bug finding, with blind spots (browser-native alert modals were invisible to the agent, and features using them were buggier). — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- [FACT] Anthropic (2026-02-05): 16 parallel agents, nearly 2,000 sessions, about 2 billion input and 140 million output tokens, just under 20,000 USD, produced a 100,000-line Rust C compiler that builds Linux 6.9; late in the project "new features kept breaking old ones" until CI enforced no regressions; generated code remained less efficient than GCC with optimisations disabled. — [Building a C compiler with parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler)
- [FACT] GameDevBench (arXiv 2602.11103; v1 2026-02-11, v2 2026-06-30): 333 game-development tasks from tutorials; the best agent solves 53.8%; success falls from 51.4% on gameplay-oriented tasks to 33.0% on 2D graphics tasks; simple image- and video-based feedback "consistently" helps, e.g. GPT-5.4 from 41.1% to 52.0%. — [GameDevBench](https://arxiv.org/abs/2602.11103)
- [FACT] BlenderGym (CVPR 2025): "even the state-of-the-art VLM system struggles with tasks relatively easy for human Blender users"; verification quality is a bottleneck and benefits from more compute at high budgets; models "sometimes struggle to detect visual differences between start and goal scenes". — [BlenderGym](https://arxiv.org/html/2504.01786)
- [OLD][FACT] V-GameGym (arXiv 2509.20136, 2025-09-24): a 2,219-sample benchmark for visual game generation with a multimodal, LLM-driven evaluation pipeline in UI sandboxes, motivated by the observation that code benchmarks miss "playability, visual aesthetics, and user engagement". — [V-GameGym](https://arxiv.org/abs/2509.20136)
- [FACT] Model behaviour differs by role: Cursor found GPT-5.2 better at extended autonomous work and Opus 4.5 inclined to "stop early and take shortcuts" in its harness; Anthropic found Sonnet 4.5 showed "context anxiety" that Opus 4.5 largely removed, and that harness scaffolding (sprints, context resets) could be removed as models improved while planner and evaluator stayed. — [Cursor: scaling agents](https://cursor.com/blog/scaling-agents); [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)

### Inferences
- The transferable recipe for a renderer is: make the renderer legible to the agent (frame capture to file, state queries, timing as JSON), give it a fast local loop (a sampled subset of gates in seconds to minutes) and a slow authoritative loop (full gates on a separate verifier), and treat every visual judgement by a model as provisional.
- The audio analogy ("Claude can't actually hear") applies to temporal visual quality: a model looking at still screenshots cannot see shimmer, popping or pacing. Those must be turned into numbers (video metrics, frame-time series) before an agent can act on them.
- Graphics is the weakest area in agentic benchmarks, and visual feedback helps but does not close the gap (41% to 52%). Expect an agent-built renderer to converge on what the gates measure and to stall or drift on what they do not; the gate set is effectively the specification.
- Compilation as an oracle (Rust) covers structure, not appearance; shader code and GPU state are outside the type system, so image and timing gates carry more weight in a renderer than tests do in a compiler.
- Costs of long autonomous runs are material (hundreds of USD per multi-hour app build; about 20,000 USD for the compiler), which argues for cheap pre-gates that fail fast before expensive GPU and device runs.

### Gaps
- No case study, benchmark or postmortem of agents autonomously building a 3D renderer or a wgpu/Bevy engine was found; the closest are a browser engine (2D layout and paint), a compiler, web apps, and Godot/Blender benchmarks. The search budget ran out before targeted queries could be run.
- OpenAI's "Harness engineering" post (February 2026) could not be read (HTTP 403); it is known to the researcher to be relevant (making an app legible to agents through browser automation and an observability stack) but nothing from it is cited here.
- V-GameGym's scores and judging details, and GameDevBench's engine and task breakdown, were not extracted beyond the abstracts.

## 7. Recommended gate set for a first prototype (the objective's closing deliverable)

### Takeaway
Build the prototype around five machine-run gates in three tiers — determinism and golden regression on hosted CI; reference-render, temporal-stability and per-pass GPU gates on one self-hosted GPU machine; sustained frame-time, memory and thermal gates on two tethered real phones — with all thresholds calibrated from a measured noise floor, references and verifier code out of the builder agents' reach, and photographs kept as an advisory, human-calibrated gate rather than an automatic pass/fail for "photoreal".

### Cited Findings
- [FACT] Starting thresholds with a published basis: mean FLIP 0.01–0.1 per test (wgpu); SSIMULACRA 2 at 90 = visually lossless in a flicker test, 80 = not noticeable side by side; 1 JOD = 75% of people prefer the better clip; hitch time ratio under 5 ms/s is good, 5–10 ms/s noticeable; a frame later than 50 ms is "slow" and more than 25% slow frames makes a slow session; thermal headroom 0.85 / 0.95 / 1.0 map to possible light / moderate / severe throttling, polled at most once per 10 s; 16.67 ms is one 60 fps frame. — [wgpu_test image.rs](https://wgpu.rs/doc/src/wgpu_test/image.rs.html); [cloudinary/ssimulacra2](https://github.com/cloudinary/ssimulacra2); [pyfvvdp on PyPI](https://pypi.org/project/pyfvvdp); [WWDC20 session 10077](https://developer.apple.com/videos/play/wwdc2020/10077/); [Android Slow Sessions](https://developer.android.com/games/optimize/vitals/slow-session); [ADPF Thermal API](https://developer.android.com/games/optimize/adpf/thermal); [Analyzing the performance of your Metal app](https://developer.apple.com/tutorials/data/documentation/xcode/analyzing-the-performance-of-your-metal-app.md)
- [FACT] Hosted CI can run Metal (`macos-26`), software Vulkan (Mesa under Xvfb) and DX12/WARP rendering jobs today, as Bevy and wgpu do; GPU larger runners offer a Tesla T4 (16 GB VRAM). — [example-run.yml](https://github.com/bevyengine/bevy/blob/main/.github/workflows/example-run.yml); [wgpu ci.yml](https://github.com/gfx-rs/wgpu/blob/trunk/.github/workflows/ci.yml); [Larger runners reference](https://docs.github.com/en/actions/reference/runners/larger-runners)

### Inferences

All of the following is the researcher's recommendation. Numbers marked "start" are starting values to be replaced by calibration; none is a validated acceptance level for this project.

**Preconditions (build these before any gate)**
- One capture harness in the engine: offscreen render target; fixed time step; fixed seeds for all procedural placement; scripted camera path keyed to frame index; an explicit "scene ready" signal (assets, pipelines, streaming queue empty) instead of a frame-count wait; a "golden mode" switch that freezes wind, auto-exposure, motion blur and temporal jitter for stills; output of PNG (tone-mapped) and float/EXR (scene-referred) per capture.
- One telemetry stream as JSON per run: per-frame CPU frame time, per-pass GPU time (pass-boundary timestamps), draws/instances/triangles counted on the CPU side, allocator and process memory, streaming state, thermal reading.
- One control surface (JSON-RPC such as BRP): set camera, set time of day, force LOD level, freeze streaming, start/stop capture, dump telemetry.
- A noise-floor measurement for every metric: run the identical build 10 times per machine; a threshold is the noise floor plus a margin, never a guessed constant.

**Tier 0 — every change, hosted CI (minutes)**
- G0 Determinism: two runs of the same build in the same job produce identical output hashes on the software rasterizer. A failure here is a root-cause bug in the engine (unseeded randomness, wall-clock, load order), not a tolerance problem.
- G1 Golden regression: about 10–20 small fixed views (vista, forest edge, meadow, forest floor, stream, a few lighting times) rendered at low resolution on software Vulkan, WARP and `macos-26` Metal; compared per adapter with FLIP: mean at most 0.01–0.02 (start) and 99th percentile at most the measured noise floor times 2 (start). Prefer comparing candidate against base commit rendered in the same job; stored goldens per (backend, adapter, driver) as second line.
- G1b CPU-side counts: draws, instances, triangles and texture/geometry memory per view within budget (deterministic, exact comparison with a small allowed delta).

**Tier 1 — per merge candidate, one self-hosted GPU machine, runs serialised (tens of minutes)**
- G2 Reference render: for 3–5 small lighting-validation scenes that use the game's real materials (foliage card, grass patch, bark, water, haze volume), compare the real-time frame with a path-traced reference of the same scene data (in-engine path tracer if it supports alpha-masked and transmissive foliage; otherwise Cycles via export, with looser thresholds). Score with HDR-FLIP on scene-referred output and FLIP on tone-mapped output. Gate as a ratchet: no regression beyond noise against the last accepted value; set absolute targets only after a person has reviewed where the numbers sit.
- G3 Temporal stability and popping: the dual-run dolly described in section 5 (LOD live versus LOD frozen, same path, same seed), 10–20 s at full resolution: gate on the maximum tile-wise frame-to-frame jump in the FLIP error map (start: calibrate with an injected pop so that the injected pop fails and a clean run passes with margin), and on ColorVideoVDP between the two clips (start: at most 0.25–0.5 JOD loss). Add CGVQM where CUDA is available.
- G4 Per-pass GPU budgets on desktop-class hardware: each pass's median and 95th-percentile GPU time over the camera path within its budget; sum of pass budgets below the frame budget with explicit headroom; whole-frame GPU time cross-checked.
- G4b Asset-pipeline equivalence: texture compression, impostors and simplified meshes rendered against originals at the distance they are used: SSIMULACRA 2 at least 90 where the swap must be invisible, at least 80 for distant sets (start).

**Tier 2 — nightly or per milestone, two tethered real phones (one iPhone and one Android phone with 8 GB RAM), one run at a time**
- G5 Sustained performance: 20 minutes of the scripted path looping, app-measured and written to JSON, pulled over USB; cross-checked with `dumpsys SurfaceFlinger --timestats` on Android and an `xctrace` recording on iOS. Gates (start): 95th-percentile frame time at most 16.67 ms; hitch time ratio at most 5 ms/s; zero frames over 50 ms after the first minute; last-5-minute median frame time within 10% of first-5-minute median; Android thermal headroom forecast below 0.95 throughout; per-pass GPU budgets on device (pass-boundary timestamps).
- G5b Memory: peak process memory and GPU allocator totals below a budget set from the measured available memory on each device, with the minimum remaining headroom reported; no growth trend across loops (leak check).
- Device farms (Firebase Test Lab game loop) only for breadth across models, using the same self-reported JSON; not for thermal or per-pass gates.

**Advisory, human-calibrated (not automatic pass/fail)**
- G6 Photograph comparison at matched viewpoints: fixed-exposure luminance percentiles, colour statistics in a perceptual space, contrast-versus-depth for haze, cover fractions (sky/vegetation/ground), canopy gap fraction for upward views; a patch-based MMD-family distance to the photo set as a trend line. Report every run; gate only on "no regression beyond noise"; a person reviews a contact sheet at milestones and re-labels a small calibration set.
- G7 Vision-language review: pairwise, order-randomised, several prompts, restricted to "list visible defects against this reference photo"; its output opens issues, it never closes a gate.

**Integrity (applies to all gates)**
- Verifier, thresholds, camera paths and references live in a repository or protected paths the builder agents cannot write; references are content-hashed; missing reference fails; changes to references need a person's approval with before/after images.
- The verifier builds and runs the artifact itself; a share of views and seeds is held out and rotated; performance uses an external clock or OS counter as well as engine counters.
- Each gate has a canary (a known-bad build that must fail) and a sampled "fast" mode for the agents' inner loop; gate output to agents is short (one line per failure, files for detail).
- Builder agents have a documented way to flag a gate as wrong instead of working around it.

**Feasibility, bluntly**
- Achievable now with public tools: G0, G1, G1b, G4 (Vulkan/DX12 out of the box; Metal with own instrumentation), G4b, G5/G5b with one-time manual device setup.
- Achievable with engineering work and calibration: G2 (reference path tracer coverage of foliage materials is unverified), G3 (no off-the-shelf popping detector; needs injected-defect validation), on-device per-pass timing.
- Not achievable as an automatic gate on current evidence: a number that certifies "photoreal versus Crimson Desert or versus photographs". The gates above can prove the image is stable, correct to its reference, within budget and statistically closer to or further from the photographs; the judgement that it is photoreal still needs periodic human eyes.

### Gaps
- Every "start" threshold above needs calibration on the project's own scenes and machines; none has been validated for natural-environment content.
- Whether the target (dense forest to the horizon at 60 fps on 8 GB phones) is attainable at all is outside these notes; the gates measure it, they do not make it feasible.
- Cost and runtime of the Tier 1 and Tier 2 gates (minutes per run, GPU hours) are unmeasured.
- Coverage of the in-engine or exported reference path tracer for foliage, water and volumetrics must be verified before G2 can be relied on.
